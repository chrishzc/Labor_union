# LINE 客服與月嫂自助服務正式規格

## 1. 範圍、主切邊界與基本不變量

本文件定義 LINE 官方帳號人工服務、Webhook 同步回覆（`line_webhook_reply`）、月嫂端 LIFF 自助服務、管理端 LINE 工作台／手機審核，以及 `LINE-PAY-01`～`08` 繳款提醒與收據通知的現行正式契約。

- **Domain 邊界**：LINE Integration 擁有平台身分關聯、Webhook 收件與投遞任務，Customer Service 僅維護既有歷史紀錄與切換結案；訂單、排班、客戶帳務與月嫂應付等根事實仍由各自 owning Domain／Subsystem 唯一擁有並經既有 canonical writer 提交，UI 與 LIFF 不得旁路寫入業務根事實。
- **授權與主切**：所有非公開 LIFF 頁與自助服務 API 皆以 `server-verified LINE token` 結合伺服器端 `line_identity_bindings` 作為唯一授權依據；query string 上的 `userId`、顯示參數或未驗證前端狀態僅作導航輔助，不得構成授權或身分依據。舊入口退場後維持唯一新線，僅保留明確設定 `LINE_LEGACY_ROLLBACK_MODE=true` 時之緊急回退開關；禁止隱性雙寫與靜默回退。
- **PII 與憑證邊界**：送往群組訊息、公版預覽或通用審計的摘要一律套用去敏或明確欄位投影，禁止外洩未遮罩手機號、身分證字號、完整地址或原始 provider payload。

## 2. 官方帳號人工服務與舊工單交接

- 工會人員日常查閱 LINE 官方帳號並在原對話回覆一般詢問及正式客訴。通用聯絡、正式客訴、問答負評與業務求助均停止新增客服工單、人工升級、對話暫停及客服提醒。
- 舊求助 Postback 依原聊天室回一次留言指引。一般留言與舊通用求助文字交由工會在官方帳號查看。綁定、自助導覽與 FAQ 指令沿用各自入口。舊改資料與改訂單指令只回覆留言指引（見 §5.3）。
- 舊工單及事件留在原資料表。桌面 LINE 營運移除歷史客服紀錄入口，舊查詢 API 回傳 `410 Gone`。切換中既有工單留用原版本化結案 Preview／Apply 與證據檢核解除暫停，結案不建立客戶 LINE 通知。新建、認領、開始處理及系統回覆 API 退役。尚未處置且缺少必要證據的舊暫停由工會逐筆交接。

## 3. Webhook Reply-Only 與 Push 投遞分工（`line_webhook_reply`）

LINE 官方帳號回應依是否具備有效一次性 `replyToken` 嚴格區分同步回覆與主動推播：

### 3.1 `line_webhook_reply` 涵蓋範圍

下列兩類互動固定走純 `line_webhook_reply` 同步回覆通路，**禁止 fallback 改走 Push API**：

1. **第一批 — 一般文字、綁定引導與選單回覆（靜態回覆）**：操作引導、未綁定提示、客戶／月嫂／工會身分綁定入口回覆、群組設定指令格式錯誤與未註冊提示、舊求助 Postback 留言指引及已停用 AI 按鈕提示（加入好友歡迎訊息已退役並改由 LINE 官方帳號設定，系統不針對 `follow` 事件發送）。
2. **第二批 — Postback 按鈕與開工日付款文字回報即時確認（Batch 2）**：
   - 正式媒合月嫂意願按鈕與初步候選共用回覆卡的受理確認。初步候選按「可以接案」或「無法接案」時，Webhook 均先提交意願，再立即以 Reply 回覆「感謝回復!!已記錄」。寫入失敗不得送成功回覆。初步候選的意願記錄見 [媒合候選池規格 §3.1](02A_媒合候選池與客戶決定及通勤規格.md#31-寄送案件資訊候選詢問與更新詢問期間)；
   - 媒合推薦客戶端 Postback。接受配對仍發同事件 Reply，背景依媒合規格驗證並提交。舊求助按鈕只回官方帳號留言指引。
   - 請假或交接代班月嫂 Postback ack（願意代班／無法代班）；
   - 訂金及各期款項卡片保留「已經匯款」Postback。繳款疑問引導到同一私人聊天室留言。開工當天的第一期款提醒仍可在原案件群組回報。

### 3.2 `line_webhook_reply` 執行與驗證契約

- **即時 Reply 路徑**。凡使用 LINE Reply 的互動，在 Webhook 收到事件後走即時回覆路徑，其他作業可非同步交背景執行。回覆文案表示結果已記錄時，須在回覆前完成並提交該筆寫入。沿用現有回覆文案與不補發 Push 的規則。
- **時窗與嘗試上限**：單次 `line_webhook_reply` 任務最大嘗試次數固定為 `1`，有效時窗為自 Webhook `received_at` 起 **45 秒**。逾時、缺少有效 `replyToken` 或 LINE API 失敗時，立即標記為不可重試終態失敗（`non-retryable`），完整寫入投遞紀錄供稽核，**絕不降級改發 Push 訊息**。
- **同室同事件檢核**：投遞前比對 `line_inbox_events` 的原事件與來源聊天室。重送同一事件不重複發送。背景程式僅處理其餘業務及結清遺留 Reply 任務，逾時或未完成的 Reply 任務不在背景呼叫 LINE。
- **媒合客戶回覆失敗**。背景的檔期衝突或方案失效保留於 Inbox 失敗紀錄；暫時性故障沿 Inbox 重試規則。工會依失敗原因處理，客戶端維持單次受理 Reply。

### 3.3 `line_push_worker` 保留範圍

LINE 流程圖按觸發方式標示自動推播、人工發送或聊天室回覆。需求申請核准、請假排班完成、滿意度問卷及結算依各自正式流程維護公版。

主動通知、定時提醒、LIFF 送出後跨請求確認、卡片主體與多氣泡組合仍維持 durable outbox → `line_push_worker`：含 Flex 媒合／推薦／請假卡片、訂金／各期催繳提醒及取消／退款／追償通知；訂金、第一期、第二期確認入帳通知已移除系統 LINE Push 與後台範本編輯，改由工會人員於 LINE 官方帳號聊天後台使用預設訊息手動發送，系統內僅保留入帳待辦提醒與「已於官方帳號發送／標記已通知」確認結案。

歷史案件的通知接續資格、客戶綁定提醒及舊逾期款人工催繳邊界，依 [歷史案件通知接續責任分界](27_歷史訂單生命週期與服務天數帳務正式規格.md#81-歷史案件接續通知的責任分界)；LINE 通知查詢與排程共用該資格，驗收依同規格 `HIST-NOTIFY-01`～`05`。

## 4. 月嫂端 LINE 自助服務

月嫂通過姓名、身分證字號與生日綁定唯一 `staff_id` 後，透過 `staff_menu` 開啟高對比、大字版自助服務頁面。

### 4.1 個人案件查詢、群組小幫手選單與服務排程

- **月嫂專區四大 LIFF 銀髮長者友善設計通則**：
  - 圖文選單「月嫂專區」四大自助 LIFF（`staff_order_search.html`、`staff_schedule.html`、`staff_profile_update.html`、`staff_payout.html`）全面遵循銀髮長者友善人機介面規範：
  - **清晰大字體與高對比**：標題 24px～32px、內文 16px～18px、重要金額 28px～36px，嚴禁 12px 以下難讀小字；文字與背景符合 AAA 護眼高對比。
  - **質樸溫潤沉穩配色**：全面採用與「我的排班」一致之溫潤護眼暖米底（`#f8f5f0`）、高對比深炭棕文字（`#241c18`）與工會深磚紅（`#973b17`）／暖杏色徽章（`#fcebdd` / `#8c320e`），禁止使用刺眼霓虹色、鮮綠漸層或高彩度色塊。
  - **大觸控區域與免打字點選**：按鍵、輸入框、選單高度至少 52px～56px，選項優先以大標籤按鈕點選，避免長輩繁瑣打字或格式輸入錯誤。
- **案件查詢（`staff_order_search.html`）**：呼叫 `GET /api/v1/line/staff-self-service/orders`，呈現個人承接中、待開工、已完成案件及曾受徵詢但尚未指派之案件。**客戶電話欄位以大字純文字安全呈現，不提供「一鍵撥號」（`tel:`）功能**，防止滑動頁面時誤觸撥出。
- **個人班表查詢（`staff_schedule.html`）**：
  - 只讀顯示 Scheduling `effective` 逐日排班，不納入 buffer。
  - **不在此個人排班 LIFF 提供「雙方合意延期」工作台**：「雙方合意延期」係案件專屬流程，由案件群組小幫手選單獨立發起（見 §4.2），不在個人排班 LIFF 混淆呈現。
  - **「我的不接案日期」專區**：月嫂可登記自己的不可服務起訖日與事由。LIFF 以已驗證的 LINE 月嫂身分呼叫 `/api/v1/line/staff-self-service/availability-blocks` 下的 Query／Preview／Apply，只能建立本人的有期不可服務紀錄。沿用 [Staff Availability §4](24_Staff_Matching_Preferences與不可服務期間正式規格.md#4-長假暫停接案不可服務期間) 的寫入、排班衝突及同鍵回執。月嫂端沒有強制保存權限。取得有效回執並讀回正式紀錄後才顯示登記成功。月曆和媒合使用同一份正式紀錄。本專區只在個人排班顯示。
    - **驗收**。月嫂以本人的 LINE 帳號登記沒有排班衝突的未來區間。送出後讀回同一筆正式紀錄與月曆，再重開頁面查一次。結果須有相同區間及原因。若排班衝突、拒絕或寫入尚不明，畫面不得自行加入紀錄或顯示成功。回應遺失時保留原請求，同頁重試沿用原操作鍵。
- **案件服務群組「月嫂專屬小幫手選單」（純 `line_webhook_reply`，0 Push 額度消耗）**：
  - 月嫂於案件群組輸入「工會」或「小幫手」時，系統以免費 `replyToken` 即時回覆選單卡片，所有互動步驟嚴禁使用 Push 額度：
    1. **【確認開工日】**：
       - **發起**：月嫂或客戶任一方可用原生日期滾輪選定約定開工日。卡片依發起方顯示「月嫂已發起，請客戶確認」或「客戶已發起，請月嫂確認」，系統以免費 ReplyToken 回覆「開工日期確認單」卡片。
       - **同意**：由對方點選同意，依 [`02_Assignments_Scheduling_Domain.md`](02_Assignments_Scheduling_Domain.md) `SSTART-01`～`08` 單一 UoW 自動完成排班並 Reply，提示可查看【服務排程】。自提自審防護：提案方若誤點同意按鍵，系統靜默不反應。
       - **重新選擇**：點擊【日期有誤，重新選擇】時，系統以 ReplyToken 發布「{角色}已取消本次提議，雙方可再次點選小幫手重新選擇日期」。
       - **正式開工後**：選單自動隱藏【確認開工日】。
    2. **【服務排程】**：以 7 欄排班日曆卡片呈現（標註多月嫂區段與固定排休日顏色圖例，精簡直觀不輸出冗長日期列表）。開工前點選提示預期排程或請雙方先確認開工日；正式開工後保留此選項，供雙方查閱已服務天數、剩餘天數與固定排休日。
    3. **【案件資訊】**：顯示確認月嫂時之服務條件與費用約定。以 LINE 原生高對比 Flex 卡片呈現三大完整約定區塊：①「服務約定」（案件編號、服務人員姓名、客戶名稱、預計服務起訖日、每日服務時段、每日服務時數、服務方式、希望服務天數、服務地址、下廚需求、胎數）、②「客戶付款約定」（訂金金額／預計繳款日、第一期款金額／預計繳款日、第二期款金額／預計繳款日、樓層費／預計繳款日、客戶應付總額）、③「其他約定」（特殊休假日、注意事項備註）。內容與正式推薦確認單一致，客戶、月嫂或工會人員皆可於群組小幫手選單點選按鈕查閱（不開放訊息文字指令觸發），純 `line_webhook_reply`，0 Push 額度消耗。
    4. **【雙方合意延期】**：請見 §4.2。
    5. **案件群組留言**。需要工會協助時在原案件群組留言，舊專員協助按鈕只回留言指引，舊客服結案指令停止受理。
    6. **【客戶常見疑問】**：提供客戶常見疑問導覽卡與標準回答庫（如食材採買、服務時段、補助撥款），當客戶提問時月嫂可操作選單以免費 `replyToken` 叫出工會標準回答；包含導覽卡文案、重要提醒、問題選項按鈕與公版標準回答內容，皆支援於後台「通知與發送」直接維護與即時預覽。
    7. **【滿意度調查問卷】**：正式完工後，本案月嫂在原群組重新開啟選單即可點選，依 §4.4 回覆問卷文案。

### 4.2 雙方合意延期（`leave-v1`）

- **觸發資格（月嫂專屬）**：
  - 案件服務群組小幫手選單【雙方合意延期】僅限本案月嫂操作。若客戶於群組點擊或傳送指令，系統以免費 ReplyToken 提示由本案月嫂選擇原服務日與補班日期。
- **開啟方式與零 Push 額度**：
  - 月嫂點選原案件群組的小幫手【雙方合意延期】後，官方帳號以 Reply 回覆申請卡。月嫂可在原群組重複使用同一個【開啟延期申請】按鈕進入本案 LIFF。全程 0 Push 額度消耗。
- **案件嚴格鎖定與身分辨識阻擋**：
  - LIFF 嚴格綁定單一 `case_no`，隱藏全域班表與其他案件，杜絕跨案操作。
  - LIFF 啟動時即時校驗 LINE 身份；若開啟者為客戶身分或非本案指派月嫂，即刻切換至全螢幕專屬阻擋畫面（標示 `🔒 僅限本案月嫂操作`、顯示客戶身分及案件編號，並提供【關閉並返回群組】按鈕），完全無法窺探或調整排班。
  - 已驗證為本案正式指派月嫂時，案件狀態、服務資料鎖定或沒有可調整服務日造成的限制，依排班查詢結果顯示目前無法調整的原因。符合「訂單成立」或「服務中」且有可調整服務日的案件才開放送出。
  - 查詢及送出均以本案當前正式指派為準。送出時重新確認案件狀態、服務資料鎖及所選服務日。群組綁定依 [Client Finance 訂金核銷規則](04_Client_Finance_Domain.md#unpaid-deposit-override) 檢查訂金已銷帳。
  - **延期視角隔離**：雙方合意延期專屬工作台完全隔離並隱藏個人排班專屬之「🚫 我的不接案日期」面板與一般請假區塊，絕不將個人非接案管理混入案件延期畫面中。
  - 申請卡的 LIFF 連結指定案件，每次使用均以當前 LINE 登入身分與案件指派驗證權限。先前已發出的限時連結沿用既有的 15 分鐘身分憑證期限，逾期時引導月嫂從小幫手開啟可重複使用的申請卡。
- **純延期補班與後台日曆多天調整**：
  - 本 LIFF 僅提供延期補班，維持約定服務天數與補助時數。局部代班由工會依 [多月嫂排班](31_MultiCaregiver_Admin_UI正式規格.md#4-局部代班工作面) 辦理。
  - 共用[案件排班月曆](31_MultiCaregiver_Admin_UI正式規格.md#case-staffing)的日期格與檔期標示。以圖例區分現行服務日、已取消原服務日、已新增補班日及空白休假。依畫面所選月份顯示本人檔期。其他案件的占用只標示類別，不顯示案件或客戶識別，也不提供跨案操作。
  - 月曆預選現行可調整的服務日。月嫂在同一張月曆點選任一日期即可加入或取消該日，換月時保留選取。畫面即時顯示已選及原服務天數。選取有變更且天數相同時，將取消的原服務日及新增的補班日分別按日期排序，再逐一配對顯示。補班日須晚於配對的原服務日。
  - 本案有同一位月嫂的多筆正式指派時，LIFF 提供切換。每次提案對應一筆指派。
- **檔期衝突預檢與群組確認連動**：
  - 選取有變更且服務天數守恆時，自動以後端唯讀預檢核對本次異動與月嫂本人檔期。重疊時顯示「檔期衝突」並阻擋送出，提示重新協調。變更選取後以最新結果判定，送出前重查。日期未變更或天數不符時不得送出。
  - 月嫂在原群組開啟 LINE 內的 LIFF，選擇單日或多日調整，檔期無衝突時按一次送出。LIFF 儲存草稿並代月嫂向群組傳出訊息。群組 webhook 核對案件、原群組與送出月嫂後，才將該草稿設為新的待確認提案，並以 `replyToken` 在原群組回覆一張「雙方合意延期確認單」。同一筆草稿的重送不重複建立確認卡。
  - 群組訊息請客戶確認是否同意日期調整，並顯示該案的簡短提案編號。重送同一筆申請會沿用同一編號。後台依編號辨識對應草稿，確認卡的按鈕仍綁定該筆提案。
  - 送出後可留在同一個 LIFF 修改日期，或在原群組重開同一張申請卡。日期有變動且重新通過檔期檢查時，月嫂可送出新提案。正式排班維持最近一次客戶確認的結果，直到客戶同意當前最新提案。
  - 外部瀏覽器、私聊或 LIFF 未設定傳訊權限時，頁面在提交前提示從原群組開啟。提案草稿持久化、LINE 傳訊及原群組 webhook 受理是各自可查證的結果。LINE 傳訊結果不明時，保留原提案識別，只提供查詢原提案。查到 webhook 受理才顯示原群組已受理。查不到受理紀錄時維持未確認，不能據此重傳群組訊息或建立新提案。
  - 確認卡只允許操作卡面對應的現行提案。原群組核對並接受新提案後，舊卡的同意與不同意均回覆失效。只有本案客戶點選最新卡【同意延期補班】才會於單一 UoW 更新正式排班，月嫂點同意時靜默不處理。
  - 本案客戶點選最新卡【不同意，重新協調】可拒絕提案，原提案月嫂點選同一按鈕可撤回提案。官方帳號用 Reply 回覆取消結果，原排班保持原樣。其他群組成員無法取消提案。
  - 確認時的檔期衝突依 [Scheduling 衝突處理](02_Assignments_Scheduling_Domain.md#service-start-and-substitution) 辦理；操作入口見 [案件人力配置](31_MultiCaregiver_Admin_UI正式規格.md#case-staffing)。
- 舊直送及雙邊確認 API 依 [入口治理規格](19_Global_Entry_Point_Governance.md#32-已停用移除之端點與替代邊界) 退役。

### 4.4 滿意度調查問卷

- `Orders` 正式狀態為 `訂單完成` 時，本案已綁定身分的正式服務月嫂在原案件群組重新輸入「小幫手」，新選單才顯示【滿意度調查問卷】。點選時，系統重新核對正式完工狀態、群組及月嫂歸屬，隨即在原群組 Reply 目前的純文字範本。預設範本只有文字。具文案維護權限的工會人員可在「通知與發送」的同名範本加入問卷網址，後續回覆即帶出該網址供客戶開啟。問卷回覆不改變完工與帳務狀態。
- LINE 流程圖的「群組小幫手選單」提供「已約定開工」與「服務已完成」兩種公版。工會可從既有小幫手文案頁切到正式完工的唯讀公版。
- 完工事件的自動群組投遞依 [LINE Gateway](17A_LINE_Gateway_Inbox與通知投遞正式規格.md#2-line-webhook-inbox-與-delivery-task-骨架)。

| S 情境 | T 任務 | A 操作 | R 可觀察結果 |
|---|---|---|---|
| 訂單已正式完工，本案月嫂在原案件群組 | 發送問卷訊息 | 開啟小幫手後點選【滿意度調查問卷】 | 原群組收到一則即時純文字 Reply，無 Push。預設文字無網址。 |
| 訂單尚未正式完工，或操作人與本案月嫂身分不符 | 阻擋非適用的問卷操作 | 開啟小幫手並嘗試點擊舊卡的問卷項目 | 選單不顯示問卷項目。舊卡操作無法發送問卷。 |
| 工會人員已在「通知與發送」儲存含問卷網址的範本，訂單已正式完工 | 提供客戶問卷入口 | 本案月嫂在原案件群組點選【滿意度調查問卷】 | 原群組的 Reply 使用新文字及所填網址。 |
| 工會正在查看小幫手選單公版 | 核對各階段選項 | 從流程圖或文案頁開啟兩種公版 | 「服務已完成」公版顯示【滿意度調查問卷】。「已約定開工」公版無此選項。 |

## 5. 管理端 LINE 工作台、手機審核與 LIFF 設定

### 5.1 管理端桌面分頁

LINE 管理介面依 [`19_Global_Entry_Point_Governance.md`](19_Global_Entry_Point_Governance.md) 拆分為四個獨立桌面入口，另整合 `#notifications` 全域通知中心：
- **`#line-management`（LINE 營運）**：整合身分綁定查詢／撤銷與審核（`binding`）及服務群組作業（`order_groups`）。舊 `tab=tickets` 連結回到身分與授權。電腦與手機的通知事項移除客服工單來源。
- **`#line-notifications`（通知與寄送）**：整合統一通知與發送工作台（`push_queue`，支援 `?tab=push_queue&message=<id>` 定位）與寄送追蹤／異常，並維護含 Flex 在內之通知文案／設計公版；繳款收據深連結（`#notifications?subtab=payment_receipt`）於通知事項頁跟催。
- **`#line-interface`（LINE 介面設定）** 與 **`#line-faq`（LINE 常見問答）**：
  - `#line-interface` 包含圖文選單（`visitor`／`customer`／`staff`／`union_staff` 四角色草稿）、**LINE 表單工作室（`LiffCardStudio`）** 與 LINE 流程圖；表單工作室提供現行官方 LIFF 表單與行動工作面預覽（含 `gateway.html` 兩步導流、`register.html` 需求調查、`non_citizen_registration` 非市民服務申請與三個 `mobile_admin` 視圖，不含 `staff_baby_log.html` 與 Flex 訊息卡片），其中 `gateway` 與 `non_citizen_registration` 透過同源唯讀預覽端點 `/api/v1/line/identity/studio-preview/{gateway|non-citizen-registration}`（經 `applicationUrl` 支援前綴代理）載入互動預覽，右側僅呈現唯讀預覽與官方入口操作。
  - [LINE 介面設定的引導動作分頁](19_Global_Entry_Point_Governance.md#21-現行導航與頁面清冊)提供觸發指令編輯與唯讀預覽。不執行模型問答。清單依系統內建流程標示「僅手動輸入」與「有其他入口」，並可篩出只靠聊天室手動送出文字的動作。系統按鈕會代送文字或可從其他入口完成同一動作時，詳情須指出該入口，例如「常見問題」的圖文選單按鈕。

  - LINE 常見問答提供「常見問答題庫」與「LINE 聊天室版面」兩個分頁。新增分類、編輯卡片和手機預覽留在同一管理入口；不提供公開 FAQ 網頁或 AI 問答。兩種發布的作用範圍依 [共用問答與聊天室版面](29_LINE服務說明、客服互動與選單角色正式規格.md#41-共用問答與聊天室版面)。

### 5.1.1 通知事項分類與處理入口

- `#notifications` 依目前帳號權限查詢各來源。每筆提醒由原 owner 依自身業務條件判定。其他提醒是否出現、已處理或已移除，都不影響此筆資格。回到通知頁或手動刷新時，以目前資格和共用移除結果更新清單及計數。來源讀取失敗須明示，不能以零筆代替。搜尋只涵蓋已載入事項，各來源保留分頁及完整總數。
- 桌面與手機依同一份來源目錄篩選，依序呈現「申請與資料」、「LINE 身分」、「媒合、簽約與交接」、「款項」、「案件群組」。目錄提供每個來源的分類識別及名稱。各端只列含有權限可見來源的分類，分類計數與頂部待辦總數只納入該端可見待辦。原 API 的 `review`／`reminder` 識別保留供既有呼叫端使用。
- 日誌缺漏、客服工單、申請請假、系統狀態以及系統與寄送異常（`delivery`、`notification_failure`）不列入待辦清單與頂部待辦總數。系統狀態沿既有獨立摘要，寄送與通知建立異常由 `#line-notifications`（通知與寄送）工作台統一查詢與處理。「寄送紀錄」分頁保留 `support` 篩選。
- 各來源沿用原 owner 的業務條件與作業入口。寄送與通知建立異常共用 [LINE 處理投影及結清契約](17A_LINE_Gateway_Inbox與通知投遞正式規格.md#41-共用待辦判定與操作資格)。歷史案件資格依 [歷史通知接續責任分界](27_歷史訂單生命週期與服務天數帳務正式規格.md#81-歷史案件接續通知的責任分界)。

| 申請與資料 | `registration` | 以原申請編號開啟原審核作業。桌面進入客戶名冊指定申請，手機開啟同筆申請的行動審核入口 |

「客戶已接受配對，待辦簽約」沿媒合資格列出仍需簽約的方案，並依現行契約的 Orders `contract_completed` 及契約識別判定完約。透過[正式 PDF 歸檔或其他正式途徑完成簽約](21_Contract_Signing_Commitment與正常驗收資料鏈正式規格.md#34-分開文件回收手工證明與本機測試跳過)後，清單及計數移除該筆待辦。

`registration` 依 [Case Import 待審清單及原申請讀回](17B_Case_Import與非市民Redis待審正式規格.md#registration-review-readback) 投影一般與非市民申請。每個原 `registration_id` 只列一筆。卡片只顯示申請類型標題、原申請編號、收件時間及處理入口，非市民使用「非市民申請待審核」。姓名、電話、問卷與銀行資料只由原審核入口依原權限讀取。通知事項不保存第二份申請或待辦，也不觸發 LINE 寄送。

`import_fields` 依 `data_browser.read` 唯讀查詢 Case Import 目前的 HCM／BeClass 欄位問題。每案一筆，詳情聚合該案問題及其正式修正入口，只列案號、問題說明與欄位定位。客戶名冊與訂單進件欄位的正式修正入口在桌面後台，因此手機目錄排除這個來源。修正後由原 Query 重新判定，各問題都解除時移除該案事項。選填欄位可由有資料修改權限的承辦在待辦逐欄確認「略過此欄」。HCM 明確允許留白的 email 經既有 Preview／Apply 保存欄位處置，不寫入原資料，也不沿用到新匯入版本；BeClass 退款欄位沿名冊既有「確認此欄留空」規則。必填、條件式必填和未確認可留白的欄位不提供略過入口。成功後讀回；同案尚有其他問題時繼續列出。本來源無整案略過、通用已讀或 LINE 寄送作業。

### 5.2 手機審核中心、DB 版控 LIFF 設定與非市民入口契約

- **`line-mobile-admin`**：統一行動審核入口，包含 `staff_review`、`order_tracking` 與 `dashboard` 三個視圖。舊 `customer_service` 連結導向待辦工作台。原獨立群組／主管異常推播已退役，管理員改從 `line-mobile-admin?target=staff_review` 頂端可收合系統狀態摘要卡（`retired_admin_alert` 狀態）查閱告警總覽。
- **LIFF 設定唯一來源與 DB 版本控管**：
  - 服務申請入口（`gateway.html`）、需求調查（`register.html`）、帳號綁定（`bind.html`）、非市民申請頁（`/line-non-citizen-registration`）及管理端設定統一讀寫 MySQL 之版本化 `LIFF` 設定（`LineConfigurationKind.LIFF`）。
    - **初次建立**：[`config/liff_settings.json`](../../config/liff_settings.json) 僅於資料庫尚未建立 LIFF 設定（`revision = 0`）時供明確 fresh bootstrap。
    - **執行期間**：禁止 fallback 讀檔。設定缺失、格式錯誤或資料庫不可用回 `503`；頁面不存在或停用回 `404`。
  - 公開與管理端沿用既有 `/api/config/liff`、`/api/config/liff/runtime`、`/api/config/liff/state`、主題／頁面／欄位設定（`/api/config/liff/theme`、`/api/config/liff/pages/{page_id}` 與欄位新增／修改／刪除）、版本歷史（`GET /api/config/liff/history`）與還原（`POST /api/config/liff/rollback/{revision}`），並共用 `LiffSettingsConfig` typed validation。
    - **並行更新**：`ETag`／`If-Match` 採資料庫 revision 執行樂觀併發檢查，讀取後遭並行更新回 `409`。
    - **還原與副作用**：還原於目前 revision 新增一版，不覆寫或刪除既有版本。所有設定異動僅留存版本與稽核，不建立訊息投遞或選單發布工作。
- **入口分流與非市民 LIFF 設定契約**：
  - `/line-gateway` 的正式畫面與後台預覽依 [服務閘道 §2](29_LINE服務說明、客服互動與選單角色正式規格.md#2-服務閘道gateway與登記入口規則) 呈現兩步分流。市民已登記與非市民已建案共用 `/line-bind`，各自依 §2 處理核對不到或資料不完整的結果。既有直接連結仍到原目的地。一般需求問卷使用 `/line-registration`。非市民專用合併表單固定由 `/line-non-citizen-registration`（後端於 `<body>` 注入 `data-registration-kind="non_citizen"`）開啟，管理端表單工作室則透過同源 `/api/v1/line/identity/studio-preview/gateway` 與 `/api/v1/line/identity/studio-preview/non-citizen-registration` 渲染唯讀預覽，且頁面內執行期設定查詢依當前預覽前綴解析 `/api/config/liff/runtime`。
  - 既有站台透過 `PUT /api/config/liff/pages/gateway` 直接更新導流頁版型、四個選項與對應網址。只調整需要變更的 LIFF 頁面，保留相容自訂文案、其他設定及歷史版本。後端非市民申請設定 API 維持提供 `GET /api/config/liff/non-citizen`、`POST /api/config/liff/non-citizen`（首次初始化）與 `PUT /api/config/liff/non-citizen` 供版本化查詢與寫入；前台 `#line-interface` 之「非市民服務申請」僅顯示唯讀互動預覽，不內嵌頁面欄位編輯表單。各項設定共用 `If-Match` 衝突控制。新站台的初始設定包含完整兩步導流。既有版本仍可讀取與還原，重複套用同一導流設定不得新增重複選項。
  - 保留既有輔助導流與 `register` 補助問卷設定，非市民必填系統欄位受共用 schema 驗證保護不得停用或設為選填（違規回 `422`／`409`），且非市民必填規則不套用到其他申請類別。一般問卷（`/line-registration`）與非市民表單（`/line-non-citizen-registration`）共用之 `register.html` 固定提供必填閉鎖單選「**胎數（單胞胎／雙胞胎）**」（對應 `特殊計費:胎數` 並提示將影響服務時薪標準，不沿用「第一胎／第二胎」自由文字輸入，亦不更動既有 DB `LiffSettingsConfig` 系統欄位清單）；銀行帳號備註及依申請類別區分的存摺圖片收集規則，依 [Case Import 非市民進件表單契約](17B_Case_Import與非市民Redis待審正式規格.md#31-非市民進件與配號nc-entrync-formnc-approvalnc-numbernc-stat)。非市民 LIFF 不顯示舊「寶寶資訊」多行文字輸入框與 `LINE ID`（`id="line_id"`）輸入欄（改由客戶主動加入官方帳號並保留系統 `clients.line_id` 欄位），送出時由所選胎數（`單胞胎`／`雙胞胎`）同步帶入 `baby_info`，且執行期套用設定安全略過缺席之 DOM 節點。待審收件、可離頁提示與原申請重送依 [Case Import §3.1](17B_Case_Import與非市民Redis待審正式規格.md#送件欄位與原申請查詢)，正式建案與 `A` 字頭編號規則見 [`17B_Case_Import與非市民Redis待審正式規格.md`](17B_Case_Import與非市民Redis待審正式規格.md#3-非市民自費進件與專用-redis-7-待審隔離架構)；新增頁面不新增 Rich Menu audience、選單發布或外部 provider 授權。

### 5.3 客戶資料與訂單異動流程

客戶如需變更聯絡方式、服務地址或訂單內容，在 LINE 官方帳號或案件群組留言，由工會專員確認後在客戶名冊或訂單管理直接維護。舊客戶自填表單、桌面審核與行動待辦入口均已退役，既有申請紀錄保留於資料庫。

#### 月嫂更新個人資料

- 已綁定的現役月嫂可由圖文選單左下角「我的資料」（`staff_profile_update.html`）開啟本人申請表。查詢與送件以目前有效的 LINE 身分綁定取得 `staff_id`。
- 個人資料申請欄位限手機、市話、分機、Email、縣市、郵遞區號、地址、緊急聯絡人姓名及電話，以及[接案偏好](24B_Staff_Roster_Case_Preference_Ownership_Clarification.md#21-可寫偏好-vs-只讀投影-vs-獨立能力-root)的兩項數字偏好和六項接案事實。「我的資料」在同一張申請受理[個人網頁照片與證照](35_月嫂個人網頁與照片審核發布正式規格.md#32-月嫂我的資料送審)。月嫂可只改原欄位、只附照片，或同時提交兩者。模板項目、日期要求、發布與到期提醒依該規格。
- **接案偏好條件規範**：
  - 調整接案偏好條件之格式與可選值嚴格符合後台規格（`canonical_service_period` 與 `RELATION_OPTIONS`）：
    - 偏好服務時段 (`service_periods`)：嚴格採用 `8小時(08:30-17:00)`、`8小時(09:30-18:00)`、`4小時(08:30-12:30)`、`4小時(09:30-13:30)`、`24小時(09:00-次日09:00)` 等標準起訖時間格式。
    - 偏好服務地區 (`service_regions`)：符合 `東區`、`北區`、`香山區`、`竹北市`、`竹東鎮`、`寶山鄉` 等標準鄉鎮市區。
    - 接案胎數 (`baby_types`)：`單胞胎`、`雙胞胎`。
    - 排休方式 (`rest_schedule`)：`週休二日`、`週休一日`、`連續服務`。
    - 承接天數區間 (`preferred_service_days`)：最少承接天數與最多承接天數。
  - 介面提供長者友善大按鈕點選，自動填入標準值，免除長輩繁瑣打字與格式出錯。
- **銀行收款帳戶變更**：
  - 將原分立之「金融機構代碼 (3碼)」與「分行代碼 (4碼)」合併為單一 7 碼欄位 `金融機構代碼與分行代碼（共 7 碼）`。
  - 前端輸入 7 碼數字（前 3 碼銀行代碼＋後 4 碼分行代碼），送出時由前端自動拆解為 `bank_code` 與 `branch_code`，完全相容後端既有 API 契約。原帳號於月嫂表單只顯示末四碼。通知只提供待審摘要與審核入口。
- 送件沿用[需求調查的 Redis 待審機制](17B_Case_Import與非市民Redis待審正式規格.md#32-核准前問卷不得進-mysql-與獨立-redis-7-架構reg-boundaryreg-redisreg-expiry)，以月嫂資料異動專用的 Redis 鍵與存取範圍保存待審內容。核准前申請內容不寫入 MySQL；待審查詢與通知摘要以申請編號辨識，同一核准操作以原操作識別及正式寫入回執核對結果。
- 送出成功時保存待審申請。月嫂端驗證回執的申請編號、版本及狀態後，才清空表單及顯示該申請的結果。回應不明時以同一已驗證月嫂身分及原送件識別查詢。查到回執就顯示原申請，確認未收件且原表單仍在才以同一識別與原資料重送。查詢故障維持結果未確認。已知送件衝突只查原申請，查無回執即停止送件。重開同一瀏覽器工作階段先查原送件識別。原資料已不在頁面時只允許查詢，避免再用同一識別提交另一份內容。異動資料、照片及身分憑證不寫入瀏覽器持久儲存。送審待辦提醒只出現在後台「通知事項」，由有審核權限的工會人員開啟對應申請。受理及審核不發送 LINE 通知。工會人員核對異動前後資料後核准或退回。核准才經各欄位既有的正式寫入流程更新主資料；退回、權限不足或資料版本衝突時，主資料不變。需到期日項目的通知資格另依[到期提醒契約](35_月嫂個人網頁與照片審核發布正式規格.md#24-到期提醒staff-web-04)。
- 同一次送件的所有異動屬於同一張申請，工會一次核准或退回整張。核准時，各正式寫入流程在同一筆 MySQL 交易內鎖定並重新核對來源資料版本，全部成功才提交。任一異動驗證失敗或版本衝突時，整筆交易回滾。正式提交後，才將 Redis 申請標為已核准並清除暫存的完整申請內容。
