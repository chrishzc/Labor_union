## 2. 核心不變量與公式（SSOT）

<a id="case-accounting-schemes"></a>

### 2.1 案件金額關係與資金代號（`SCHEME-AMOUNT-01`、`SCHEME-CASH-01`） ^case-accounting-schemes

| 符號／代號 | 定義與唯一口徑 | 正式負責 owner |
|---|---|---|
| `F` | 樓層費／其他費用合計（已計入 `T` 與訂金，不再重複加計） | Orders／Client Finance |
| `T`（案件總額） | 客戶端 `服務費 + F`；市民等於月嫂應收合計且工會不抽成。非市民客戶與月嫂分別依各自適用費率定價，差額為工會收入，不列金額異常 | Payroll（月嫂）／Client Finance |
| `S`（政府補助） | 本案補助金額（與工會實收 `G` 及是否設方案獨立） | Government Subsidy／Client Finance |
| `客戶應付（淨負擔）` | 一般情境為 `T - S`；§2.3 全額免自備加成差額不自動列客戶負擔 | Client Finance |
| `B`（客戶應繳工會） | `訂金應繳額（含 F） + 第一期 + 第二期` | Client Finance |
| `C` | 同案客戶款經正式核銷的累計實收，扣除原入款的有效沖正。不含預計應繳、未核對匯入、一般退款出款或政府入款 | Client Finance |
| `G` | 政府付工會（台新存入） | Government Subsidy |
| `P永`／`P台` | 永豐一般付月嫂／台新補助轉交月嫂（合計 `P = P永 + P台` 清償月嫂正式應收；市民時等於 `T`） | Staff Payables |
| `R永`／`R台` | 永豐正常退客戶／台新退客戶先墊補助（合計 `R = R永 + R台`） | Client Finance |

- **資金方向與提醒語意**：銀行核銷與款項方向嚴格對應 `receivable_from_client`（客戶存入 `C`）、`payable_to_staff`（`P永／P台` 月嫂應付）與 `payable_to_client`（`R永` 一般退款或調整；`R台` 對應 `subsidy_return` 先墊補助退還）；`subsidy_advance_due` 僅為唯讀應付／先墊提醒，不構成付款或自動核銷指令。

- **`SCHEME-AMOUNT-01／TERMS-01～03`**：客戶款與補助是同一案件總額 `T` 的資金來源；`B` 及各期金額依本案獨立繳款條款（未建列期款須經正式條款確認為 0 元始視為免繳；歷史案件依 [規格 27 §6](27_歷史訂單生命週期與服務天數帳務正式規格.md#historical-accounting-carry-forward) 承接原期款，缺漏列待確認，不虛構基準應收）。
- 非市民工會收入為客戶服務費與月嫂服務薪資差額，沿雙方正式帳務結果讀取，不由前端推算。例如各自時薪 350／320，8 小時雙倍日客戶服務費 5,600、月嫂應付 5,120、工會收入 480。僅服務時薪加成，不倍增整張帳單。
- **`SCHEME-CASH-01` 與守恆範例**：`工會收付差額 = C + G - P永 - P台 - R永 - R台`。非市民依獨立定價保留合法工會收入，不以差額非零判異常。下為市民 `T = 30,000`、`S = 12,000` 的典型完成淨額（均為實收減沖正後淨額）。此表是守恆範例，不排除 §2.2 以核對到的月嫂補助出款辨識方案一；不是正式收付更正或結清規則：

| 項目 | 方案一（分別入款） | 方案二（先墊後退） | 方案三（政府直接付客戶） |
|---|---:|---:|---:|
| `C`（永豐客戶入款） | 18,000 | 30,000 | 30,000 |
| `G`（台新政府入款） | 12,000 | 12,000 | 0 |
| `P永`（永豐付月嫂） | 18,000 | 30,000 | 30,000 |
| `P台`（台新轉交月嫂） | 12,000 | 0 | 0 |
| `R永`（永豐正常退客戶） | 0 | 0 | 0 |
| `R台`（台新退客戶先墊補助） | 0 | 12,000 | 0 |
| 工會收付差額 | 0 | 0 | 0 |

- **`SCHEME-BANK-01／02` 與 `SCHEME-SETTLE-01／02`**：銀行分類、案件方案分類與真實交易核銷分開；工會收付差額為 `0` 不能掩蓋未完成或錯付對象；方案分類本身不等於已收付或已結清。取消違約金依 [Client Finance 取消結算](04_Client_Finance_Domain.md#client-cancellation-settlement) 獨立認列，支出 `0～100` 元手續費依 [支出核銷規則](22_銀行流水匯入與帳務異常處理正式規格.md#outgoing-statement-fee-reconciliation) 處理。

<a id="holiday-recalculation-protection"></a>

**假日異動雙邊保護**：開啟或關閉雙倍均重算受影響的一般訂單。未有正式收付才可由兩方 owner 同步更新案件總額、客戶應收、月嫂應付及對應工會差額。任一客戶部分或全部正式核銷、月嫂正式出款，即保留該案兩邊原帳、工會差額及交易，不僅更新另一邊，也不自動追加差額調帳。正式收付依 Client Finance allocation／ledger 與 Staff Payables 的正式清償／付款事實判斷，不依 UI 標籤。落帳前在同一 outer UoW 鎖定重讀收付來源；競爭中的正式收付不得被覆寫，同鍵同命令重送沿用原結果而不重複入帳。歷史案維持原帳，含規格27 §8 精準重啟後狀態已回「訂單成立」而有 `orders_historical_precision_restart` 來源紀錄的案件。本規則同樣約束服務日期調整接續的假日重算，不改其他一般服務歸屬更正流程。設定或日期儲存成功不等於各案帳務重算成功；既有回執及案件／對帳入口須保留逐案結果、實際重算金額、未重算原因及重送身分。未重算失敗不得稱為「不需更動」，單案兩邊不得部分落帳。重試未重算案件須再讀最新服務來源與正式收付；已成功者不重複入帳，後續已有收付者保留兩邊原帳。 ^holiday-recalculation-protection

### 2.2 依核銷實收與補助出款辨識方案（`SCHEME-CLASSIFY-01～02`） ^scheme-classification

- **`SCHEME-CLASSIFY-01`**：一般單與歷史單共用判定。讀取本案獨立成立的客戶計價總額 `T`、正式補助 `S`，以及 Client Finance 同案已核銷客戶入款減有效沖正的累計實收 `C`。客戶收款與沖正依原收據辨認。未核銷明細、政府入款與一般退款出款不計入 `C`。歷史單只讀該案可追溯的計價、有效費率和補助資料，缺值留待確認。工作台綜合已收、應繳工會 `B`、前三期繳款進度和月嫂應付明細均不參與辨識。
- 除 §2.3 全額免自備例外，`T` 和 `S` 須可確定且 `S > 0`。同案的款項與受款對象證據須一致。`P台` 與 `R台` 均已有合格結果時，或 `R台` 與「少收恰為補助」互相矛盾時，保留待確認。
  - **方案一**：`T - C = S` 且有效實收為正，或 `C = T` 且已有同案台新補助轉付月嫂 `P台` 的正式核對結果。
  - **方案二**：`C = T` 且已有同案台新補助退還客戶 `R台` 的正式核對結果。退款承接 Client Finance 原義務、預檢與核銷。
  - **待確認**：`C = T` 而缺合格 `P台` 或 `R台` 時，列缺少已核對的補助出款。一般月嫂薪資 `P永`、政府入工會 `G` 與一般退款 `R永` 均不能補足。金額缺漏、超收、證據跨案、對象不唯一及證據衝突分別顯示原因。
  - **方案三**：經辦依 §3 確認政府直接退客戶。方案三不建工會的該筆應退補助，也不提供該筆核銷操作。一般退款、既有正式收付及歷史紀錄仍可依原入口查閱及處理。
- **`SCHEME-CLASSIFY-02`**：客戶款正式核銷成功或同案補助出款核對成功時，原命令讀取當下有效事實，符合條件才記正式確認。兩種結果可依任何順序取得，由後完成者用有效事實完成判定。只匯入、配對候選、查閱、預覽或收到尚無成功回執的 `202`，均不新增方案確認。原命令同鍵重播返回原結果。
- 未定方案時，原 Client Finance 可依已核實的交易及同案款項走既有部分收款或差額核對，保留欠款。`P台` 和 `R台` 候選沿原受款人、款項、日期、金額和來源預檢，在正式方案成立前也可核對符合原 owner 資格的交易。需要擬建款時在同一 outer UoW 重驗版本及金額，由原 owner 承接款項及核銷。命令失敗時，款項、核銷和方案事件一起回滾。
- 更正或沖正後，Query 以有效證據重新投影。銀行或收款確認的來源失效時顯示待確認原因，歷史事件仍可查閱。重新判讀不能自行反轉方案、核銷或出款，也不能改寫人工確認或已入帳金額。方案未定時，Payroll 仍依正式計薪事實建立及讀回月嫂應付，實際出款資格由 Staff Payables 判定。

### 2.3 全額補助免自備例外（`SCHEME-FULL-01～05`）

- **`SCHEME-FULL-01`（唯一條件）**：正式適用身分為 **補助市民** 或 **原住民**，且正式服務總時數 `H <= L`（`H` 是未按補助上限截斷的正式服務總時數；`L` 取本案有效政策或個案設定的上限，見[帳務規格 §2.2](04_Client_Finance_Domain.md#22-帳務參數與個案分段計價price-0109)，不用身分預設值代替）。身分、`H` 或 `L` 未知時留待確認；`H > L` 或一般市民回一般三方案。
- **`SCHEME-FULL-02／03`（結果）**：未涉及國定假日加成差額時，條件成立即自動 `S = T`、`B = 0`（訂金、第一期、第二期免繳），直接歸入「方案一全額補助免自備子情境」，補助經政府入工會後轉交月嫂 `P台`；不要求人工免自備審核、客戶實付、或先有零額期款列，不建立客戶 `R台`。
- 全額免自備已排班後開啟假日雙倍，不警示、不阻擋、不移班，服務費仍依 [PRICE-04](04_Client_Finance_Domain.md#holiday-service-pricing) 計算，補助不增加、客戶免繳不自動改為補差額。`S = T` 無法表達加成後 `T` 與獨立 `S` 的差額。例如原服務費及補助均為 2,800 元，8 小時全為雙倍後服務費 5,600 元，補助仍為 2,800 元、`B = 0`，另有 2,800 元未指定負擔人。只要兩邊都沒有正式收付，仍須重算並持久化案件總額及月嫂應付的結果，經既有正式帳務／對帳 Query 讀回，不只保存預覽候選或繼續顯示原價。重算金額、已入帳金額與待人工對帳差額分開表達。只有新增差額的負擔與相應入帳子項待決策，不因此跳過可完成的重算；不假填補助、客戶欠款、工會收入或正式分錄，不自動寄通知或移班。現有欄位若不足，須具體列出無法保存／讀回的金額或狀態，完成不受影響部分，不自行新增表或改正式資料庫；經辦沿 [22B 對帳](22B_帳務差額處置與工作台UI正式規格.md) 核對差異。補助仍由 [Government Subsidy](14_Government_Subsidy_Domain.md) 擁有。
- **`SCHEME-FULL-04／05`（守恆與分層）**：`F` 已納入 `T` 不再作第二道門檻；`P永 + P台` 合計僅清償 `T` 而不加薪；與既有收款或人工更正衝突時明示原因而不覆寫歷史；免自備自動成立不等於人工完成階段確認，仍可獨立保存人工安排。

<a id="subsidy-flow"></a>

### 2.4 補助獨立計算、B 生效時點與預檢（`SUBSIDY-FLOW-01～06`）

- **`SUBSIDY-FLOW-01／02`**：依原補助資格、有效上限 `L`、服務量與費率優先獨立計算 `S`（來源足即顯示金額，缺值顯示待確認，非 0 不補 0），不以方案或退款單為前置。方案僅決定對象（一：月嫂、二：客戶、三：政府直付），不使 `S` 由零變正、不重算前三期、不對月嫂與客戶雙邊重複建款。
- **統一金額口徑**（客戶名冊、案件抽屜、銀行核對、每月帳務與清冊共用）：

| 統一項目 | 唯一業務含義與來源 | 顯示限制 |
|---|---|---|
| 本案補助金額 `S` | Government Subsidy 含人工更正計算額 | 未定方案亦顯示；未知與 0 分開；非已成立退款或實付 |
| 應付月嫂補助／待付 | 方案一之下 `T` 內合法應付與未付餘額（Payroll／Staff Payables） | `P永 + P台` 不超過 `T`；未建單時標待成立，不以 `S` 作加薪 |
| 應退客戶補助／待退 | 方案二依 Client Finance 墊款來源成立之退款與餘額 | 與 `S` 分開；未成立／缺件明確標示，不誤顯為 0 元已結清 |
| 銀行原始實付 | 銀行列不可變 `debit` 原額 | 未核銷原列不計已清償，不用以重算 `S` |
| 已核銷金額 | owner 正式 allocation 清償額（含合法 `0～100` 手續費） | 例：應付 `12,000`、實付 `11,970`、手續費 `30` → 核銷清償 `12,000` |
| 方案三政府直付 | 本案 `S` 及政府直付客戶確認安排 | 本補助不列工會待退款、不追蹤政府實收、顯示不適用 |

- **`SUBSIDY-FLOW-03／04`（B 方案生效時點）**：原始銀行明細可先保存；預覽只列「依明細可確認方案一／二」候選，本身零寫入。保存原始明細及預覽都不正式確認方案、不移出進行中案件、不建款、不核銷。經辦觸發原「套用／確認處理（B）」，重讀並通過預檢後成功提交，才取得正式明細結果；方案辨識依 §2.2，原 owner 仍在同一 outer UoW 依計畫承接合法款項及核銷，不須再人工重選已可確定的方案。人工明確保存也是方案確認來源。人工設定方案一／二依[款項交接規則](16A_Accounts_Payable_Export與現金需求清冊規格.md#manual-subsidy-plan-payables-handoff)辦理；未到成立時點只確認方案並明示不建款。已到成立時點時，預檢通過後由原 owner 在同一交易承接合法款項及接續核銷。方案三依 §3 保存逐案直付安排，不表示政府已撥款或工會已核銷。

## 3. 公開契約：未來預設與逐案直付安排（`SCHEME-REPORT`、`finance_case_arrangement_events`）

- **`SCHEME-REPORT-01／02`、`SCHEME-DIRECT-01`**：對政府提出之補助清單沿用方案三報表格式；報表格式不等於逐案方案。逐案方案三只能人工確認，不改寫既有方案歷史金流，也不代表已撥款。
- **逐案直付安排保存與更正（`GET／POST /api/v1/finance-import/cases/{case_no}/accounting/arrangement`）**：
  - Owner：Finance Import statement-workspace；資料表 `finance_case_arrangement_events`（append-only，`confirm_direct | withdraw_direct`、`case_no`、連續 `version`、`actor`、`reason`、`created_at`、唯一 `operation_key`）。
  - 限制：§2.3 全額補助案件初次不接受確認方案三；初次確認須 `C = T`、`S > 0`，由經辦正面確認政府直接退給本案客戶，且無同案 `G／P台／R台` 衝突；變更採 `withdraw_direct` 追加事件（均必填 `reason`，UTC offset ISO 存儲、Asia/Taipei 顯示；`expected_version` 與 `Idempotency-Key` 防 stale 409 與重送）；後續沖正致客戶實收不再等於案件總額，或出現同案政府入工會、台新轉交月嫂或台新退客戶時，保留原安排與歷史事件並回報待確認原因。
  - **初次確認例**：一筆非 §2.3 全額免自備案件，`C = T`、`S > 0`，沒有同案 `G／P台／R台` 衝突。經辦確認政府直接退給該客戶、填寫原因並送出直付確認，成功後本案新增一筆 `confirm_direct` 安排事件，不代表政府已撥款。若其他條件相同，但確認前已有屬於本案的政府款入工會（`G`），則不能完成初次直付確認，不新增 `confirm_direct` 事件。

## 4. 驗收標準

1. **`SCHEME-A01～A16`**：涵蓋市民 `T = 服務費 + F = 月嫂應收` 與非市民獨立定價、依客戶核銷實收及補助出款對象辨識三方案、待確認條件（禁止缺 `G` 猜方案三）、方案三無此筆工會待退款與不追蹤政府直付實收、銀行對帳 `P永／P台／R永／R台` 嚴格分離與守恆、`SCHEME-FULL` 之 `H < L`／`H = L`／`H > L`／缺值與衝突檢核、以及清單格式獨立於實際金流。
   - **全額免自備正反例**：兩筆原住民正式案件的有效個案上限均為 88 小時，無既有收款或人工更正衝突。假日加成未改變服務費與補助關係時，以正式服務總時數判定：84 小時須自動成立，`S = T`、`B = 0`；92 小時不得先截為 88 小時後判定成立，須回一般三方案。
2. **`SUBSIDY-FLOW-A01～A17`**：涵蓋一般與歷史訂單先算 `S`、明細保存／預覽不生效直到 B 正式套用成功、尚無資料庫目標時之擬建款＋核銷四層預檢、`P永／R永／P台／R台` 原判定表與帳號例外區分、`應付 12,000／實付 11,970／費用 30／核銷 12,000` 統一呈現、先設方案後匯入與先匯入後設方案雙向流程，以及正式套用 B 失敗時整批回滾，不保留部分套用結果。依 §2.4 留待核對的同案方案衝突列不納入套用，其他通過預檢且無衝突的案件仍可繼續套用。
