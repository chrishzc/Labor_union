# 潛在狀態機規則盤點

## 文件狀態

- 狀態：文件整併第二階段的候選規則盤點。
- 用途：在整理同類文件時，同步擷取可能需要集中管理的狀態、事件、合法轉移、門禁及副作用。
- 本文件不是 `system_map.yaml`，不代表候選節點已通過 CP-1，也不代表文件所稱的「已實作」已在本輪完成獨立驗收。
- 本文件不建立一個涵蓋所有領域的巨大狀態機；每一組狀態必須有自己的 aggregate／workflow owner。

## 整理時的固定擷取規則

每一份後續整理稿都必須同步建立「狀態機候選」附錄，至少記錄：

1. 狀態或 workflow 的擁有者。
2. 狀態集合，以及哪些只是畫面狀態、衍生投影或處理結果。
3. 觸發事件、合法來源狀態與目標狀態。
4. 前置條件、拒絕原因、並行控制及冪等規則。
5. 同交易副作用及失敗回滾範圍。
6. 人工修正、暫停、重試、取消、重開及終態邊界。
7. 不可覆寫事實與只能追加調整／沖正的歷史資料。
8. 來源文件、已確認程度、衝突文件及待裁決缺口。

候選分類：

| 分類 | 定義 |
|---|---|
| 領域生命週期 | Aggregate 自身的正式狀態，具明確事件與合法轉移 |
| 命令工作流 | Preview／Apply、人工審核、匯入核銷等有開始、成功、拒絕或重試的流程 |
| 衍生投影 | 由正式事實計算出的目前結果，不允許 UI 直接指定 |
| 事件帳本 | 以 append-only 事件重建淨額或結果；重點是不變量，不一定有單一 current state |
| 操作流程 | Worker、Webhook、部署等系統處理生命週期，不屬於訂單 Domain |
| 非狀態機 | HTTP status、API envelope 的 `success`、行事曆顏色、單純顯示模式 |

證據標記：

| 標記 | 定義 |
|---|---|
| `confirmed-decision` | 來源文件明確記為已確認的產品決策 |
| `proposal` | 已形成方向，但仍待 SSOT／Checkpoint |
| `historical` | 舊設計、施工紀錄或已被後續決策取代 |
| `implementation-evidence` | 本次唯讀盤點找到相符 Schema／Service 證據；不等於完整驗收 |
| `conflict` | 來源文件彼此或與最新確認決策衝突 |
| `missing` | 有狀態名稱，但 owner、轉移、門禁或副作用不完整 |

## 一、訂單、媒合與排班

### ORD-01 訂單生命週期

候選狀態：

```text
洽談中 → 訂單成立 → 服務中 → 訂單完成
   └──────────────→ 訂單取消（僅限全部約定服務完成前）
```

自動評估優先順序：

1. 全部約定服務尚未完成且已有有效取消事件：`訂單取消`。
2. 目前時間已到達 `actual_end_date` 當日最後一個正式服務班次的結束時刻，且沒有已登記、會阻擋結案的未處理異常：立即自動成為 `訂單完成`；不是當日 00:00，也不等待隔日或客戶款項結清，且不因此立即鎖定服務資料。全部約定服務完成後不再接受取消訂單命令，即使客戶款項尚未結清、服務資料鎖尚未成立也相同。
3. 訂金已成功核銷、沒有「等待重新確認真正開始日」的阻擋異常，且已到仍有效的 `actual_start_date`、尚未完成：`服務中`。
4. 已到 `actual_start_date` 但訂金尚未成功核銷或核銷已被沖正：不得進入服務中，維持原狀並建立待工會人員處理的異常。
5. 正式契約流程已有完成事件、訂金已成功核銷且尚未開始：`訂單成立`。正常流程先簽約才建立訂金義務；舊資料只有訂金、缺正式簽署證據時進異常覆核，不得反推補造契約事件。
6. 其餘：`洽談中`。

主要事件：

- 建立正式 `case_no`。
- 訂金首次全額核銷或合法沖正。
- 儲存／更正 `actual_start_date`，或由工會人員完成真正開始日重新確認。
- 請假、代班、出勤或 assignment 套用。
- `actual_end_date` 重新計算。
- 跨越業務日期。
- `actual_end_date` 當日最後一個正式服務班次結束。
- 訂單取消、人工狀態修正、hold 解除或異常解除。
- 客戶應付款完成核銷、沖正或因調整而重新產生未結餘額。

已確認寫入權與交易邊界：

- 本輪納入付款事件與 ORD-01 的整合；範圍是消除 payment writer 對 `orders.status` 與案件服務資料門禁的直接寫入，不是新增 REF-01 退款功能。
- Payment Application Service 擁有付款分類、金額、allocation、核銷與 append-only 金流事實；ORD-01 只消費已成功寫入的付款事實，不計算金額、不執行匯款，也不推測退款。
- Payment Application Service 必須在同一資料庫交易內先寫付款事實，再呼叫 `OrderLifecycleApplicationService` 依最新付款、日期、異常、人工確認與排班事實重新評估。
- `OrderLifecycleApplicationService` 是訂單狀態、狀態歷史及案件服務資料門禁的唯一 writer；Payment writer、Finance importer、reprocessor、webhook 與 UI 不得接收 target order status 或直接呼叫通用 status update。
- 付款寫入、生命週期重算、狀態歷史與必要 outbox 任一步失敗時整筆回滾；相同事件重送則依 event／idempotency key 回傳既有結果，不重複核銷或轉移。
- 訂金核銷只建立 `deposit_reconciled = true`；進入服務中仍須通過 `actual_start_date`、`Asia/Taipei` 當下時間、真正開始日重新確認及其他 domain blocker。
- 第一／第二期款等客戶應付款只影響「全部結清」門禁，不能在服務完成前提前建立服務資料鎖；政府補助入帳及應退補助款不得誤算為客戶未結應付款。

已確認 Orders Terms 與相鄰 Domain 邊界：

- `client_name` 屬 Client Domain；姓名更正不觸發 assignment 重建，也不使既有 Preview fingerprint 過期。
- `orders.start_date` 是預計開始日根事實，`actual_start_date` 首次確認後凍結；`end_date` 可依凍結 start 與新服務條款重算，`actual_end_date` 則由有效正式服務日推導。
- `service_hours_per_day` 是獨立合約根事實，不由服務起訖時段差推算。`service_start_time`、`service_end_time`、`service_end_day_offset` 是不可拆分的案件統一服務時段條款；可在洽談早期全空，但簽正式合約、建立訂金義務或確認真正開始日前必須完整。
- 「訂金應收日」功能保留於 `client_payments.deposit_due_date`；實收日只由有效收款交易推導。`orders.deposit_date` 僅 legacy 唯讀相容，不得再作已收證據。`deposit_service_days` 移至 Client Finance 付款條款，assignment 重建不得修改。
- 所有 Terms Apply 共用不可變 `order_term_change_events`，保存完整 before／after、原因、操作者、版本、Preview fingerprint 與 idempotency key；`orders` 只保存目前投影。
- 正式契約是獨立操作／文件流程，不是已成立 Orders Terms 的權威。條款 Preview／Apply 不等待重簽；契約重發、第三方平台故障或 webhook 延遲不得回滾或阻擋已完成的 Terms Apply，只建立整合異常／重試。
- 系統內沒有訂單草稿。洽談在外部先完成後才匯入；同一 `case_no` 由 importer 與 DB 唯一鍵阻擋，來源內容錯誤由 Import Domain `review_required` 處理。Orders 不提供一般 DELETE、DiscardDraft 或 InvalidateImportedOrder。

門禁與副作用：

- `actual_end_date` 有值不等於訂單已完成。
- 每個案件使用一組統一的每日服務開始／結束時間，所有正常排班日、代班日及順延後服務日一律繼承；不支援逐日晚班或個別日期時間覆寫。
- 完成邊界是 `actual_end_date` 加上案件統一服務結束時間所形成的 `Asia/Taipei` 時刻，不是該日或隔日 00:00；必須由後端計算。
- 所有服務日期、案件服務時段、跨日判斷及完成時刻固定使用 IANA `Asia/Taipei`，不得隨伺服器、資料庫 session 或瀏覽器時區改變；若保存 UTC 時間戳，領域判斷前必須轉為台灣時區。
- 完成時刻以前或同一時刻已由後端受理的正式請假 Apply，優先於同案自動完成；草稿與 Preview 不取得優先權。
- 同案命令必須序列化。完成工作遇到優先請假交易時應延後重試；請假成功後依新 `actual_end_date` 評估，請假失敗／回滾後才依原事實完成。
- 完成時刻後才受理的補登請假不改寫排序歷史，但在案件尚未鎖定時仍可成功套用，並依新事實把訂單完成退回服務中。
- 填入未來 `actual_start_date` 會啟用正式精算，但日期未到前不提前進入服務中。
- 日期到達時還必須驗證訂金已成功核銷；未付訂金時月嫂不提供服務，不能以日期推測服務已開始。
- 「實際開始日已到但訂金未核銷」是需由工會人員處理的異常，不新增另一個訂單狀態。
- 異常解除前不得把排班日計為已完成服務，也不得觸發只適用於服務中的薪資或帳務副作用。
- 訂金在原 `actual_start_date` 經過後才核銷時，核銷本身不得解除異常或自動進入服務中；案件必須維持阻擋，等待工會人員重新確認真正開始日。
- 重新確認必須是具權限的明確命令，驗證訂金仍有效，並帶原因、操作者、原／新日期、預期版本與冪等鍵。
- 重新確認命令必須在同一交易更新 `actual_start_date`、重算實際排班、`actual_end_date`、薪資與帳務日期投影、解除異常並留下稽核歷史。
- 新確認日期已到且沒有其他阻擋時才進入服務中；若為未來日期，解除此異常後回到訂單成立並等待日期到達。
- 原已過期日期至新確認日期之間不得因重新確認而補記為實際服務日。
- `訂單完成` 是可依新事實重新評估的生命週期狀態，不是案件服務資料鎖；客戶款項尚未全數結清時，工會人員仍可用 Preview → Confirm → Apply 補登最後一天等既有日期的請假／順延／代班。
- 結清前補登順延使 `actual_end_date` 移至未來時，狀態應由 `訂單完成` 自動退回 `服務中`，到新的最後服務日後再自動完成。
- 「完成後仍可補登或更正服務根事實」不等於「完成後可取消訂單」。若更正後仍確認全部約定服務已完成，訂單維持 `訂單完成`；月嫂薪資以完整履約結果結算，不因人員口語上的取消服務而縮減。只有更正後證明服務其實尚未全部完成，才依新的根事實重評估狀態，但仍不得把已完成服務假造為中途取消。
- 案件服務資料只有在「訂單完成」且「客戶全部應付款已有效實收／核銷」兩項同時成立後，才禁止一般覆寫；客戶提前付清但服務未完成時不得提前鎖定。
- 案件服務資料鎖一旦成立即不可逆。後續退匯、沖正、退款或收款失效只能重新形成客戶應收、超收／退款、adjustment 或 reversal，不得解除服務資料鎖、恢復一般 assignment 重建或否定已發生服務。
- 工會應退還客戶的補助款不是客戶應付款；未退、待覆核、失敗或沖正均不得阻擋案件服務資料鎖成立。
- 案件門禁成立後的漏登或錯誤只能走具權限的完工後調整／沖正命令，追加修正與差額紀錄，不得覆寫原服務及財務事實。
- Query、頁面 render 或重新開啟畫面不得轉移狀態。
- 日期、狀態、未實現財務投影及狀態歷史應由 Application Service 在同一交易協調。
- 已實收、實付、核銷或月結事實不可覆寫，只能追加調整／沖正。
- 人工修正不得使用任意 `PUT status`，也不得接受任意目標狀態；只能修正訂金、實際開始日、服務日、排班、取消等根事實，由狀態機重新推導並保存原因、操作者、資料版本與不可變歷史。
- 取消後的受控重開是獨立命令：只有尚未產生取消相關退款、沖正或正式結算時才可受理；不恢復舊 assignment、schedule 或檔期鎖，必須重新 Preview。已有正式退款／結算時若仍需服務，建立新訂單。
- `human_hold` 控制類型已確認長期考慮移除：既有資料僅供歷史相容讀取，不新增 UI、API、欄位或狀態機依賴，也不建立新的 hold／release 命令。
- domain blocker 只能由對應 domain facts／command 解除。實際開始日已到但訂金未核銷、或延遲核銷後尚未重新確認真正開始日，不能由 Alert resolve 或歷史 hold release 繞過。

#### 訂單完成門禁候選：異常、領域事實與業務事件

本節是從既有異常規格、業務規則及目前實作擷取的**候選清單**，尚未完成最終裁決。候選必須先分層，不得把「存在 open alert」直接等同狀態門禁，也不得把應在上游 Apply 阻擋的非法狀態包裝成正常的完成門禁：

1. `write-time-invariant`：所有正式排班 mutation 在同一交易提交前必須滿足；不成立就拒絕 Apply，不能保存成等待完成時處理的狀態。
2. `completion-predicate`：合法 aggregate 到達完成時刻時真正需要評估的生命週期條件。
3. `consistency-assertion`：完成時可用同一 validator fail-closed 偵測 legacy、人工繞過、migration／import 或程式缺陷；不是正常業務流程的第二套限制。
4. `completion-reevaluation-event`：正式業務事件會觸發狀態重算，但事件本身不一定阻擋完成。
5. `case-lock-gate`：只影響完成後能否禁止一般覆寫，不影響服務生命週期完成。
6. `alert-only`：操作、前置流程、財務或稽核提醒，不得直接影響訂單完成。

已確認：權威門禁是可重算的 domain predicate；`finance_alerts`／`system_alerts` 只是稽核或顯示投影。人工認領或解除警示不得取代修正底層事實，也不得讓狀態機依 UI 工作流誤判。

##### D. 本輪擷取發現的漂移

- `SCHEDULE-006` 在訂單完成後才偵測服務量不符。正確修正不是再加一個正常完成門禁，而是讓所有正式排班 mutation 在寫入前共用 canonical invariant；完成時只作相同規則的 fail-closed consistency assertion。
- `SCHEDULE-001` 以「假日完全沒有排班」推測尚未決策，但相同資料形狀也可能是漏排、未選 outcome 或資料遺失；應先分類底層原因。
- 舊排班文件把已發生歷史服務日立即鎖死，與最新「訂單完成且客戶應付款全數結清後才禁止一般覆寫」衝突。
- 舊 LINE 規格把尾款入帳直接等同訂單結案，與最新「服務結束決定完成、客戶結清只決定案件鎖」衝突。
- 財務異常同時存在 snake_case 與 `CLIENT-*`／`RETURN-*`／`SUBSIDY-*`／`STAFF-*`／`COMMON-*` 兩套命名，缺少完整 canonical mapping。
- 現行一般訂單狀態 API 仍可直接寫入 `orders.status`，缺少合法轉移、原因、版本、權限、冪等及狀態歷史；目前也尚未找到正式的自動「服務中／訂單完成」production owner。
- 訂金推進「訂單成立」仍有多個分散 writer，狀態 ownership 尚未集中。
- 舊 BreezySign 規格在簽署完成後直接建立排班，與目前「客戶確認只取得等待訂金鎖、訂金核銷才轉正式 assignment」衝突。

| `fix_schedule_conflicts.py --repair` | 維運 CLI 可執行 | 可降級案件、清 staff 並刪除排班，缺 preview manifest、付款鎖、逐案確認與正式 correction history | `critical-operations-bypass` |
| historical order importer | 一次性正式匯入 | insert-only、不覆寫既有 case，但直接帶入 status／actual dates 且沒有 lifecycle history | `bounded-baseline-writer`，需 imported baseline event |
| client HCM importer | 正式主檔匯入 | insert-only、只建立洽談中及 planned dates | `bounded-case-created-writer` |
| fixture reconcile／snapshot import／reset | 僅 fixture／local test | 有固定範圍、checksum、dry-run／confirm 或 non-production gate | `non-production-exception` |
| frozen fake-data generator | 不可執行 | import 前即 `SystemExit`，system map 也禁止副作用 | `historical-reference-only` |

確認結果：

- 目前不是一個 canonical mutation boundary，而是至少五套各自擁有部分規則的 writer。
- 強路徑也不是完整 aggregate transaction：assignment synchronization 會處理 order dates 卻繞過 lifecycle；leave-resolution 的 Preview／Apply 契約最完整，卻沒有更新 order actual end 與全部後續投影。
- 正確整合方式是保留不同 typed Commands，共用 candidate builder、`ScheduleAggregateValidator`、日期／財務投影及唯一 lifecycle writer；不是建立可接受任意欄位的萬用 API。
- legacy／generic writer 在完成 scanner 加門禁無法修正；只要它們仍可正式寫入，就仍能產生 scanner 才發現的髒資料。
- 已確認不保留 legacy 相容轉接：入口直接移除；若短期保留 route 供舊 client 明確辨識淘汰，只能固定回 `410 Gone`，不得接受 payload、呼叫舊 writer或轉調新 Command。

##### F. 已確認的共用核心與交易 ownership

採用「命令分開、核心規則共用」：

| 層級 | Ownership | 禁止事項 |
|---|---|---|
| Router／Streamlit／React／Integration Adapter | 接收使用者意圖、顯示 Preview、送出 Apply | 不計算 status、actual end、actual hours 或 canonical schedule；不直連 DB／Service writer |
| Command-specific Application Service | actor／權限、idempotency、expected version、鎖定 fresh facts、完整 transaction、audit／outbox | 不複製 calendar／coverage／ownership／lineage 規則；不分段 commit |
| `ScheduleCandidateBuilder`／calendar calculator | 以命令意圖與權威事實建立完整候選 aggregate | 不讀寫 DB、不依賴 UI session、不接受 client 衍生結果 |
| `ScheduleAggregateValidator` | 服務量、coverage、ownership、lineage、區段、檔期、付款不可變性 | 不保存資料；不得被各 Command 複製成近似版本 |
| projection calculator | 推導 planned／actual end、actual hours、未實現薪資與帳務日期 | 不覆寫已實現交易 |
| lifecycle evaluator／Application Service | 由 typed domain facts 決定合法 status，並在 caller outer transaction 寫 history | 不讀 Alert open／resolved；其他 writer 不得直接更新 status |
| Repository | 使用 Application Service 傳入的 transaction／cursor 執行 persistence | 不自行開連線或 commit，不內藏商業判斷 |

正式 Commands 至少分為 assignment synchronization、leave-resolution batch、actual-start confirmation／correction、availability-lock conversion，以及 settlement boundary 後 correction。不同 Command 可增加專屬規則，但 Apply 都必須遵守：

```text
authorize + idempotency + expected version
→ lock and load fresh facts
→ rebuild candidate with the Preview rules
→ compare fingerprint/version
→ validate all write-time invariants
→ persist source facts + assignment/schedule
→ derive dates/hours/payroll/accounting projections
→ reevaluate lifecycle in the same outer transaction
→ audit/outbox/idempotency result
→ one commit
```

Preview 允許回傳無效候選與 blockers，但零正式寫入；Apply 不接受 client 傳回的衍生結果，必須重新計算。若 fingerprint／version 漂移就拒絕並要求重新 Preview。Domain、Repository helper 及 lifecycle dependency 均不得在 Application Service 之外自行 commit。

已確認：完成且結清後若客戶收款再發生退匯／沖正，案件服務資料鎖維持不可逆；只重新形成客戶應收、超收／退款、adjustment 或 reversal，不恢復一般服務資料覆寫。

### MAT-01 媒合溝通方案

候選階段：

```text
配對草稿
→ 發送資訊／待月嫂回覆
→ 願意或不願意
→ 全部必要月嫂願意
→ 履歷已發送
→ 客戶確認
→ 取得等待訂金鎖
```

核心規則：

- 草稿可顯示 gap／overlap，但發送前必須重新檢查最新檔期及完整覆蓋。
- 多月嫂方案需所有必要月嫂都願意，才能發送完整履歷。
- 調整組合、重新聯繫或取消方案不得刪除既有發送與回覆歷史。
- 客戶確認不直接建立正式 assignment；只進入 AVL-01 等待訂金鎖。

來源：

- [多月嫂排班 UX 目標指南](../管理端UI/多月嫂排班UX目標指南.md)
- [多月嫂排班 UX 改善討論紀錄](../管理端UI/多月嫂排班UX改善討論紀錄.md)
- [多月嫂排班 UX 驗收矩陣](../管理端UI/多月嫂排班UX驗收矩陣.md)

缺口：

- 「資訊一／資訊二／履歷」是 message event、plan state 還是兩者投影，需正式 owner。
- 月嫂改變意願、逾時未回覆及已發履歷後重配的完整轉移尚未正規化。

### AVL-01 等待訂金檔期鎖

候選生命週期：

```text
未占用
→ 客戶確認、等待訂金鎖定
→ 訂金核銷後轉正式 assignment／schedule

等待訂金鎖定
→ 回復未綁定
→ 已釋放

等待訂金鎖定
→ 取消訂單
→ 已取消並釋放
```

門禁：

- 取得鎖及轉正式前都必須重查檔期。
- 鎖必須完整且全部屬於同一案件；遺失、不完整或 ownership 不符時整筆失敗。
- 回復未綁定只允許洽談中、零訂金，且需二次確認。
- 訂金入帳後禁止走回復未綁定；取消與回復是兩個不同命令。
- 轉正式、狀態推進、assignment、schedule 與鎖轉換必須 all-or-nothing。
- 等待訂金代表雙方已簽約並確認月嫂；訂金逾期只形成帳務／催收異常，不得由排程或時間自動解除檔期鎖。合法解除只有具權限的「回復未綁定」或「取消訂單」，或訂金核銷後轉為正式 assignment。
- 服務開始前，每個 assignment 自己的預計結束日後 7 天都必須以獨立 `buffer` 鎖定事實預留，不能偽裝為正式服務日、工時或薪資。整案第一個正式服務開始時，在同一交易解除本案全部 assignment 的 buffer locks；正式 assignment 服務區間鎖仍持續有效。

### ASN-01 正式 assignment

已確認行為：

- 每一行正式人力配置對應一個 assignment。
- 同案同日只能有一個 assignment owner；不得拆分同一天。
- Preview 是純試算、不建立 DB assignment；Apply 後才建立 `planned` assignment。
- 上游條款、日期、分段、請假、代班或出勤安排變更時，不原地截短或改寫舊 assignment；Preview 先建立完整候選，Apply 在同一交易把受影響的舊 assignment 改為 `cancelled`，再依候選建立新 assignment 及其正式工作日。
- 已開始區段更換人員時，新 Preview 可把舊服務日保留在新 assignment 集合，並自更換日 `D` 起改由新 assignment 承接；不得以更新舊 assignment 結束日作為另一套修改模型。
- 代班日由新 assignment 正式承接，取消後的舊 assignment 不得再參與目前排班或薪資投影。
- `actual_hours` 一律由該新 assignment 的正式工作日數乘以訂單每日服務時數推導；`planned`、`active`、`completed` 均使用相同薪資公式，只有 `cancelled` 被排除。
- 凍結前即使服務日已發生，也只能透過受控 Preview／Apply 取消舊資料並重建，保存命令與舊資料歷史；訂單完成且相關帳務已核銷／結算後不再重建，差額走 adjustment／reversal。
- 全案服務條款變更（服務天數、每日時數、planned start、統一服務時段等）取消並重建全案所有有效 assignments；單一請假、順延或代班只重建受影響 assignment family。兩者都必須重新驗證全案日期覆蓋、ownership、工時、樓層費、檔期衝突及薪資投影守恆。
- assignment 的整個連續區間都視為該月嫂檔期占用，包含固定排休與請假日；不得把休假日當成可接另一案件。正式代班日則由代班月嫂的獨立 assignment 承接服務。

已確認 canonical 語意：

- `planned`：已 Apply，尚未到第一個 assignment-owned 正式服務日的服務開始時刻。
- `active`：已到第一個正式服務日開始時刻、尚未到最後一個正式服務日結束時刻；中間即使有休假空窗仍保持 active。
- `completed`：已到最後一個 assignment-owned 正式服務日的服務結束時刻；整張訂單仍可能服務中。
- `cancelled`：已被取消或被新 Preview 重建取代；只作有效性篩選，不參與目前排班與薪資投影。
- `replaced` 不再是新流程業務狀態；既有值僅供歷史相容，並長期自 ENUM 與 caller 移除。

### LEV-01 請假／順延／代班批次

候選工作流：

```text
UI 草稿
→ 後端 Preview
→ 使用者確認
→ Apply／已確認

Preview
→ 資料版本過期
→ stale／拒絕，要求重新 Preview
```

核心規則：

- 每一日期只有「順延」或「安排代班」兩種 outcome；請假者只保留為事件來源。
- 多日期使用一個 batch、一次 Preview、一個 fingerprint、一次 Apply transaction。
- Preview 不建立正式請假、排班、薪資或帳務資料。
- Apply 必須驗證 fingerprint、資料版本、冪等鍵及最新 availability。
- 任一日期失敗整批回滾；每一日期仍保存獨立 append-only event，並以 `batch_key` 串聯。
- 已生效請假的取消或修改也走反向／替代 Preview → Apply，不直接刪除原事件。

### CAL-01 服務日期計算

這是兩種計算模式，不是訂單生命週期：

| 模式 | 基準 | 結果 | 寫入性質 |
|---|---|---|---|
| 服務前規劃 | 預期服務開始日 | 規劃服務日與 `end_date` | 規劃投影 |
| 實際開始日後精算 | `actual_start_date` | 正式服務日與 `actual_end_date` | 正式衍生資料 |

共同規則：

- 兩種模式共用 canonical 行事曆純計算核心，但來源事實與 Application Command 分開。
- 順延日不計服務量，向後尋找下一個合法服務日。
- 代班仍完成當日服務，不因代班本身延後。
- `end_date` 與 `actual_end_date` 都是後端自動計算結果。
- 國定假日逐日決定是否休假，不預設全部休假，也不自動雙倍薪。
- assignment-owned `actual_hours` 必須全案守恆。

## 二、帳務、退款與核銷

### PAY-01 客戶付款進度

```text
unpaid ↔ partially_paid ↔ paid
```

- 由有效收款淨額與應收總額自動投影。
- 成功收款、退款、退匯、沖正或應收調整後重新計算。
- failed、pending、review 或未唯一核銷的交易不得計入。
- UI 不得直接指定，摘要可以重算，正式交易不可直接修改。
- 已確認案件完成且結清後形成的服務資料鎖不可逆；退款、退回、沖正或原收款失效都不解除服務鎖、不改變訂單完成狀態。
- 合法退款必須同時減少有效實收與淨應收。例如原應收／實收 100,000 元，合法退回 20,000 元後為淨應收／淨實收 80,000 元，仍是 `paid`，不重新產生 20,000 元應收。
- 原收款、第一次結清與退款交易全部 append-only 保存；不得把原收款金額直接改小。
- 只有原收款被銀行拒付／撤銷、但應收義務沒有減少時，才由 100,000 元應收對 80,000 元有效實收形成 20,000 元未結餘額並進入催收。
- 合法退款、收款失效、補助款退回及 correction 必須是不同 transaction／obligation type，不得只看資金流出方向推測。

### PAY-02 客戶請款階段

```text
deposit → first_payment → second_payment → completed
全部約定服務完成前 --成功取消訂單→ NULL
```

- 單筆收款可以跨越多個階段。
- 第二期應收日只在第一期首次全額實收後設定。
- 取消後不得因退款結果把 current stage 倒退至取消前階段。
- 取消前最後階段只由事件歷史查詢。
- 受控重開不得直接恢復取消前 stage；必須依目前有效應收、實收與付款條款重新推導，取消前最後階段仍只從事件歷史查詢。

### PAY-03 帳務人工覆核

候選狀態：

```text
normal → review_required → normal／resolved？
```

已知觸發包括案件不唯一、未知帳號、超收、金額差異、共享帳號、必要資料缺失等。

已確認責任：

- `review_status` 是由可追溯根事實／核銷結果推導的帳務覆核投影；根條件修正後自動回到 `normal`。
- reconciliation `pending` 保存核銷尚未成立的結果；Alert `open／claimed／resolved` 只管理人員處理進度，三者不得混為同一欄位。
- 人工 resolve Alert 不直接修改 `review_status`、正式交易或 reconciliation 結果；根條件仍存在時警示必須 reopen。

### PAY-04 訂單帳務流程

```text
active --成功取消訂單→ cancelled
```

副作用：

- `payment_stage = NULL`。
- 停止催款及後續付款階段推進。
- 依有效客戶收款決定是否建立 REF-01。
- 訂單取消事件、`orders.status = 訂單取消`、帳務 workflow cancelled、未來 assignment／schedule／buffer lock 取消、已服務事實保留、客戶應收／退款／補收及月嫂應付重算，必須由同一取消命令在單一交易原子協調；任一步失敗整筆回滾。
- 已開始服務的訂單取消時，UI 必須先開啟逐日「實際服務日期＋實際服務月嫂」確認畫面。既有日期預填 assignment owner；新增日期必須指定月嫂；有更正時原因必填。後端依確認後根事實取消／重建受影響 assignments 並重算，不接受人工輸入 `actual_hours`、應收或應付金額。
- 取消命令的必要前提是全部約定服務尚未完成。若有效正式服務日已完整履行合約服務量，取消命令必須回傳 domain blocker 並零寫入；訂單維持完成，月嫂薪資、樓層費與其他服務結算均按完整履約計算，不得套用中途取消比例。
- 已發生的收款、退款、月嫂出款及銀行核銷均不可覆寫；差額只能新增 adjustment、refund、supplemental receivable／payable 或 reversal。
- 受控重開只適用尚未產生取消相關正式退款、沖正或結算的案件；重開後重新 Preview，不恢復取消前的帳務 stage 或排班資料。

### REF-01 一般客戶解約退款

現況：系統目前沒有一般客戶退款功能。以下為目標業務規則，不代表已有 API、UI、Service、交易類型或銀行退款能力；實作前不得用負數收款、修改原交易或挪用收款失效流程替代。

範圍決策：REF-01 只保留為後續提案，不納入本次 API、Server、訂單狀態機重整；未來須另立架構節點與 CP-1。既有訂金核銷等 payment event 委派 ORD-01 仍屬本次狀態副作用收斂，但不得藉此新增退款能力。

```text
not_required
pending → partially_refunded → refunded
pending／partially_refunded → review_required
```

規則：

- 必須先成功取消訂單，退款不得反向推測取消。
- 取消時有效收款為 0：`not_required`。
- 有有效收款：建立退款義務並進入 `pending`，但不自動操作銀行退款。
- 退款淨額、失敗、退匯與沖正均由 append-only 事件重算。
- 不得與 SBR-01 客戶預付補助款退還共用狀態、交易類型或待辦。
- 未來至少需要獨立 Refund Preview／Apply、原收款 allocation、退款義務、權限、冪等、audit／outbox 與同交易淨應收／淨實收重算。

### IMP-01 銀行匯入與核銷

候選流程：

```text
raw row
→ canonical staging
→ classified
→ reconciliation pending
→ formal transaction + reconciled

duplicate fingerprint
→ new occurrence + skipped_existing

ambiguous／amount mismatch
→ pending／review + alert
```

門禁：

- 分類成功不等於核銷成功。
- 候選對象與金額必須唯一且精確。
- 重複匯入不得覆寫 canonical row、正式交易或人工處理。
- `pending/review` 不得更新已收、已退、已付或月結完成狀態。

Canonical vocabulary 不採單一巨大 enum，而拆成：

```text
batch_status:
  staged → completed | failed

occurrence_outcome:
  inserted | skipped_existing

classification:
  pending → client_receipt
          | government_subsidy
          | client_subsidy_return
          | staff_salary
          | staff_legacy_subsidy
          | non_business_review

reclassification:
  eligible non_business_review → business classification
  business classification 不得自動倒退

reconciliation_status:
  pending → reconciled

alert_status:
  open → claimed → resolved
  resolved --問題重現--> open
```

- `skipped_existing` 只描述本次 occurrence，不得寫進 canonical classification 或 reconciliation。
- `non_business_review` 是尚未分類成業務事件；已完成業務分類但核銷 pending 是另一個狀態，
  前者逐 canonical row 顯示為 `finance_import_manual_review`，後者顯示 owning Finance
  Domain 對應的 finance alert。`IMPORT-006` 只表示匯入完整性異常，不承接普通待分類。
- 正式交易退匯／沖正不得把 staging reconciliation 倒退；以 append-only domain event 表示。
- dry-run／apply 是 Command mode／outcome，不是 canonical row state。
- 成功訂金核銷造成的訂單狀態影響必須委派 ORD-01 的 Application Service；
  importer、reprocessor 或 payment writer 不得直接指定 `orders.status`。

缺口：

- 現有文件混用 pipeline step、result 與 status，需建立分層 enum。
- File Watcher 是否只建立 durable import job，或自己擁有 processing 狀態，尚未裁決。

### TXN-01 不可覆寫金流交易事件

這是跨帳務領域共同不變量，不建議做成一個共享巨大狀態欄位：

- succeeded 才增加有效淨額。
- failed 不計入淨額。
- return／退匯恢復未付或未退餘額。
- reversal 必須關聯原交易並保存原因。
- 失敗後重送建立新外部識別的新交易，保留原失敗事件。
- 原交易不得 UPDATE／DELETE；摘要由全部有效事件重算。

缺口：

- 各 Domain 是否共用相同 transaction outcome vocabulary。
- reversal-of-reversal 是否允許及如何表達。

### SBR-01 客戶預付補助款退還

目前只能列為衝突候選：

- [帳務與訂單業務規則](../資料庫、資料處理/帳務與訂單業務規則.md)記載功能停用，不得建立退款 UI、待匯清單或正式交易。
- [帳務金流規則](../資料庫、資料處理/帳務金流規則.md)則記載義務建立、待匯、實際銀行支出、部分退款與結清能力已存在。

在正式裁決啟用狀態前，不得把兩者整理成模糊的「系統支援退款」。

### SUB-01 政府補助申請／核銷

候選主鏈：

```text
待申請 → 已送件 → 已核准 → 部分撥款／已撥款 → 結清
```

門禁：

- 案件需符合補助資格、已完工且未重複納入同一批次。
- 只有唯一且金額精確的銀行撥款候選可以自動核銷。
- 申請、核定、實撥與未撥金額分開保存，不得為對帳而覆寫原金額。

缺口：

- 同季多次送件、補件版本及批次唯一鍵。
- 補件、駁回是 batch state 或獨立 review workflow。
- 一筆撥款能否跨批次。
- `actual_end_date` 有值不等於已完工，必須同時驗證 ORD-01 完成狀態。

### STF-01 服務人員應付款清單／付款

已確認流程：

```text
assignment-owned 工時／費率／樓層費／調整
→ staff_payments 應付投影
→ 依目標付款日期查詢並按 staff_id 合併同月多訂單
→ 使用者下載應付款 Excel，後端保存完全相同 bytes
→ 銀行成功出款方向淨額精確打平該月嫂本次完整應付義務
→ 明細由「應付」轉為「已完成」
```

規則與門禁：

- 業務上沒有人工「建立月結」、draft、finalized 或按鈕定稿流程；不得為現行應付款清單／匯出另建月結 Domain 或即時計算月結文件狀態機。
- 現有 `staff_monthly_settlements`／details 與相關 caller 在遷移完成前只作歷史相容，不直接刪除；新架構不得形成新的依賴。
- 每月約 5 日由人員下載當月 15 日應發薪及應退客戶補助明細交給會計，但下載日期不是狀態轉移或封存時點；4 日、5 日或其他日期下載都依當下有效資料產生各自檔案。
- 每次下載都把同一份 XLSX bytes 原子保存至 `downloads/accounts_payable_archive/YYYY/`；檔名包含目標付款日、產生日期時間及短雜湊，永不覆蓋。保存失敗時不得把未留存版本提供給使用者。
- 不建立資料庫明細快照或下載版本狀態機；XLSX 檔案本身即為當次不可變輸出。下載不表示已付款，也不改變應付款狀態。
- 同一月嫂同一付款月份的多訂單／assignments 在匯出時合併；正式銀行核銷仍須能追溯根義務。
- 會計匯出只列「應付」；核銷後餘額精確為 0 才轉「已完成」並自後續匯出排除。退匯／沖正使有效實付淨額再次不足時，重新成為應付。
- 不足額、超付、部分付款、金額不符、缺銀行主檔或非正常時序不得形成正式中間核銷或匯出分支，一律由根事實衍生異常交人員處理。
- 訂單取消或實際服務日更正後，月嫂應付款沿用原訂單既定應付日，不自動延到下一個 15 日；若原日已過或在不正常時點才形成差額，直接進入異常中心。
- `adjustment_amount` 只由有效 `financial_adjustment_staff_allocations.amount_delta_ntd` 加總投影；不得直接修改摘要。已發生出款後的更正以追加 adjustment／reversal 保留歷史。
- 客戶端與月嫂端是獨立義務，但正式核銷後兩端各自剩餘差額都必須精確為 0；任何一端未打平都不得標示完成。

## 三、警示、LINE 與外部整合

### ALT-01 系統／財務警示

候選生命週期：

```text
open → claimed → resolved
```

門禁：

- 已被其他人認領時再次認領：conflict。
- resolve 必須有處理原因。
- UI 只能查詢、認領、解除；不得自行建立警示或修改正式帳務。
- 警示處理不得覆寫原始銀行列、正式交易或排班事實。
- Alert 使用獨立 API 與本節的 `open → claimed → resolved` 工作流；這個狀態機只管理人工處理進度，不得參與 ORD-01、ASN-01、PAY-01 或其他 Domain 狀態轉移。
- Domain fact predicate 是門禁 SSOT，由各 Domain Application Service 在交易內直接執行；不得查 alert 狀態決定命令成敗。
- Alert projector 只能共用 Domain 層提供的 predicate 契約，透過 domain event／transactional outbox 或唯讀重掃建立投影；不得複製另一套業務判斷。
- Domain 交易不等待 Alert 投影成功。修正底層事實後由 projector 更新／解除；人工 resolve 不能修改事實或繞過門禁，條件仍存在時投影可重新開啟。
- API 契約必須分開回傳 `domain_blockers` typed errors 與 `alerts` display projection，Alert API 不提供強制完成或忽略門禁能力。

待裁決：

- resolved 是否必須先 claimed。
- 認領者逾時、離職或轉派的處理。
- `finance_alerts` 不可變稽核與 `system_alerts` 可滾動更新的共同介面及差異。

已確認補充：

- 修正根事實後，衍生警示由 projector 自動解除；人工 resolve 只表示處理工作流完成，不能讓仍存在的根條件消失。
- 相同根條件再次存在或人工誤關閉時，current-state 警示必須 reopen；需要不可變稽核的財務異常另以事件保存每次 occurrence。
- 異常中心是正式保護機制的一層：上游寫入先驗證根事實，異常中心持續提前偵測，下游只保留版本、冪等、併發、金額打平與原子性等最低限度防禦，不為每個可提前發現的缺漏再建立一套重複關卡。

### LNT-01 LINE 發送任務

候選操作流程：

```text
pending → processing → sent
                  ├→ pending（可重試）
                  └→ failed
pending → cancelled
failed → pending（人工重試）
stale processing → pending
```

盤點到的共同規則：

- 以 due time 及 retry time claim 任務。
- claim 需 row lock，避免多 Worker 重複取得。
- retryable error 採 backoff；超過重試上限或不可重試錯誤進 failed。
- enqueue 需要穩定 idempotency key。
- 人工取消、立即執行及重送只能從明確來源狀態進行，不能任意跳轉。

### LNR-01 Rich Menu 發布

```text
pending → processing → published
                  ├→ pending（可重試）
                  └→ failed
failed → pending（人工重試）
```

- 同一 menu configuration 不得同時有兩個 active publication。
- 只有 published 且 current 的 publication 可成為目前 Rich Menu。
- 是否需要 publication idempotency key 仍待補強。

### WHK-01 Webhook durable inbox

建議統一語意，但每個 provider 保持自己的 adapter 與去重鍵：

```text
received → processing → completed
                     ├→ retry_pending
                     ├→ failed
                     └→ ignored
```

候選共同規則：

- LINE 使用可驗證的 webhook event id。
- BreezySign、BeClass 若沒有可靠 event id，需以 provider payload 建立 canonical fingerprint。
- handler 的正式 Domain 副作用必須冪等。
- 失敗需保存 durable evidence，不能捕捉例外後仍回成功。
- 同一 request 內多 events 是否整批原子處理需明確裁決。

### LRV-01 LINE 人工確認申請

```text
pending → approved
        ├→ rejected
        └→ cancelled
```

- approve／reject 只允許 pending。
- 拒絕需保存原因。
- 新申請取代、解除綁定或其他取消情境使用 cancelled，不能冒充 rejected。
- 決策及其 LINE 通知任務需同交易，通知使用穩定 idempotency key。

### LUS-01 LINE 使用者好友狀態

```text
unknown → active ↔ blocked
```

- follow／unblock 進 active；unfollow 進 blocked。
- active 可觸發 onboarding。
- blocked 取消尚未執行的 onboarding 任務。
- 不得與 LNT-01 發送任務或 LRV-01 人工審核混成同一 machine。

### ING-01 匯入結果與 durable import job

現有 importer outcome：

```text
inserted | skipped_existing | review_required
```

缺少的 job workflow：

```text
detected → queued → processing → completed
                            ├→ retry_pending
                            └→ failed／review_required
```

File Watcher 應只負責偵測並建立 durable job，或明確成為 job owner；不能維持目前只有記憶體 cooldown、同步 subprocess 與無持久 retry 的模糊責任。

### DAN-01 資料異常隔離

舊文件提出：

```text
pending → resolved | ignored
```

但 owner 分散在 Pipeline、LINE、管理 UI，且資料表／新警示架構存在漂移。整理時標為 `historical/proposal`，不得宣稱為現行正式機制；需先決定是否被 PAY-03／ALT-01 取代。

### CTR-01 BreezySign 合約簽署

外部狀態候選：

```text
pending_signature → completed／signed
```

目前必須標為架構衝突：

- 舊流程在完成 webhook 中自行填入實際開始日。
- 直接更新訂單成立。
- 刪除並重建舊排班。
- 缺少可靠 webhook 去重及 durable failed inbox。

正式整合的建議邊界：

- Adapter 只驗證、正規化並保存外部合約事件。
- 合約 aggregate 更新後發出內部 event。
- 是否建立鎖、成立訂單或產生排班，交由 ORD-01、AVL-01、ASN-01 的正式 Command 決定。

### NTF-01 動態通知排程

通知本身委派 LNT-01，不建立另一套 `pending/sent/failed`：

- 業務事件只負責 enqueue。
- 日期更正時，以 business key 取消舊 pending 並冪等建立新任務。
- 已 sent 通知不得覆寫；必要時追加更正通知。

缺口：

- 請假日是否跳過每日服務通知。
- audience snapshot 與 template version 的固定時點。
- 舊「尾款入帳等於訂單結案」規則與 ORD-01 衝突，應標歷史。

## 四、非領域狀態機

以下不得因整理而升格為 Domain state：

- HTTP `200／400／409／500`。
- API 回應中的 `status: success`。
- 行事曆紅／黃／綠／白顏色。
- Streamlit tab、月份切換或 dialog 開關。
- Docker container 單純的 running／healthy。

Calendar UI 可以保留 viewing、unsaved draft、previewing、applying、stale、error、success 等暫時互動狀態，但它們不能成為正式服務事實。

部署啟動可另外建立 operational workflow：

```text
starting → ready → degraded → stopped
```

但在全地端與雲端混合方案尚未裁決、也沒有完整 readiness／restart／alert 契約前，只列為 DEP-01 候選。

## 六、待裁決與暫緩清單

已完成裁決：

- assignment canonical enum 為 `planned／active／completed／cancelled`，切換時刻由 assignment-owned 正式服務日及案件統一服務時段推導；`replaced` 僅歷史相容。
- `review_status`、reconciliation pending 與 Alert workflow 分離；Alert 只管理人工處理進度，不能取代 Domain facts 或核銷結果。
- 不建立服務人員月結 canonical states；維持應付款清單／Excel 匯出，舊月結表只作相容。
- BreezySign／契約是獨立流程；簽署、重發、webhook 延遲或失敗不得越權改寫已確認 Orders Terms、assignments 或財務投影。
- 全部約定服務完成後不得取消訂單；即使服務資料鎖尚未成立也維持 `訂單完成`，月嫂薪資及服務結算按完整履約計算。
- 客戶預付補助款退還功能目前啟用，應付款清單可包含退補助給客戶的明細；舊「功能停用」記載標為 superseded。
