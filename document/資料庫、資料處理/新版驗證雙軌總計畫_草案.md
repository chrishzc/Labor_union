# 新版驗證雙軌總計畫（草案）

## 1. 文件狀態與目標

- 狀態：`proposal-for-human-review`
- 目標：同時規劃業務測試資料驗證與 Infrastructure／Runtime／Benchmark 驗證，先固定責任邊界、測試方法、證據與完成條件。
- 本文件不授權建立資料庫、執行 migration、修改環境設定、啟動外部副作用或建立正式測試程式。
- Schema 共同基線：`db/releases/labor_union_validation_schema_v1.sql`。
- A 軌規則來源：`document/資料庫、資料處理/新版測試資料規則矩陣_草案.md`。

## 2. 雙軌責任

| 驗證軌 | 負責問題 | 主要輸入 | 不負責 |
|---|---|---|---|
| A：Business Data Validation | 系統對正確／錯誤業務根事實是否產生正確event、projection、state、Alert、API與UI | `DOMAIN_ROOT_DATA`、`EXTERNAL_INPUT_FIXTURE`、fixed clock、expected manifest | process health、真實網路、TLS、filesystem容量、部署與效能證據 |
| B：Infrastructure／Runtime／Benchmark | 系統在檔案、程序、網路、DB、cache、queue、provider、release與故障條件下是否安全運作 | metadata/filesystem fixture、disposable DB、fake/sandbox adapter、process/network harness、benchmark dataset | 決定業務金額、狀態、資格或用Infrastructure結果取代Domain oracle |

兩軌都必須做，但完成狀態分開。A 軌通過不能證明部署可靠；B 軌通過也不能證明帳務、排班或補助計算正確。

## 3. 驗證素材分類

| `test_kind` | 所屬軌 | 例子 | 建立位置／方式 |
|---|---|---|---|
| `domain_root_data` | A | 訂單Terms、assignment、正式服務日、銀行root、obligation | 新 `lu_test_*`，透過importer／typed Command建立 |
| `external_input_fixture` | A | HCM/BeClass/銀行XLSX、webhook JSON、知識文件、media | 去識別化版本化fixture，送入正式入口 |
| `expected_manifest` | A | 金額、日期、狀態、row delta、Alert、API/UI答案 | 獨立YAML/JSON；不得呼叫production calculator產生答案 |
| `metadata_fixture` | B | release manifest、entry queue、config before/after bytes | temp workspace與versioned test assets |
| `filesystem_artifact` | B | backup、XLSX、archive、digest、restore evidence | temp目錄／sandbox object-store adapter |
| `process_network_harness` | B | API/worker、queue、Redis、MySQL、TLS、provider fault | 隔離process/container、fake clock、fault injection |
| `benchmark_evidence` | B | UI/API/DB latency、query count、EXPLAIN、payload bytes | 固定環境與固定A軌dataset的可重跑彙總 |
| `manual_environment_acceptance` | B | target host、edge、restore drill、實際容量 | 人工／部署者驗收receipt，不由pytest或seed script冒充 |

## 4. 共用邊界與不變量

1. A、B 軌只可使用獨立 `lu_test_*` 或工具建立的 temporary target；不得修改正式庫或舊候選庫。
2. A 軌的 expected business answer 是唯一業務oracle；B 軌故障注入不得改寫答案。
3. B 軌可以重用A軌dataset作為load，但dataset筆數不是效能通過證據，必須另保存量測環境與結果。
4. Query、Preview與render在兩軌都必須zero business mutation。
5. timeout、worker crash、cache miss或provider failure不得偽造Domain成功、重複event或改變Money/State答案。
6. 所有scenario使用穩定ID、reference clock、release/schema identity與correlation identity。
7. 兩軌各自輸出receipt；整體release gate只匯總結果，不合併或覆寫原始證據。
8. 敏感資料不得出現在fixture、log、receipt、benchmark或failure snapshot。

## 5. A軌：Business Data Validation

### 5.1 測試流程

```text
完整Schema建立於新lu_test_*
→ importer／typed Command建立ROOT
→ Preview（驗零寫入）
→ Apply（events／ledger／allocation／receipt／outbox）
→ projector／reducer／Query
→ API typed ViewModel
→ UI狀態、內容、導航與人工動作
→ 與獨立EXPECTED manifest逐層比對
```

### 5.2 A軌測試層級

| 層級 | 測試方法 | 主要答案 |
|---|---|---|
| Module | 純函式vector、固定clock、邊界與非法輸入 | 公式、日期、identity、fingerprint、typed error |
| Subsystem | 真實MySQL或repository contract、Preview/Apply、replay、rollback | row delta、event、projection、version、receipt/outbox |
| Domain | 從roots到Domain Query完整流程 | state machine、balance、hours、status、anomaly facts |
| Global Dataflow | 跨Domain outer UoW與borrowed port | one commit、partial failure全rollback、跨域守恆 |
| API | typed request/response/error、masking、pagination | payload schema、HTTP、correlation、zero hidden mutation |
| UI | 使用API結果驅動畫面與操作 | success/empty/warning/error/stale、顯示內容、修正後消失 |

### 5.3 A軌負責的功能

- Orders、Assignments/Scheduling、Payroll、Client Finance、Staff Payables、Government Subsidy。
- Finance Import 與 Case Import 的來源內容、canonical data、classification與正式dispatch。
- Anomalies 的異常根因、顯示、claim、owning Domain修正、auto-resolve與reopen。
- LINE identity/inbox/task狀態、Access Control資料、Security Audit資料、Knowledge來源／citation。
- Accounts Payable Export的資料列、聚合、排除、remaining與source trace。

### 5.4 A軌完成證據

每個scenario至少輸出：

- root fixture digest；
- expected manifest digest；
- source/event/projection/outbox/receipt row delta；
- state transition history；
- API expected/actual typed payload；
- UI expected state與操作結果；
- replay、stale、rollback、repair、auto-resolve結果；
- 規格來源與人工裁決identity。

## 6. B軌：Infrastructure／Runtime／Benchmark

### 6.1 B軌子矩陣

| ID範圍 | Subsystem | 測試方式 | 核心標準答案 |
|---|---|---|---|
| `MIG-01..10` | Preserve-data Migration／Cutover | disposable source/candidate DB、manifest/config fixture、DDL crash injection | source唯讀、candidate新建、journal可恢復、drift fail closed、switch/recovery receipt |
| `BKR-01..05` | Backup／Restore／Recovery | temp backup artifact、digest corruption、全新recovery candidate、restore drill | digest/tool/identity一致；不原地覆寫；failure→escalated |
| `REL-01..08` | Release Orchestration | manifest＋approval fixture、state-machine runner、switch/restart fault | 禁止跳階；approval scope/expiry/digest正確；failed/recovery狀態正確 |
| `DEP-01..07` | Deployment Security／Topology | container/network policy、principal、secret scanner、component health | DB不公開、權限分離、secret不外洩、partial component不冒充released |
| `OBS-01..09` | Runtime Supervision／Observability | fake metrics/clock、process fault、queue/DB adapter、log capture | readiness/heartbeat/lag/dead-letter正確，log有correlation且遮罩敏感值 |
| `PERF-01..08` | Performance／UX | browser/API/DB benchmark、query counter、EXPLAIN、payload capture | UI state及single-flight正確；bounded payload；record-only budget不改業務結果 |
| `CACHE-01..07` | Cache | fake/in-process/Redis adapter、invalidation與failure injection | hit/miss/fallback答案相同；key含actor/version；Apply永遠fresh-read |
| `JOB-01..07` | Durable Job／202 | queue harness、duplicate delivery、worker crash、cancel/notification loss | succeeded連正式receipt；failed typed；at-least-once不重複正式命令 |
| `EXT-01..06` | External Side Effects | provider sandbox/fake、timeout/4xx/5xx/ack crash | commit後才呼叫；retry bounded；已成功副作用不重複或進人工review |
| `ENTRY-01..07` | Entry Point Governance | static discovery queue/validator、endpoint regression | active/410/operator-only/removed metadata與實際entry一致 |
| `LEGACY-01..04` | Legacy Writer Retirement | writer scan、HTTP/CLI/UI regression、DB permission | legacy writer不可達；HTTP typed 410；canonical writer唯一 |
| `ARC-01..05` | Archive／Retention／Capacity | temp filesystem/object-store、hash/capacity/failure injection | atomic publish、immutable path、digest一致、failure不宣稱完成 |
| `GERR-01..05` | Typed Error／Timeout | API/repository fault injection | error envelope完整；只有unavailable同key retry；timeout查receipt不重送 |

### 6.2 B軌測試層級

| 層級 | 例子 | 是否使用A軌資料 |
|---|---|---|
| Static contract | manifest、entry queue、secret scan、legacy writer scan | 否 |
| Adapter contract | filesystem、cache、queue、provider、backup tool | 可用identity，不需業務內容 |
| Disposable integration | MySQL candidate、API/worker、restore、restart | 可重用最小A軌smoke dataset |
| Fault injection | deadlock、timeout、disk full、worker crash、provider 5xx | 可重用A軌command，但驗的是failure semantics |
| Benchmark | browser/API/DB/cache/job | 使用固定A軌dataset作load，另存環境與量測證據 |
| Manual environment | edge、VPN、TLS、target host、restore rehearsal | 不由A軌資料決定 |

### 6.3 B軌完成證據

- manifest/config/artifact before/after digest；
- process、adapter與environment identity；
- fault injection point與expected state；
- journal／job／release／recovery receipt；
- health/metrics/log redaction snapshot；
- benchmark dataset digest、環境、warmup、樣本、aggregate；
- filesystem/provider/restore evidence；
- 明確標示自動測試或人工環境驗收。

## 7. 混合型功能拆分

| 功能 | A軌：資料與業務答案 | B軌：非資料可靠性 |
|---|---|---|
| Accounts Payable Export | 哪些staff/refund/subsidy-return列應輸出、金額、聚合、排除、source IDs | XLSX bytes、SHA-256、filename、atomic archive、capacity、下載一致性 |
| Finance Import | 來源欄位、normalization、fingerprint、occurrence、classification、ledger/allocation | File Watcher、檔案權限、大檔、process crash、外部路徑、吞吐量 |
| Anomalies | trigger roots、fingerprint、Alert、UI、repair、auto-resolve/reopen | projector heartbeat、lag、dead-letter、worker crash/recovery |
| LINE | identity、inbox、task、review、publication state | signature入口、provider sandbox、TLS、timeout、retry/ack crash |
| Knowledge | source、version、review、published、citation、answer non-authoritative | crawler網路、archive/index service failure、容量與效能 |
| Access Control | user/session/capability/audit資料與授權答案 | secret store、production bypass防護、edge/VPN與process config |
| Migration smoke | A軌提供最小read-only業務dataset與API expected | B軌執行backup/candidate/switch/restart並比對smoke |
| Performance | A軌提供固定dataset digest | B軌保存browser/API/DB量測，不能反寫或改動A軌oracle |

混合功能只有A、B兩張receipt都通過，才可在整體系統矩陣標記完成。

## 8. 執行順序

1. 人工確認本雙軌界線與A軌測試資料矩陣。
2. 補齊A軌缺少的Domain scenarios與expected manifest contract。
3. 在不建立資料庫的前提下，建立B軌scenario manifest與harness contract。
4. 人工確認兩軌的write set、external side effects與驗收條件。
5. 建立全新 `lu_test_*`，套用完整Schema並執行A軌fixture。
6. 完成A軌Module→Subsystem→Domain→Global Dataflow→API/UI驗證。
7. 以A軌固定dataset作為B軌需要的smoke/load input，執行static、adapter、integration與fault tests。
8. 最後執行benchmark與需要實際環境的人工驗收。
9. 匯總兩軌receipt；任一軌未完成，不宣稱完整系統驗證通過。

## 9. 分開的完成Gate

### A軌 Gate

- 所有正式Domain的ROOT、狀態機、計算、Query、異常與修正閉環有scenario。
- 衍生資料不直接seed；expected oracle獨立於production calculator。
- API/UI與DB row delta一致；重播、stale、rollback與repair通過。
- 14個缺typed recovery action的異常保持明確GAP，未補前不宣稱閉環完成。

### B軌 Gate

- Migration、Backup、Release、Deployment、Runtime、Performance等scenario具有相符test_kind。
- 自動化與人工環境驗收清楚分開。
- fault、restart、timeout、duplicate delivery、disk/provider failure不破壞Domain不變量。
- 任何secret/PII不出現在log、receipt或artifact。

### 整體 Gate

- A軌通過＋B軌通過＋混合功能雙receipt通過。
- Schema/release/dataset/harness/evidence digest均可追溯。
- 未完成或人工待決項明確列為GAP，不以mock、seed row或人工resolve冒充完成。
