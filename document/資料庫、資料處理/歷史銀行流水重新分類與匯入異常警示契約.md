## 1. 目標與問題邊界

本輪要修復既有歷史銀行流水已成功寫入 staging，卻因欄位投影錯誤全部落入
`non_business_review` 的問題，並提供安全、可稽核、可先 dry-run 的既有批次重處理能力。

同時，所有仍無法分類成業務事件的銀行流水，必須按匯入批次彙總顯示於：

`異常警示中心 → 資料匯入異常`

本輪不刪除或重建資料庫、不刪除 canonical row／occurrence／正式交易、不以姓名、
部分帳號、同額或 Excel 列號猜測身分，也不修正會改變既有 fingerprint 的 adapter 原始欄位。

## 2. 已確認根因

1. 歷史格式已把第 10 欄「銷帳編號」保存於 canonical `cancellation_code`。
2. 分類器只讀 `bank_references["銷帳編號"]`，因此歷史格式即使有合法虛擬帳號仍被誤判。
3. 客戶入款核銷服務也只讀 `bank_references["銷帳編號"]`，且只允許 `sinopac`；
   因此只修分類器仍不會成功寫入正式帳務。
4. 既有 Sinopac adapter 的 `cancellation_code` 語意與歷史格式不同，而 fingerprint 已包含
   此欄。直接修 adapter 會讓舊檔重匯產生新 fingerprint，可能建立重複 canonical row。
5. `system_alerts` 是目前狀態的可變投影，不是帳務稽核軌跡；重分類必須另有 append-only audit。

## 3. 銷帳編號唯一投影規則

新增共用 `FinanceCancellationCodeProjection`，分類與客戶入款核銷必須共同使用：

- `legacy`：只讀 canonical `cancellation_code`。
- `sinopac`：先讀 canonical `cancellation_code`；僅當其缺失或不符合完整格式時，
  才精確 fallback 至 `bank_references["銷帳編號"]`。
- 合法值固定為 `99781699` 加六碼數字，共 14 碼。
- fallback 只維持既有 Sinopac 資料相容性，不寫回 canonical raw fields。
- 不得從姓名、備註、更正註記、第 12 欄比對欄位、部分帳號或金額推測銷帳編號。
- 本輪不修改 adapter 與 fingerprint；canonical-only 的 Sinopac 修正必須另案設計 fingerprint migration。

## 3.1 未來目標架構對齊

本功能必須遵守《可替換前端與 Streamlit 薄顯示層重整計畫》的依賴方向：

```text
Streamlit／React Presentation Adapter
  → framework-neutral Alert Center Contract
  → Alert Center API Client
  → FastAPI Router
  → Application Service
  → Domain Service／Repository
```

- `ui/pages/06_finance_alerts.py` 只保存畫面與暫時 UI state，不得解析 system alert 的 DB row、
  `details` JSON 或自行決定 alert lifecycle。
- Query、Command、ViewModel 與 Typed Error 必須由 framework-neutral contract 定義；
  Streamlit 與未來 React 共用相同 OpenAPI 語意。
- Streamlit 不得散落 `requests.*`、URL、headers、timeout 或 response envelope parsing；
  必須透過無 Streamlit dependency 的集中 API Client。
- Router 不得直接回傳 DB model；必須映射為穩定 ViewModel，並明確區分 validation、
  authorization、not-found、conflict、unavailable 與 internal error。
- 一般頁面 Query 永遠唯讀；只有明確 scan Command 可刷新物化警示。

人工匯入與重處理 CLI 是管理端 application adapter，不是商業邏輯擁有者：

```text
Import／Reprocess CLI
  → Finance Import Application Service
  → Domain Service／Repository
```

CLI 只負責參數、檔案存在性、短摘要與 exit code；normalization、transaction、classification、
dispatch、audit、alert projection 與 rollback 必須位於 Application Service。

## 3.2 IMP-01 正交狀態契約

銀行匯入不是一個把所有字串混在一起的巨大狀態機，必須拆成五個正交軸：

1. Batch lifecycle：`staged → completed | failed`。
2. Occurrence outcome：`inserted | skipped_existing`；只描述本次來源出現，不是 canonical row 狀態。
3. Classification：
   - 初始 `pending`；
   - 完成後為一個明確 business classification，或 `non_business_review`；
   - 本輪唯一允許的重分類是 eligible `non_business_review → business classification`；
   - 已是 business classification 不得自動倒退。
4. Reconciliation：`pending → reconciled`，不得倒退；正式退匯／沖正由 append-only domain
   transaction event 表示，不把 staging 改回 pending。
5. Alert lifecycle：`open → claimed → resolved`，問題重現可 reopen；不等於 classification
   或 reconciliation 狀態。

`review` 必須使用明確的 `non_business_review` 或 domain-specific review state；
`skipped_existing` 不得寫進 classification/reconciliation 欄位。所有 Service、API ViewModel、
manifest 與測試必須按上述軸分欄回傳。

## 4. 既有批次重處理

### 4.1 選取資格

- 呼叫端必須明確提供一個已完成的 `batch_id`。
- 批次成員以 `finance_import_occurrences.batch_id` 為準，對 canonical row id 去重。
- 只處理同時符合：
  - `classification_type = 'non_business_review'`
  - `reconciliation_status = 'pending'`
- 已是業務分類或已核銷的列不得倒退、重分類或重放。
- 以 row id 升冪鎖定，鎖後再次檢查資格。

### 4.2 重建、分類與 dispatch

- 從 canonical columns 重建 validator-compatible row；JSON 必須 strict decode。
- identity maps 每次 run 只載入一次。
- before／after 分類 tuple 完全相同時不 UPDATE、不寫 audit event、不 dispatch。
- tuple 改變時，才更新 classification-derived columns 與 `classified_at`，並寫 append-only event。
- 只有 `non_business_review → business classification` 才進入共用 dispatch。
- 原始匯入與重處理必須共用同一 `FinanceImportDispatchService`，不得複製第二套判斷。
- downstream 回 pending 時可保留新的業務分類，但不得建立不完整正式交易。
- pending 的正式帳務異常走既有 `finance_alerts`；仍無法業務分類者走 `IMPORT-006`。

### 4.2 訂單狀態機副作用

成功核銷訂金會影響訂單生命週期，因此不能沿用目前由
`ClientPaymentWriteService` 直接執行 `UPDATE orders SET status='訂單成立'` 的作法。

- 成功收款交易與 client payment 摘要完成後，必須在同一 transaction 將
  `deposit_reconciled` 事件交給 `OrderLifecycleApplicationService`。
- Application Service 依《可替換前端與 Streamlit 薄顯示層重整計畫》及
  `ORD-01` 規則讀取權威事實，再決定維持「洽談中」、進入「訂單成立」或其他合法狀態。
- `actual_start_date` 已到但訂金延遲核銷時，不得直接推進為「服務中」；
  必須建立／保留「等待重新確認真正開始日」異常。
- 查詢、UI render、alert list 或重開頁面不得觸發訂單狀態轉移。
- `ClientPaymentWriteService`、finance importer 與 reprocessor 不得自行指定目標訂單狀態。
- Order lifecycle transition、status history、payment transaction、reconciliation 與 deterministic
  Alert outbox intent 必須位於同一 outer transaction；任一 domain 寫入失敗全部 rollback。
- `system_alerts` 是可重建的提醒投影，由可重試 projector 在 domain commit 後消費 outbox；
  Alert API／DB 暫時失敗不得回滾或否定已提交的正式金流與 lifecycle event。

### 4.3 交易與冪等

- dry-run 與 apply 執行相同的分類、UPDATE、audit、dispatch 與警示投影路徑。
- dry-run 最後必須 rollback，任何 staging、audit、正式帳務與警示都不得持久化。
- apply 全批單一 commit；任一例外全批 rollback。
- dry-run 產生 `plan_fingerprint`，綁定 DB identity、batch、classifier version、排序 row ids
  與 before／after tuple。
- apply 必須提供同 DB、同 batch 的 `plan_fingerprint`；重新計算不同時在 dispatch 前停止。
- 正式交易繼續使用既有 `fp:<dedup_fingerprint>` external reference 防重。
- 相同完成 plan 重跑回 existing；不得重複 audit event 或正式交易。

## 5. Append-only 稽核 Schema

新增 `finance_import_reprocess_runs`：

- batch、actor、classifier version、plan fingerprint。
- selected／changed／dispatch／reconciled／pending counts。
- request/result summary JSON、開始與完成時間。
- 同 batch 與 plan fingerprint 唯一。

新增 `finance_import_reclassification_events`：

- run、canonical row、actor。
- before／after classification type、reason、matched ids、resolved account。
- dispatch result、reason、formal references。
- 每個 run 與 row 唯一。
- 禁止 UPDATE／DELETE；不得用 `system_alerts` 取代此稽核紀錄。

Migration 必須 additive、可重跑，不回填、不修改或刪除現有 staging、occurrence 或正式帳務。

## 6. `IMPORT-006` 匯入異常投影

- 代碼：`IMPORT-006`
- 名稱：`銀行對帳匯入待人工分類`
- 儲存：`system_alerts`
- `source_domain = "IMPORT"`
- `case_key = "finance-import-batch:<batch_id>"`
- 每個 batch 最多一筆，不為每一列建立警示。

Details 只保存物化摘要：

- batch id、格式、來源檔、批次狀態與時間。
- occurrence count、distinct canonical count。
- `non_business_review` 總數、pending eligible 數、非 pending 不一致數。
- direction 與 classification reason counts。
- 最多 20 個 sample row ids。
- 最近一次 reprocess run id／時間。
- 不保存姓名、完整帳號或整列 raw payload。

Lifecycle：

- 剩餘數大於零：create/update；已 resolved 而問題重現時 reopen。
- claimed 狀態更新 details 時保留認領資訊。
- 剩餘數為零：open 或 claimed 都自動 resolve，保留原認領資訊並記錄系統解除原因。
- 人工解除但問題仍存在時，下次 import、reprocess 或 scan 必須 reopen。
- 初次正式 import 在 batch completion 後、commit 前投影。
- import dry-run 走同一路徑但 rollback。
- historical scan 只 materialize alerts，不重分類、不 dispatch。
- 一般 UI/API 只讀已物化 `system_alerts`，不得在每次頁面載入時掃描數千列。
- Router 必須回傳 batch import review ViewModel；UI 不得自行解析 `details` JSON、
  拼 reason counts 或從 system alert DB 欄位推導顯示狀態。

## 7. CLI 契約

入口：`scripts/imports/reprocess_finance_import_batch.py`

- 必填 `--batch-id <positive-int>`。
- 預設 dry-run。
- apply 必須同時提供 `--apply`、`--actor <nonblank>`、
  `--plan-fingerprint <dry-run hash>`。
- 不提供 `--all`、delete、truncate、force-reconcile 或姓名匹配參數。
- stdout 只顯示短摘要；逐列明細只在指定 `--report-path` 時寫入 UTF-8 JSON。
- 短摘要包含 DB server/database、batch metadata、before/after reason counts、
  selected/unchanged/changed、dispatch/reconciled/pending、alert action、
  elapsed time、rows/sec、plan fingerprint 與 transaction outcome。
- dry-run 的 run/event ids 不得宣稱為可持久查詢識別。

## 8. 效能與鎖定

- 以 occurrence 的 batch index 取得 distinct canonical ids。
- bulk fetch canonical rows，identity maps 每 run 只載入一次。
- row id 固定排序鎖定，降低 deadlock。
- 只 UPDATE changed rows，只 dispatch newly eligible rows。
- `IMPORT-006` 使用 aggregate SQL 一次重算，不逐列 upsert。
- 預設 safety ceiling 為 5,000 distinct rows；超過停止並要求明確提高。
- 重處理是人工一次性 CLI，不放進一般頁面 request path。

## 11. 遷移、回復與停止條件

執行順序：

1. 套用 additive audit schema 並驗證可重跑與 FK。
2. 執行 historical alert backfill，只投影不重分類。
3. 對目標 batch dry-run，保存 summary、report 與 plan fingerprint。
4. 人工核對後，以相同 fingerprint apply。
5. 驗證 staging／occurrence cardinality不變、event count 等於 changed count、
   正式交易可追溯 canonical row、警示摘要正確。

正式帳務建立後若發現錯誤，只能使用既有 domain reversal；不得 DELETE 正式交易、
canonical row、occurrence、run 或 event。功能回退時 additive audit tables 仍保留。

本機 Schema Update 的回復以 v4 switch receipt 將 `DB_DATABASE` 指回
`union_db`，再重新啟動 API／UI；原始庫與候選庫都不得刪除。receipt 不得包含
`.env` 原始內容或 API key。切換前備份為 560,301 bytes，SHA-256
`b234f1a254560a0376f82ecf734bdc2bec838ad8553185e6f0e4173204445c23`。

以下任一情況必須停止：

- classifier 與 client receipt reconciliation 未共用銷帳編號投影。
- Finance import orchestration 仍放在 CLI script，或 Streamlit 直接呼叫 Service／DB。
- Finance Alert Center 尚未具備 framework-neutral Contract 與集中 API Client。
- 成功訂金核銷仍由 ClientPaymentWriteService／importer 直接寫入 orders.status，
  未委派 OrderLifecycleApplicationService。
- 嘗試直接修 Sinopac canonical 欄位卻沒有 fingerprint compatibility migration。
- apply 未先取得同 DB、同 batch 的 dry-run fingerprint。
- audit migration 尚未套用。
- eligible row 已存在正式交易但 reconciliation 仍為 pending。
- JSON 無法 strict decode、fingerprint 不合法或 batch 非 completed。
- 方案包含姓名、部分帳號、金額或 Excel 列號推測身分。
- 驗收預期宣稱 279 筆必定全部正式入帳。
