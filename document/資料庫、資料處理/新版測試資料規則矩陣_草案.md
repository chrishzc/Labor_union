# 新版測試資料規則矩陣（草案）

## 1. 文件狀態

- 狀態：`proposal-for-human-review`
- 用途：定義新版驗證資料庫的測試資料生成邊界、標準答案與除錯定位。
- 範圍：只負責業務根事實與外部輸入 fixture；Migration、Deployment、Runtime、Network、Filesystem、Benchmark 另由專屬驗證矩陣負責。
- 雙軌總計畫：`document/資料庫、資料處理/新版驗證雙軌總計畫_草案.md`。
- 本文件尚未成為正式 SSOT；人工確認後才可據此實作 fixture、seed script 或資料庫寫入。
- 權威順序：人工最新裁決 → `架構重整/01_規格基線/15`～`19` → 各 Domain 正式規格 → 欄位血緣與歷史案例。
- `schema`、production code 與舊 fixture 只能證明現況，不能推翻正式業務規格。
- 2026-08-10 人工裁決：客戶退款正常流程預設一次清償；`partially_refunded` 只保留給人員實際匯少款項後的補救流程，不是正常付款策略。

## 2. 第一原則：生成輸入，不生成系統應算出的答案

測試資料分成五類：

| 類別 | 定義 | 寫入方式 |
|---|---|---|
| `ROOT` | 人員、外部來源或正式命令提供的根事實 | 透過 owning Domain 的 importer／Command／Repository fixture 建立 |
| `EVENT` | Apply 成功後形成的不可變正式事件 | 優先透過正式 Application workflow 產生；只有 repository migration test 可直接 fixture |
| `EXPECTED_EVENT` | Apply 後應產生的 immutable event／ledger／allocation／receipt／outbox | 不預先播種；驗證事件內容與 row delta |
| `EXPECTED` | 可由根事實唯一算出的 projection／Query／XLSX 標準答案 | 不寫入資料庫；保存在獨立 oracle／expected manifest |
| `EXPECTED_ABSENCE` | 在拒絕、衝突或 rollback 情境中絕對不應出現的資料 | 驗證 row count 為 0 或保持不變 |
| `PROJECTION` | status、balance、hours、alert、read model 等衍生結果 | 不直接播種；執行 projector／Query 後與 `EXPECTED` 比對 |
| `INVALID` | 故意違反格式、狀態或不變量的輸入 | 只送到預期拒絕它的入口；不得繞過入口污染正常 fixture |
| `ASYNC_OBSERVATION` | Alert、cache、projector、通知等 post-commit 結果 | 與核心交易分開等待與驗證；不得倒過來決定核心交易成功 |
| `COMPATIBILITY_ONLY` | 為舊 caller 保留的表或欄位 | 可驗唯讀相容性，但禁止生成或作為新規則計算來源 |

標準 dataflow：

```text
ROOT／外部來源
→ typed Preview（零寫入）
→ typed Apply（fresh-read、版本、不變量、outer Unit of Work）
→ immutable EVENT／ledger／allocation／receipt／outbox
→ projector／reducer／Query
→ PROJECTION／API ViewModel／UI
                ↕
       獨立 EXPECTED oracle 比對
```

若測試直接寫入 `status`、總額、餘額、警示或 read model，再用同一欄位驗證，就只是在驗證「資料能被讀回」，無法證明系統計算正確。

## 3. 全域生成與驗證規則

| 規則 | 要求 |
|---|---|
| 固定時間 | 每個資料集宣告 `reference_time`、IANA timezone；日期標準答案只使用注入的 `BusinessClock` |
| 固定識別 | case、staff、bank row、event、command、correlation、idempotency key 使用穩定且可讀的 fixture identity |
| 整數金額 | 正常金額一律為整數 `MoneyNTD`；小數輸入是異常案例，不可在 fixture 中預先四捨五入 |
| 可重播 | 相同 seed 與相同 reference time 必須產生相同 ROOT 與 EXPECTED；重跑不得複製正式事件 |
| 領域所有權 | 每筆根事實只由 owning Domain 建立；跨 Domain 只以 committed event／outbox／typed port 傳遞 |
| 零 hidden commit | 跨域情境由唯一 outer Unit of Work Apply；任一 persistence failure 不得留下部分事件或 projection |
| Preview 純度 | Preview 前後資料庫內容完全相同；Preview 結果可作 Apply 前標準答案但 Apply 必須 fresh-read |
| Query 純度 | Query、XLSX export、UI render 不得建立或修正根事實 |
| 敏感資料 | 姓名、電話、身分證、銀行帳號、LINE ID 使用合成值；不得複製真實附件中的個資 |
| 新舊隔離 | 新資料集只允許 `lu_test_*`；不讀取舊候選庫作真實來源，不覆寫正式或人工資料 |

### 4.1 必須獨立計算的精確 Oracle

| 主題 | 標準答案 |
|---|---|
| Assignment hours | `effective assignment-owned official workday count × service_hours_per_day`；cancelled generation 完全排除 |
| Order actual end | 全案有效 assignment-owned 正式工作日的最大日期 |
| Payroll rate | 一般市民 300、補助市民 350、非市民 320；低收入戶／中低收入戶保存原值但映射至補助政策 |
| Payroll service salary | `(actual_hours + explicit_double_pay_hours) × frozen hourly_rate`；國定假日不自動等於雙薪 |
| Payroll payable | `service_salary + allocated_floor_fee + effective_adjustments`，所有正常結果皆為整數 |
| Floor fee allocation | 先按全案 `ROUND_HALF_UP`，再以最大餘數法依 assignment 正式服務日分配；各 assignment 加總必須等於全案值 |
| Staff due date | client payable `> 0`：結案後次一曆月 15 日；client payable `= 0` 且符合全補助條件：結案後第二曆月 15 日；原日期形成後不因晚到更正自動順延 |
| Client receipt Apply | 每筆 selected bank row 100% allocation，且 selected receivable obligations 同次 Apply 精確歸零；否則正式 ledger／allocation row delta 全為 0 |
| Client refund progress | `remaining = effective refund obligation − valid refund payouts + valid returns/reversals`；正常一次精確清償，`partially_refunded` 僅處理實際匯少後的補救，付款進度與 review 狀態正交 |
| Staff net paid | `valid payout − return − reversal`；只有精確結清才 `completed`，partial／overpaid／ownership mismatch 為 anomaly |
| Subsidy item requested | `approved/claimed official hours × frozen unit price`；requested、approved、net allocated、outstanding 都由 item/event reducer 加總 |
| Subsidy outstanding | `approved total − valid receipt allocations + valid reversal allocations`，不得小於 0 或大於 approved total |
| Finance Import dedupe | 同 fingerprint 永遠只有 1 canonical row，另有 N occurrences；fingerprint 不得包含檔名、sheet 或 row number |
| Alert current state | detector 的 active/inactive desired state 經 identity upsert 形成；根條件消失自動 resolve，復發 reopen |
| Access session | idle timeout 30 分鐘、首次登入起 absolute maximum 8 小時；role、disable 或 credential rotation 同交易撤銷既有 sessions |

### 4.2 每個情境都要記錄的 Dataflow Checkpoint

為了讓資料同時可用於 debug，每個 scenario 的 expected manifest 必須記錄以下 checkpoint 的 `新增／不新增／保持不變` 與預期 row count：

1. Source payload／typed command。
2. Canonical raw／staging／occurrence。
3. Preview candidate、typed blockers 與 Preview writes=`0`。
4. Immutable event／ledger／allocation／receipt。
5. Aggregate version、lifecycle、balance、hours 等 projection。
6. Outbox、Alert、cache 等 async observation。
7. API ViewModel、XLSX、UI 所見標準答案。
8. 相同 idempotency key 重跑，以及 stale version／fingerprint conflict 的 row delta。
9. 每個 transaction seam 注入失敗後的 `EXPECTED_ABSENCE`。

## 5. 狀態機測試矩陣

狀態欄位一律是 root events 的 reducer／projection 結果。測試必須提供觸發事件與 guard，不得直接寫入 target state。每個 transition 都要驗證 history、version、outbox、idempotency replay，以及非法轉移的 `EXPECTED_ABSENCE`。

### 5.1 Orders 與服務資料鎖

### 5.7 狀態機共通驗收模板

每一列至少測試：

1. 合法 transition 的 before／after state、history event、aggregate version、receipt、outbox row delta。
2. 缺 guard、stale version、fingerprint 改變與 capability 不足時，state/history/version 全部不變。
3. 相同 idempotency key＋相同 payload 回原 receipt，不新增 history；不同 payload 固定 conflict。
4. transition transaction 每個 persistence seam 失敗都完整 rollback。
5. Query、Preview、UI render、XLSX export 與 Alert resolve 不得偷偷觸發業務 state transition。
6. projector 停擺時 root transaction 可依契約提交；恢復後由 checkpoint 重播且不重複 transition。

## 6. 異常狀態測試資料與修正閉環

異常測試不得直接 `INSERT anomaly_current_alerts`。一般整合測試必須建立會觸發異常的 source-domain roots，執行 detector／projector，再由 API 與 UI 驗證投影。只有 Anomalies Repository 的局部測試可以直接建立 stored projection。

### 6.1 每個異常都必須通過的閉環

```text
建立異常 ROOT
→ 執行 owning detector／consumer
→ canonical alert active/open
→ API summary/detail 顯示安全 snapshot、timeline、available_actions
→ UI 顯示正確分頁、代碼、severity、狀態、導航／修正入口
→ 人員 claim
→ 透過 owning Domain Preview／Apply 修正 ROOT
→ detector 輸出 inactive desired state
→ alert predicate_active=false、workflow_status=resolved
→ active-only API／UI 不再顯示，歷史查詢仍保留完整 timeline
```

另須測試「只按人工解除但沒有修正 ROOT」：下一次 scan 必須 `reopen`。Anomalies 的 resolve 動作不能修改 Orders、Scheduling、Finance、Payroll、Staff Payables 或外部 identity。

### 6.2 API／UI 共通標準答案

| 檢查面 | 標準答案 |
|---|---|
| 清單 | 顯示 definition code、source domain、severity、predicate active、workflow status/version 與安全 display snapshot |
| 詳情 | 顯示 occurrence＋workflow timeline、root fact 摘要、projection freshness、domain blocker 與 available actions |
| 分頁 | Import、流程、帳務、服務人員、LINE 分組正確；同一 fingerprint 不得重複出現在錯誤群組 |
| 導航 | `ORDER-*` 可前往配對；`SCHEDULE-001/003/005` 帶入 staff/date；有 Preview action 的異常顯示正確入口 |
| 認領 | open → claimed；兩位人員競態只有一位成功，另一位收到 409 conflict |
| 人工解除 | reason 必填；只改 workflow，不改 source root 或 blocker；根條件仍在時下一次 scan reopen |
| 自動解除 | root 修正後 projector 產生 inactive；active-only 清單消失，歷史與 audit 保留 |
| 隱私 | 不顯示完整銀行帳號、姓名、電話、LINE user id、raw payload 或 token；snapshot 只含 registry allowlist |
| Projector retry | source transaction 不回滾；相同 source event 重播不增加 occurrence，內容不同則 integrity conflict |
| UI 錯誤 | API typed error 顯示 code/message；不能因單筆 detail 失敗讓整頁其他異常消失 |

| GOVSUB-004 | reversal超過可沖額、target錯誤或來源receipt矛盾 | blocking；remaining reversible、source receipt | PreviewGovernmentSubsidyReversal修正target／amount | 合法append-only reversal後 inactive；禁止reversal-of-reversal |
| GOVSUB-005 | 送件snapshot與assignment/service roots發生漂移 | blocking；assignment、claim item、drift fields | 查詢batch，依凍結邊界建立revision／人工裁決 | 合法revision吸收差異後 inactive；不得覆寫已送件snapshot |

### 6.7 LINE 異常與已知規格漂移

| Code | 要生成的異常 ROOT | UI 標準答案 | 人員修正動作 | 消除條件／負向測試 |
|---|---|---|---|---|
| LINE-001 | 需通知客戶但角色內沒有有效LINE binding | LINE區；case；不得顯示完整line_user_id | LINE review bind／rebind | 客戶角色binding有效後 inactive；不可以line_id文字代替 |
| LINE-005 | 需通知staff但角色內沒有有效LINE binding | LINE區；case | LINE review bind／rebind | staff角色binding有效後 inactive |
| LINE-002 | sent delivery task超過回覆條件且無對應webhook response | LINE區；task id、遮蔽recipient | 人員檢視task、重送或處理recipient binding；正式回覆到達 | response/root條件滿足後 inactive；provider attempt不等於業務回覆 |
| LINE-004 | 現行detector以跨clients/staff相同line_user_id形成Alert | 必須建立反向驗收：同一identity跨角色時UI不應顯示異常 | 正式規格允許同一人同時是客戶與staff；只有同角色歧義才需review | 目前registry/source與正式規格漂移；在detector修正前此案例預期揭露失敗，不得把跨角色資料改掉來讓測試通過 |

### 6.8 異常 fixture 的 row-delta 標準

每個 anomaly scenario 必須在 expected manifest 列出：

1. 異常 ROOT 建立後：source tables/events 的精確新增數。
2. 第一次 scan：`anomaly_current_alerts +1`、projection receipt `+1`、root snapshot／checkpoint insert或upsert；只有 Finance occurrence 型才 `finance_anomaly_occurrences +1`。
3. 重掃相同 source version：current row 不重複；事件式重播回原 receipt。
4. claim：workflow event `+1`、status=`claimed`、source tables `0` 變更。
5. owning Domain修正：只新增正式 correction/event/receipt/outbox，不直接更新Alert。
6. inactive projection：predicate=false、workflow resolved、`auto_resolve` workflow event `+1`、active-only query減1；歷史row與timeline保留。
7. 未修ROOT只resolve：下一次scan workflow event=`reopen`、current row `+0`、active-only重新出現。
8. projector failure：source Domain transaction不回滾；API顯示 `projection_freshness=stale`，retry補齊後不得重複current row或occurrence。
9. UI：清單、detail、導航、action、成功／typed error訊息與修正後消失均有驗收。

### 6.9 必須由測試揭露、不能用 fixture 掩蓋的現況缺口

1. Canonical registry 目前共有 33 個 anomaly codes，本矩陣已全數覆蓋；但其中 14 個沒有 typed `available_actions`：`BECLASS-001`、`CLIENTPAYABLE-001`、`IMPORT-004`、`LINE-001`、`LINE-002`、`LINE-004`、`LINE-005`、`RECEIVABLE-001`、`RETURN-001`、`SCHEDULE-001`、`SCHEDULE-002`、`SCHEDULE-003`、`SCHEDULE-005`、`SUBSIDYADVANCE-001`。
2. UI 的「前往行事曆／配對」只能算 navigation，不等於 owning Domain typed recovery。測試必須分開驗證「能前往」與「修正命令真的存在並能解除異常」。
3. `SCHEDULE-002` 尚缺正式「財務拆分已複核」root fact／receipt。現況只能人工 resolve，不能證明根因已消除；在補完資料模型前，閉環測試應預期失敗並列為 GAP。
4. `LINE-004` detector 仍把 clients/staff 跨角色共用 identity 當衝突，違反已確認的角色語意。測試必須保留合法跨角色資料並揭露 false positive，不得修改 fixture 配合錯誤 detector。
5. 舊文件中的 `LINE-003`、`DOC-SEND-002`、`SCHEDULE-004`、`FAQ-001` 等尚未進 canonical registry，且缺可靠結構化 detector／root fact；不得直接 seed Alert 冒充已支援。
6. 舊 `IMPORT-006=普通待分類` 已退役；普通待確認只能投影 `finance_import_manual_review`，完整性故障才是 `IMPORT-006`，兩者不得同時替同一原因報警。
7. 無 typed recovery action 的 code 即使 detector／UI 顯示測試通過，也只能標為「辨識與顯示完成」，不能標為「人工修正閉環完成」。

## 7. 最小情境目錄

新版資料集不以「固定 50 案」作為完整性的唯一標準，而以可追蹤情境覆蓋為主。每個情境具有穩定 `scenario_id`，一案可以覆蓋多項相容規則，但禁止把互相矛盾的正常／異常條件混在同一案。

### 7.1 正常主流程

1. 洽談中，沒有正式 obligation、assignment 或服務日。
2. 契約完成但訂金未核銷。
3. 訂金已核銷、等待 actual-start confirmation。
4. 單一月嫂服務中。
5. 兩位月嫂無縫交接服務中。
6. 三位月嫂無縫交接並完成。
7. 一般市民完成、客戶應收與月嫂應付皆精確核銷。
8. 補助市民不超過 120 小時且無自費，形成全補助 funding path。
9. 補助市民超過 120 小時，超出部分每小時 350 元形成客戶應收。
10. 補助市民有樓層費，樓層費形成客戶應收。
11. 未完整履約取消，保留已服務 roots 並形成退款或補款結果。
12. 請假／代班後仍維持全案 coverage 與 ownership。

### 7.2 財務與補助邊界

1. 精確收款、部分收款、先部分後超收、單筆超收。
2. 客戶退款正常一次清償、人員匯少後補匯、退匯與 reversal。
3. 月嫂精確出款、少付／多付、共享銀行帳戶、退匯／沖正。
4. 銀行同列跨批次重複、fingerprint collision、缺列與 partial batch。
5. 補助短撥、溢撥、無法唯一對應、政府款未入但月嫂款到期。
6. 已有正式核銷歷史後 Terms／服務日更正，只追加 adjustment／reversal，不覆寫歷史。

### 7.3 排班、資料與安全異常

1. 月嫂占用重疊、七日 buffer 衝突、固定休假／國定假日衝突。
2. assignment coverage 缺口、雙 owner、cancelled assignment 殘留 projection。
3. HCM／BeClass 孤兒列、重複 identity、缺必要欄位、非法日期與非法金額。
4. LINE identity 同角色多重綁定、重複 webhook、缺 recipient、provider delivery failure；跨客戶／月嫂角色的同一 identity 為允許情境。
5. 無 capability 管理操作、失效 session、同時版本衝突。
6. projector 失敗、outbox 重送、Apply 中途 persistence failure。

### 12.1 稽核判定方式

### 12.4 測試資料責任邊界

「可以測試」不等於「應由測試資料生成器負責」。本專案將驗證素材分成以下五類：

| 類別 | 是否屬於本測試資料矩陣 | 內容 | 驗證方式 |
|---|---|---|---|
| `DOMAIN_ROOT_DATA` | 是 | 客戶、訂單條款、assignment、正式服務日、銀行root、obligation、外部identity等業務根事實 | 在全新 `lu_test_*` 內透過importer／typed Command建立，再驗events/projections/API/UI |
| `EXTERNAL_INPUT_FIXTURE` | 是 | HCM／BeClass／銀行XLSX、webhook payload、知識來源文件、media等系統輸入 | 保存去識別化檔案／payload，送進正式入口；不得直接硬塞已型別化主表 |
| `METADATA_FILESYSTEM_FIXTURE` | 否；另屬Infrastructure驗證矩陣 | release manifest、config bytes、backup artifact、archive path、entry queue | temp filesystem、digest、CLI／script契約測試，不播種業務資料 |
| `PROCESS_NETWORK_HARNESS` | 否；另屬Runtime／Integration驗證矩陣 | API/worker readiness、queue lag、DB pool、TLS、provider timeout、Redis failure、process restart | fake adapter、容器、故障注入、process/network harness |
| `BENCHMARK_MANUAL_EVIDENCE` | 否；另屬效能／部署驗收 | UI click-to-render、API/DB latency、N+1、EXPLAIN、容量、實機edge與restore drill | benchmark evidence、環境量測或人工驗收；不能靠生成幾筆DB資料宣稱通過 |

混合型 Subsystem 必須拆開責任。例如 Accounts Payable Export 的「哪些應付款應出現在報表」由 `DOMAIN_ROOT_DATA` 驗證；XLSX bytes、SHA-256與archive原子發布則由 `METADATA_FILESYSTEM_FIXTURE` 驗證。LINE 的binding/task roots屬測試資料；provider 斷線與TLS不屬測試資料。

### 12.5 測試資料矩陣真正負責的範圍

| 範圍 | 測試資料應負責 | 不由測試資料負責 |
|---|---|---|
| Orders／Scheduling／Payroll／Finance／Subsidy | roots、commands、events標準答案、projection、狀態機、異常根因與修正閉環、Query/UI內容 | service process health、真實網路延遲 |
| Finance／Case Import | 去識別化來源檔、canonical row、occurrence、classification、reprocess資料答案 | File Watcher程序存活、OS檔案權限、實際網路磁碟 |
| Anomalies | 造成異常的source roots、Alert標準答案、UI顯示、owning Domain修正後auto-resolve/reopen | worker heartbeat、projector實際營運lag告警門檻 |
| LINE／Knowledge | webhook/source/media fixture、identity、inbox/task/index狀態答案 | 真實LINE provider、TLS、外部平台可用性 |
| Access Control | admin/session/capability/audit roots、typed authorization結果、security anomaly資料 | production secret管理、VPN/LAN拓撲 |
| Accounts Payable Export | payable/refund/subsidy-return來源資料、聚合與列內容標準答案 | archive filesystem故障、容量、實際Office相容性 |
| API／UI | 以資料驅動的success/empty/warning/error/stale內容與操作後資料變化 | 真實瀏覽器paint時間、連線協定與target-host效能 |

因此，12.2 中真正屬於本文件必須補齊的項目是：Order/Finance/Subsidy Query、Waiting Deposit Lock、Calendar View、Payroll/Finance計算、Client Subsidy Return、Adjustment、Historical Reprocess、Rich Menu資料狀態、Security Audit資料、Knowledge citation、異常root與修正閉環，以及Accounts Payable的資料內容部分。

### 12.6 非測試資料責任：移交其他驗證矩陣

下列項目仍然必須測試，但不能用「生成測試資料」證明完成：

| Subsystem | 驗證 owner／類型 | 不應由seed script做的事 |
|---|---|---|
| Preserve-data Migration／Cutover | Infrastructure／`METADATA_FILESYSTEM_FIXTURE`＋disposable database harness | 不在業務fixture中模擬production source、config switch或DDL journal |
| Backup／Restore／Recovery | Infrastructure／external tool＋restore drill | 不以一筆backup metadata row冒充可還原 |
| Release Orchestration | Release harness／manifest＋approval receipts | 不播種`released`狀態當標準答案 |
| Deployment Security／Topology | Deployment／network/process acceptance | 不用DB資料證明port、TLS、VPN、principal或secret隔離 |
| Runtime Supervision／Observability | Runtime harness／fault injection | 不直接seed health、heartbeat或lag數值 |
| Performance／UX latency | Benchmark／browser、API、DB evidence | 不由fixture數量直接推斷速度，也不把budget failure建成業務Alert |
| Cache | Adapter contract／fault injection | 不把cache內容當SSOT或seed業務結果 |
| Durable Job worker reliability | Process/queue harness | 不直接seed`succeeded`；必須實際跑worker並連結正式receipt |
| External Side Effects | Provider adapter／sandbox integration | 不以假provider success row證明外部真的完成 |
| Entry Point Governance | Static metadata validator | 不需業務DB資料 |
| Legacy Writer Retirement | Static scan＋endpoint/CLI regression | 不需生成客戶或訂單資料才能證明writer不可達 |
| Archive／Retention／Capacity | Filesystem/object-store harness | 不用業務row宣稱atomic publish、retention或容量通過 |
| Global Typed Error／Timeout | API contract＋fault injection | 不以異常業務資料取代timeout/deadlock/unavailable注入 |

Accounts Payable Export、Finance Import、LINE與Knowledge屬混合型：業務內容由本測試資料矩陣負責；檔案、process、provider或archive可靠性移交對應的Infrastructure／Runtime矩陣。

### 12.7 測試資料矩陣 Gate

在以下條件完成前，本文件只能稱為「核心 Domain 主流程＋現行 anomaly registry 草案」，不能宣稱完整測試資料規則：

1. 12.2 中屬 `DOMAIN_ROOT_DATA`／`EXTERNAL_INPUT_FIXTURE` 的 missing Subsystem，各有正向、負向與replay/rollback scenario。
2. 14個缺typed recovery action的anomalies補成正式入口，或明確保持GAP且不得標閉環完成。
3. Access/Security alerts、Rich Menu/Media資料、Historical Reprocess、Client Finance Adjustment/Subsidy Return加入fixture manifest。
4. 所有Query與UI資料情境驗證zero mutation、遮罩、bounded payload與source version。
5. 混合型輸出明確拆分「資料內容oracle」與「filesystem/provider/process驗證」，不互相冒充完成。

Migration、Deployment、Release、Runtime Observability與Performance不再列為「測試資料矩陣未完成」；它們應另建Global Infrastructure／Runtime驗證矩陣，並在整體系統release gate匯總。
