# 媒合候選池、客戶決定及通勤規格

## 1. 文件邊界與所有權

- 狀態：`current-spec`
- Owner：Assignments／Scheduling Domain — Matching Coordination Subsystem（`subsystems/scheduling/`、`domains/scheduling/`）
- 單一負責範圍：Candidate Contact Pool（寄送案件資訊、意願詢問、`latest_willingness_event_id` 與更新詢問期間）、M3 Matching Coordination（`caregiver_matching_plans`、`1..4` 連續分段、`event_key` 冪等收據與可選履歷 PDF）、LINE 及人工接案意願／客戶決定更正、服務前整案換人（R-04）與 24h 跟進掃描、推薦／客戶決定／自動保留單一日期解析與結果核對（`MATCH-ROOT-01～07`）、機車通勤即時路況人工查詢（`TWO_WHEELER`），以及歷史訂單配對證據。
- 關聯引用：見 [Global 共同契約](00_Global_共同契約.md)、[Orders Domain](01_Orders_Domain.md)、[訂單看板、事前日期與歷史採納](01A_訂單看板與事前日期及歷史採納規格.md)、[Assignments / Scheduling Domain](02_Assignments_Scheduling_Domain.md)、[Payroll Domain](03_Payroll_Domain.md)、[Client Finance Domain](04_Client_Finance_Domain.md)、[Global 效能與 UX 體感架構](12_Global_效能與UX體感架構.md)、[External Integration / Access Control](17_External_Integration_LINE_Access正式規格.md)、[LINE Gateway 與通知投遞](17A_LINE_Gateway_Inbox與通知投遞正式規格.md)、[Contract Signing 正式規格](21_Contract_Signing_Commitment與正常驗收資料鏈正式規格.md)、[Staff Matching Preferences](24_Staff_Matching_Preferences與不可服務期間正式規格.md)。

## 2. 核心不變量與資料模型（SSOT）

- **Candidate Contact Pool 獨立性**：僅擁有候選月嫂聯繫、發送事件、意願回覆與拒絕理由（append-only 且按 candidate event key 冪等）；不得建立 waiting lock、assignment、日期表、客戶履歷發送或指派資格（一次可加入多位，含部分衝突者，並於加入與每次寄送時 fresh-read 可用性及 [偏好設定](24_Staff_Matching_Preferences與不可服務期間正式規格.md)）。
- **M3 `accepted` 邊界**：客戶決定 `accepted` 僅為 Matching Coordination 決策，不等於契約完成、正式指派或薪資義務；唯有與 [事前確認服務日期](01A_訂單看板與事前日期及歷史採納規格.md#32-confirm-service-dates-與休假覆寫契約) 雙條件齊備時，由後到條件之 Apply 在同一 outer UoW 自動取得 `waiting-deposit` 鎖。
- **Criteria Tuple Preview/Apply**：首次建立無既存 snapshot 時由 Preview fresh-read owner facts 回傳 canonical tuple（不接受 client version 斷言）；Apply 回傳完整 tuple 與 fingerprint 並重新 fresh-read 驗證（M3 不接管 `assignment_plan` 或 `leave_substitution` writer）。

## 3. 公開契約與流程

### 3.1 寄送案件資訊、候選詢問與更新詢問期間

- **工作台操作順序**。先在「尋找月嫂與詢問意願」設定休假並保存每週服務說明的預計日期，再開啟案件共用預覽。第三步從指定月嫂卡片確認寄送，一次只送該名月嫂。每次寄送核對共用預覽及該收件人的內容與預覽指紋，投遞任務與結果逐人回讀。案件內容更新時，經辦重新核對預覽後再確認寄送。

- **寄送案件資訊**。工會人員對每位選定的候選月嫂人工確認後，將「服務條件與費用（訂單資訊－1）」、「照護與飲食需求（訂單資訊－2）」、「每週服務說明」依序各放一張表格圖片，最後附一張共用接案意願回覆卡。四頁組成一則可左右滑動的 LINE Flex 訊息，整包建立一筆投遞任務，向該月嫂執行一次 Push。訂單資訊－1 的財務欄位限於薪資單價、預估總薪資及預計付款日，取自 [Payroll 唯讀預估](03_Payroll_Domain.md#31-候選月嫂唯讀預估)。
- **寄送條件與核對**。每週服務說明使用 [Orders 已保存的最新確認服務日期與每日時數](01A_訂單看板與事前日期及歷史採納規格.md#32-confirm-service-dates-與休假覆寫契約)。日期尚未保存時，整包不可寄送。寄送預覽綁定該月嫂與整包內容。確認時重驗收件人、已保存日期與預覽內容，將凍結的整包快照與投遞任務一併提交，並以同一筆回條查詢整包投遞結果。同鍵同指令回傳原回條。該候選已有初次整包投遞任務時，新指令鍵不另建任務。
- **共用接案意願回覆卡**。卡片只有「可以接案」與「無法接案」兩個操作。系統核對原卡片與收件月嫂身分，並確認案件仍開放回覆後，直接將選擇記錄為「願意承接」（`willing`）或「無意願」（`unwilling`）。案件開放回覆且原卡片有效時，月嫂可在同一張卡再次點擊以變更意願，採最新有效紀錄。點擊不開啟表單、不建立協調待辦、不通知客戶、不修改訂單條件，也不新增 Push 任務。
- **候選回應識別**。同一案件可記錄多位月嫂的意願，由工會決定推薦人選。回讀回傳可空的 `latest_willingness_event_id`，僅在 ID 與意願值皆吻合該次回條時確認儲存。更新詢問期間時追加帶有前後日期的 `pending` 意願事件，並停用原期間意願。
- **人工處理疑問**。月嫂有疑問時直接聯絡工會，由工會人員處理。工會可在既有案件工作台登記接案意願，需更改條件時依 [Orders Domain](01_Orders_Domain.md) 辦理。候選卡送達滿 24 小時仍未回覆時，僅列入工會內部提醒。
- **退役範圍**。移除「詢問或婉拒接案」表單、「人工協調問題與回覆」與「重新詢問」的入口，以及該流程專用的客戶回覆表單、詢問與回覆公版、待辦、審核與寄送功能。既有表單連結停止受理，相關未投遞任務停止發送，已保存的紀錄留存。
- **單人推薦免阻擋預計日**：單一已願意初步候選建立推薦方案時，沿候選詢問預計期間驗可用性（不受前段每週說明已保存日期範圍干擾；多月嫂分段須明確分段並驗完整 coverage）。
- **正式推薦建立（`event_key` 1..191 字元）**：Apply 先鎖案再鎖 `event_key`（僅重查 receipt，同鍵同指令直接回原收據、不重驗被本指令變更之檔期；同鍵異指令衝突零寫入）；首次建立未收訂金檔期之推薦釋放若缺 `settlement projection`，須先於同 UoW 取得 [Client Finance UnreceivedDepositConfirmation](04_Client_Finance_Domain.md#34-不可變帳本補助退還分離調整單與釋放確認)。

### 3.2 客戶推薦確認、手動更正與服務前整案換人（R-04）

- **意願投影與雙向修改**：同案候選詢問期間涵蓋正式區段且已同意時，直接投影為該區段同意；有效期限內月嫂本人可在客戶決策 `pending / contact_requested` 反覆改意願，`accepted` 方案亦允許改 `unwilling` 觸發換人（已拒絶則關閉）；人工補登意願變更於同一 outer UoW 同步更新該區段對應之 active 初步候選。
- **推薦確認與專人協助**：履歷 PDF 為可選附件（缺檔或儲存不可用不阻擋寄送確認資訊，僅介面提示並省略按鈕）；客戶點「專人協助／進一步了解」寫入客戶服務待辦而不阻擋原卡片隨後接受；送達滿 7 天僅作內部待辦提醒而不自動關閉按鈕；客戶人工決定「回覆依據」為選填（空白存空字串、500 字上限，DB `chk_matching_response_manual_reason` 限制已移除）。
- **服務前整案換人（R-04）**：僅限尚未發生任何 assignment-owned 實際服務日者（已服務一律改走請假代班）。
  - 尚無正式 assignment 時先走「釋放鎖 → 取消原 proposed 方案 → 新建方案」；已有 waiting lock／generation 無實際服務日時，由 R-04 Apply 同 UoW 退役原方案、標記原候選 withdrawn（保留歷史但不移植同意或接受），使 `訂單成立` 案件得以在綁定當下 R-04 receipt 與零有效排班條件下重啟候選詢問與推薦，並以同一 predicate 執行 24h 逾期跟進與前置取消。

### 3.3 單一日期解析與未知命令核對（`MATCH-ROOT-01～07`）

- **日期一致性**：推薦建立、客戶確認 Preview（`service_period_start` / `service_period_end` 僅投影已保存服務日首末日，缺則為 `NULL`）與自動保留共用同一 current confirmed-date version，不以舊推薦外框覆蓋已保存服務日；錯分三類失敗：（1）真實班次／保留／不可服務重疊（衝突＋對象＋起訖）、（2）日期／分段缺口或日數不符（日期／方案錯誤）、（3）占用缺可追溯時段（「時段待確認」）；buffer 僅提醒。
- **結果核對不盲目開新鍵**：首次與原鍵重試採相同業務拒絕語意（明確未提交解除輸入保護）；僅在斷線或 timeout 未確認結果時保留原鍵沿原 writer 冪等查詢，僅當鎖定 current plan 證實無原鍵收據且 version 已遞增使舊鍵必失敗時始允許開放新鍵（`401/403` 先驗權限恢復）。

### 3.4 人工機車通勤即時查詢與歷史訂單配對

- **機車通勤查詢**：路線為「月嫂名冊地址 → 客戶案址」，參數 `TWO_WHEELER` ＋ `TRAFFIC_AWARE_OPTIMAL`（以當下出發時間計即時路況）；按人員手動逐位觸發（限 1 次 Google 請求、不自動重試）；於同一瀏覽器分頁按 `case_no + staff_id` 暫存上次結果與查詢時間（關閉重開抽屜保留，重整／切換登入清空，不存 DB／WebStorage，顯示用量僅限新增候選抽屜）；`GET /api/v1/orders/{case_no}/commute-history` 維持 `system_admin` 最近 50 筆 metadata-only 唯讀端點（不回傳地址、距離、分鐘或原始回應）。
- **歷史訂單配對證據**：支持保存 1 或 2 位月嫂不可變來源證據（姓名缺漏／不明留 bounded review 不阻擋 Orders 採納）；唯單一月嫂具備唯一共同起訖日且可歸屬本人時得由專屬 Scheduling writer 建立 `completed` `case_staff_assignments`（缺逐日 ownership／rate snapshot 時 Payroll fail closed 不猜算日薪）。

## 4. 驗收標準

1. **`MATCH-ROOT-01～07`**：驗證單月嫂延伸已保存服務日期不觸發誤報缺口、真實占用／不可服務精準阻擋與回滾、先接受後存日與先存日後接受兩條順序之原子保留、未知結果與 `401/403/409` 分流及空原因事件與升級前後資料保存。
2. **寄送案件資訊**。日期已保存且預覽有效時，每位收件月嫂各有一筆投遞任務與一則四頁 Flex Push，頁面依序為三張資料圖和一張共用回覆卡。日期未保存或預覽已失效時，建立零筆投遞任務。同鍵同指令重試可查得原回條，投遞狀態以整包回讀。
3. **候選意願回覆**。驗證兩個按鈕各自直接記錄對應意願，`latest_willingness_event_id` 與回條一致。同一 LINE 事件重送不新增紀錄。同一張有效卡可由本人多次變更意願，非收件人或已關閉案件零寫入。驗證退役入口無法提交或寄送，既有紀錄留存。
4. 驗證 `R-04` 換人與 24h 跟進零移植、機車通勤無 DB/localStorage 洩漏及 `commute-history` metadata 隱私。
