# 案件與月嫂整合名冊正式規格

## 1. 文件邊界與所有權

- 狀態：`current-spec`
- Owner：Admin Registry Composition（Clients／Staff Roster）
- 單一負責範圍：管理端「客戶名冊」（以 `case_no` 為中心）與「月嫂名冊」（以 `staff_id` 為中心）的跨 owner 唯讀投影組合、Excel 表頭篩選與匯出契約、電話正規化、root 永久刪除未簽約案件邊界、欄位可編輯／唯讀能力、BeClass 補登／照護／退款帳號連動與月嫂完整銀行帳號顯示規則。
- 關聯引用：見 [Global 共同契約](00_Global_共同契約.md)、[Client Finance Domain](04_Client_Finance_Domain.md)、[Global Migration 與 Cutover](10_Global_保留資料Migration與Cutover_Subsystem.md)、[Case Import 與非市民待審](17B_Case_Import與非市民Redis待審正式規格.md)、[Global Entry Point Governance](19_Global_Entry_Point_Governance.md)、[LINE 客服與月嫂自助服務](20_LINE客服與月嫂自助服務正式規格.md)、[銀行流水對帳與手動補登](22_銀行流水匯入與帳務異常處理正式規格.md)、[Staff Roster Case Preference Read Model](24A_Staff_Roster_Case_Preference_Read_Model正式補充契約.md)、[歷史訂單生命週期與服務天數帳務正式規格](27_歷史訂單生命週期與服務天數帳務正式規格.md)

名冊只是 authenticated composition／presentation，不擁有任何 root fact。每一區塊獨立呼叫對應 owner Query／Preview／Apply；跨 owner 儲存不得假造 atomicity，UI 必須明確顯示各 owner 結果與 fresh readback。

## 2. Owner 路由矩陣

| UI 區塊／欄位 | 唯一 mutation owner | 名冊責任 |
|---|---|---|
| Client profile（含 `clients.email`） | Client Profile | 組合、送出 typed command、顯示 receipt／readback |
| Client BeClass effective correction（含退款帳戶、照護） | Case Import | 保留原始問卷；僅寫 effective correction Overlay |
| 預計服務日期、天數、時數、下廚、樓層費、服務時段 | Orders Terms | 直接重用 `/api/v1/orders/{case_no}/terms` Q/P/A |
| 歷史訂單實際服務天數 | Orders / Historical Accounting | 於案件詳情帳務區原地操作（見 [規格 27](27_歷史訂單生命週期與服務天數帳務正式規格.md)） |
| Staff 個人／聯絡／行政註記／`union_no` | Staff Profile | 不混入 lifecycle、資格或 LINE identity |
| Staff active／retired | Staff Lifecycle | 重用 Staff Retirement Q/P/A（無永久刪除） |
| Staff 銀行帳戶 | Staff Bank Account | `add`、`replace`、`deactivate`、`set_primary` |
| Staff 專業資格／接案條件／不可服務期間 | 各既有 owner | 名冊依各 owner Q/P/A 或唯讀投影組合 |

## 3. Root 案件永久刪除（RD-1）

- **權限**：僅已登入、enabled、具持久化 ID 且 `is_root=true` 之帳號可 Query 刪除資格及 Apply（透過 `/api/v1/admin/auth/me` 回讀確認）。月嫂名冊**不提供**永久刪除（僅保留退役／復職）。
- **禁止條件**：任一相關月嫂或客戶曾完成簽回（`contract_signing_events.signed_received` 或 `order_contract_flow_events.contract_completed`，含非 current plan）即禁止刪除。契約草稿、配對、排班、帳務或歷程本身不阻擋未簽約案件刪除。
- **原子刪除範圍**：同一 outer UoW 內沿 canonical case/client identity 與 inbound FK 刪除該案配對、排班／占用、帳務、匯入綁定、歷程、收據、待處理任務、獨佔 Client 及 LINE／附件之 case-owned metadata（共用 Client、月嫂、共用銀行批次、NAS 實體檔案與外部 LINE 訊息不刪不撤）。現行 price-event／obligation-source cycles 僅於待刪列解除 nullable 指標；依賴 `registry_delete/v1` pending claim 與 `lu_nas_delete_unsigned_case_v2` guard 保護不可變歷程。
- **端點與 UI**：`GET /api/v1/admin/registries/clients/{case_no}/deletion`、`POST /api/v1/admin/registries/clients/{case_no}/deletion/apply`（401/403 零寫入、404 不存在、409 conflict／`registry_deletion_guard_rejected`）。UI 明示刪除後果，收到成功 receipt 才關閉抽屜移除案件列；結果未明鎖住離頁以原鍵核對。

## 4. 公開 HTTP 契約

### 4.1 客戶名冊與匯出

- `GET /api/v1/admin/registries/clients`（支援 `query`、`multi_birth_count`、`order_status`、`requires_cooking`、`sort_by`、`sort_order`、`limit`、`after`、`offset`、`column_filters`）：`after` 與非零 `offset` 不得併用；排序 allowlist 為 `case_no`、`customer_name`、`service_days`、`expected_start_date`；接受 A 開頭非市民案號。
- `column_filters`（JSON array，每欄至多一筆 `{field, operator, values}`）：allowlist 涵蓋案件編號、姓名、補助身分、電話、地址行政區、BeClass effective 胎數、訂單狀態、服務方式、下廚、天數、預計服務日期、訂金／一二期／補助退還日、月嫂應付日。不同欄位 AND、`in` OR、`not_in` 排除、`null` 表空白（與 `requires_cooking=false` 分離），支援 `contains`／`starts_with`／`equals`／`gt`／`lt`／`between`／`blank`；多筆義務不因 join 重複案件列。
- `GET /api/v1/admin/registries/clients/filter-options?field=&search=&limit=&offset=`：從全名冊該 allowlisted 欄位取 distinct nullable 值。
- `GET /api/v1/admin/registries/clients/{case_no}`：Client／BeClass／Order Terms／唯讀帳務 composition readback。
- `GET /api/v1/admin/registries/clients/export/order-accounting`：依名冊目前篩選與排序匯出每案一列 XLSX（HCM 八欄＋Orders Terms＋Client Finance／補助投影金額與日期，原生數值日期型別）。
- `GET /api/v1/admin/registries/clients/export/case-inspection`：依名冊目前篩選與排序匯出九工作表案件資料檢查 XLSX（案件總覽、保存資料、派案、排班、客戶義務、收付流水、款項分配、月嫂應付、月嫂付款分配，以 `orders.case_no -> clients.id` 關聯；不匯出身分證、電話、住址、真實銀行帳號、憑證或 raw payload，文字不為公式）。
- `POST /api/v1/admin/registries/clients/{case_no}/profile/preview`、`POST /api/v1/admin/registries/clients/{case_no}/profile/apply`、`POST /api/v1/admin/registries/clients/{case_no}/beclass/preview` 與 `POST /api/v1/admin/registries/clients/{case_no}/beclass/apply`（客戶主檔沿用 `client_profile_version` 與 Client-owned event／receipt 保護並行更新）。

### 4.2 月嫂名冊與公會編號

- `GET /api/v1/staff/roster`（`data_browser.read` 權限，200 人上限 cursor Query，支援 `lifecycle_state=active|retired`）：固定 10 次批次 Query 取得完整 Profile、銀行帳戶、`care_babies` 與七個 canonical relation（含 `cooking_skills`），不逐人發請求，不輸出 LINE User ID、IP 或 credentials。主頁分「現役月嫂／已退役月嫂」分頁；全名冊讀完 bounded cursor 後依 `union_no` 自然升冪排序（例如 A2 在 A10 前，未設定排後、同序依 `staff_id` 升冪）。
- `GET /api/v1/staff/summaries`（支援 `lifecycle_state=active|retired`）：供下拉／排班 selector；管理端所有可由 canonical Staff id 識別之月嫂顯示統一為「公會編號 姓名」（未設定顯示「未設定 姓名」）。
- `staff.union_no`：Staff Profile-owned `VARCHAR(50)`（nullable，去除前後空白，保留前導零，`utf8mb4_0900_bin` 唯一索引 `uq_staff_union_no`，碰撞回 `409 staff_union_no_collision`，1213 死鎖回 `409 staff_profile_concurrent_conflict` 不自動重試）。
- `GET /api/v1/staff/{staff_id}/profile`（含 `profile_version`、`bank_accounts_version`）、`POST /api/v1/staff/{staff_id}/profile/preview`、`POST /api/v1/staff/{staff_id}/profile/apply`、`POST /api/v1/staff/{staff_id}/bank-accounts/preview`、`POST /api/v1/staff/{staff_id}/bank-accounts/apply`、`GET /api/v1/staff/{staff_id}/qualification-editing`、`POST /api/v1/staff/{staff_id}/qualification-editing/preview` 與 `POST /api/v1/staff/{staff_id}/qualification-editing/apply`。
- Staff Profile allowlist：`union_no`、`name`、`identity_card`、`phone`、`tel`、`tel_ext`、`email`、`birthday`、`city`、`zip_code`、`address`、`education`、`emergency_contact_name`、`emergency_contact_phone`、`admin_notes`。Bank command 限 `add`、`replace`、`deactivate`、`set_primary`（同 Staff 至多 20 筆、至少一筆 active primary、不可跨 Staff 共用）。

## 5. 互動模式、Client Profile 與 BeClass Correction

### 5.1 一次點擊送出與選填備註（`CRX-ACCOUNT-04`）

管理端客戶主檔、BeClass 報名／照護／退款帳戶、月嫂個資、銀行、專業資格、接案條件、不可服務期間與退役／復職一律採一次點擊儲存（見 [Global 共同契約](00_Global_共同契約.md) §2.4），客戶／月嫂一般資料異動「備註（選填）」省略時傳空字串；銀行帳戶、人事狀態、不可服務期間與申請審核依各自必填原因契約。`staff_qualification_editing/v1` 使用五欄（`special_skills`、`has_massage_cert`、`certifications`、`care_babies`、`transportation`）canonical snapshot fingerprint 防 stale 409；版本衝突要求重讀、結果未明沿同鍵核對而不 blind retry，正式回讀成功後才更新名冊並保留各區草稿與離頁保護。

### 5.2 Client Profile 與 BeClass 欄位及照護修正（`CRX-ACCOUNT-01`）

- **電話規則**：`clients.phone` 保存手機或含區碼市話（去除空白括號連字號，`+886`/`886` 轉 `0`；手機 `09` 開頭 10 碼，市話 `02`–`08` 開頭 9–10 碼），不改 BeClass 獨立欄位。
- **Email 與服務方式**：`clients.email`（HCM Email）與 BeClass Email 獨立不互填，HCM 匯入僅可補入空白主檔 email；`clients.service_type` 採自由文字輸入（≤100 字，不設固定下拉）；`clients.city` 自由文字（≤20 字）。
- **BeClass Correction（含 14 項照護／約定與未綁定補登）**：原 `beclass_records` 永久唯讀；無 `bound_case_no` BeClass 列之訂單 Query 提供 `version=0` 空白可編輯 view，首次 Apply 建立 `record_origin='admin_manual'` 容器（同案多筆綁定拒絕，不以姓名、電話或 `query_no` 猜配）。
  - **三節與樓層文字**：`holiday_pricing_terms` 與服務樓層方式僅保存文字協調紀錄，不觸發雙倍薪或金額重算；實際樓層費改於 Orders Terms 輸入。
  - **胎數**：`multi_birth_count`（`單胞胎`/`雙胞胎`）僅允許正式服務開始前修改並同交易同步 Client Finance、Payroll 與補助單價（雙胞胎固定 450）；服務開始後財務鎖定。
  - **歷程與換人**：案件抽屜最下方顯示預設收合的變更歷程；倒數第二區「服務月嫂」依 Scheduling Assignment Plan Query 顯示分段並提供「換人」／接任流程分流（已服務轉介代班，未服務走 successor matching round）。

### 5.3 客戶名冊欄位權威、唯讀邊界與退款帳戶連動

| ID | 欄位／區塊 | 正式來源與編輯規則 |
|---|---|---|
| `CRX-01` | 補助身分 | 唯讀讀取 `clients.identity_status`（一般市民／補助市民／原住民／非市民）；嚴禁編輯、反推或改案號 |
| `CRX-02` | 計價身分與補助上限 | 獨立於 `CRX-01`，讀取本案綁定政策／個案計價與版本 |
| `CRX-03` | 退款銀行／分行／帳號 | 讀寫唯一綁定之 BeClass 有效修正（7 碼 `refund_bank_code`＋保留前導零 `refund_account_no`）；缺件標「待補」 |
| `CRX-04` | 生日 | 唯讀讀取 `beclass_records.birth_date`（缺值顯示「尚未登錄」） |
| `CRX-05` | 備註與行政註記 | `clients.notes`（Client Profile 編輯）、`clients.admin_notes`（獨立唯讀）、BeClass `admin_notes`（BeClass 編輯）三者分開不互填 |
| `CRX-06` | 案件日期摘要 | 預計與實際起訖唯讀讀取 Orders 正式值（與排班區段分開）；修改走原 Orders 入口 |
| `CRX-07` | 三方案、免自備與退款摘要 | 唯讀組合案件帳務共用 typed Query；不在此設定方案或改義務金額／日期 |

- **退款快照自動連動（`CRX-ACCOUNT-02`）**：一般退款與補助退款共用同一有效帳戶來源，正式退款建立時保存收款快照；透過客戶名冊 BeClass 抽屜補登退款帳戶儲存時，同一 UoW 自動連動 Client Finance `sync_refund_recipient_snapshots`，為該案尚無快照的 open 退款義務補登不可變快照（`source_kind='beclass_correction_supplement'`），不覆寫已有快照。
- **敏感遮蔽（`CRX-ACCOUNT-03`）**：客戶退款完整帳戶僅存於 owner 資料與授權輸入流程，一般查閱採遮蔽／已登錄狀態，變更歷程、回執、log、錯誤與既有匯出不得流出完整帳號。
- **表格操作（`CRX-SCROLL-01`）**：寬表格使用 bounded vertical viewport 並將水平捲軸固定於表格可視區底部，表頭與資料同步對齊。
- **非市民審核與待審問卷邊界**：待審問卷核准前不進 MySQL（滿 14 天清除，見 [Case Import 與非市民待審](17B_Case_Import與非市民Redis待審正式規格.md)）；核准後 A 開頭案件可於名冊搜尋、查看與匯出。

## 6. 月嫂銀行帳戶顯示契約

- **管理端查閱**：Staff Profile Query 與月嫂名冊清單／詳情支援讀取並展示月嫂銀行完整帳號 `account_no`（無完整帳號時向下相容顯示 `account_last4`）；replace 輸入新完整值，送出後清空 browser state。
- **稽核去敏**：bank event、receipt、一般 log、錯誤訊息與匯出不保存或輸出完整帳號（bank event 僅保存 `last4`）；`deactivate` primary 前須已有或同命令指定另一筆 active primary。現行投影僅影響未固定之未來付款 Query，不回寫歷史 payout snapshot。

## 7. Persistence、不回溯保護與驗收標準

### 7.1 Schema 與不回溯保護

- `beclass_records.record_origin` 僅允許 `imported`／`admin_manual`。DB 變更與執行門依 [Global Migration 與 Cutover §6](10_Global_保留資料Migration與Cutover_Subsystem.md)。
- 下列事實固定不可因名冊修改原地改寫：已簽發／確認契約、已付款／匯出薪資、ledger／payment snapshot、已完成 assignment／schedule、歷史 event／receipt／audit、original BeClass evidence、已送出 LINE 訊息。Orders Terms 使契約失效時僅形成需換版或重確認狀態。

### 7.2 驗收標準

1. `case_no` detail 正確組合 Client、唯一 BeClass effective view（含無綁定案件之 `admin_manual` view）與 Order Terms；`CRX-01`～`07` 唯讀與編輯邊界嚴格一致；補助退款補登帳戶後正確連動產生 `beclass_correction_supplement` 快照。
2. 月嫂名冊完整展示 Staff Profile（`union_no` 自然排序）、完整銀行帳號（無值顯示末四碼）與資格能力投影；一般查詢與事件不洩漏客戶退款帳號及系統敏感憑證。
3. 所有 owner mutation 通過 zero-write Preview、fresh version／snapshot fingerprint、typed 409 conflict、idempotency replay、safe receipt 與 fresh readback；RD-1 永久刪除嚴格驗證 `is_root=true`、未簽約才刪、共用 Client 與月嫂保留。
4. React desktop 與窄畫面實際驗證表頭篩選、底部水平捲動、各區草稿與結果未明離頁保護、換人分流與取消結算入口。
