# 案件與月嫂整合名冊正式規格

狀態：`approved-current`
Authority：GitHub Issue `#276`、2026-09-11 人工明確要求「完成 #276」，以及 2026-09-15 人工明確要求所有未綁定 BeClass 案件均可人工補登
適用：repository-local additive schema、typed API、React entry、focused tests
排除：production DB migration／cutover、部署、外部 provider effect、歷史資料回寫

## 1. 目的與邊界

管理端日常修正收斂為兩個 bounded 名冊：

- 客戶名冊以 `case_no` 為選取中心，組合 Client Profile、唯一綁定的 Client BeClass effective correction（或未綁定案件的後台人工補登資料）與 Orders Terms。
- 月嫂名冊以 `staff_id` 為選取中心，組合 Staff Profile、Staff Lifecycle、Staff qualification／preference read model 與 Staff Bank Account current owner。

名冊是 authenticated composition／presentation，不擁有任何 root fact。每一區塊獨立 Query、Preview、Confirm、Apply；
跨 owner 儲存不得假造 atomicity，UI 必須顯示各 owner 的結果與 fresh readback。

舊六來源 Data Browser 保留 bounded masked archive Query 作相容讀取，但不再是 canonical React 日常入口；
legacy raw table metadata 及 generic PATCH／source-correction 維持退役。`#data-browser` 相容深連結導向客戶名冊，
不得再呈現六來源 tab 或任意 table／column 編輯器。

## 2. Owner 路由

| UI 區塊／欄位 | 唯一 mutation owner | 名冊責任 |
|---|---|---|
| Client profile（管理端含 HCM email） | Client Profile | 只組合、送出 typed command、顯示 receipt／readback；申請人欄位依既有 allowlist |
| Client BeClass effective correction | Case Import | 保留 original row；只顯示 effective correction 與 lineage version |
| 預計服務日期、天數、時數、下廚、樓層費、服務時段 | Orders Terms | 直接重用既有 Orders Terms Q／P／A，不建立 proxy writer |
| Staff 個人／聯絡／行政資料 | Staff Profile | 不包含 lifecycle、qualification、preference 或 LINE identity |
| Staff active／retired | Staff Lifecycle | 重用既有 Staff Retirement Q／P／A |
| Staff 銀行帳戶 | Staff Bank Account | current account projection、version、immutable safe audit event |
| Staff qualification／preference／availability | 各既有 owner | 名冊只讀既有 typed projection；不混入 profile command |

## 3. 公開 HTTP 契約

### 3.1 客戶名冊

2026-10-13 人工授權試做 Excel 式表頭篩選第一版：下列新增唯讀契約同時適用清單分頁與訂單帳務匯出；不改 root facts、writer 或交易邊界。

- 清單與匯出新增 optional `column_filters` JSON array，每欄最多一筆 `{field, operator, values}`；欄位固定 allowlist 為案件編號、姓名、電話、地址辨識的行政區、BeClass effective 胎數、訂單狀態、保存的服務方式、下廚需求、服務天數、預計服務日期、訂金／第一期／第二期應繳日、客戶補助退還日及 Orders 保存的月嫂應付日。
- 不同欄位以 AND 組合；`in` 的值以 OR 組合，空陣列代表無符合資料。`not_in` 排除指定值，用於全選後取消部分勾選，避免只選取已載入的選項。`null` 表示空白，須與下廚明確 false 分開。文字提供 `contains`／`starts_with`／`equals`，天數及日期提供 `equals`／`gt`／`lt`／inclusive `between`，所有欄位提供 `blank`；欄位、operator、值型別及區間均須驗證，錯誤回 typed validation。
- 客戶義務日期只查與清單相同 direction／stage 的未取消保存義務；一案多筆時，包含／區間條件符合任一筆即納入，排除條件要求沒有任何被排除值。空白含缺少該義務或任一筆未登錄日期，不得因 join 重複案件列。補助退還日仍以清單 obligation 日期篩選，匯出報表日期來源維持原契約。
- `GET /api/v1/admin/registries/clients/filter-options?field=&search=&limit=&offset=`：與清單相同 reader 權限；從整份名冊的該 allowlisted 欄位取得 distinct nullable 字串值，提供搜尋與 `next_offset` 分頁，與畫面目前單頁筆數無關。選項搜尋只縮小候選清單，不自動改變勾選。
- React 表頭提供勾選／排除、全選／取消全選、條件輸入、日期本月／下個月快捷、確定／取消及清除此欄；按確定才更新清單並重回第一頁。保留既有四個排序欄位；已套用條件顯示漏斗與可移除摘要，提供清除全部篩選，匯出使用已成功套用的條件。沒有符合案件時仍可操作表頭篩選；選項載入失敗不得當成空白選項。第一版不包含儲存篩選組合或欄位配置。

- `GET /api/v1/admin/registries/clients?query=&multi_birth_count=&order_status=&requires_cooking=&sort_by=&sort_order=&limit=&after=&offset=`：bounded 案件 selector；新增條件皆 optional 且以 AND 組合。`multi_birth_count` 查詢唯一綁定 BeClass 的 effective `multi_birth_count`，僅接受 `單胞胎`／`雙胞胎`；`order_status` 精確匹配 Orders current status；`requires_cooking=false` 僅匹配明確 false，不得將 `NULL` 視為 false。排序僅接受 `case_no`、`customer_name`、`service_days`、`expected_start_date` 與 `asc`／`desc` allowlist。既有 `case_no` 升冪 cursor 保留供案件 selector 使用；唯讀清單以 `offset`／`next_offset` 支援所有 allowlisted 排序的上一頁、下一頁，`after` 與非零 `offset` 不得併用。
- `GET /api/v1/admin/registries/clients/{case_no}`：Client／BeClass／Order Terms composition readback。
- `GET /api/v1/admin/registries/clients/export/order-accounting`：依目前名冊篩選與排序匯出每案件一列的 XLSX；固定組合經核准的 HCM 八欄、Orders Terms、Client Finance 金額與日期，不提供任意欄位選擇，也不得因一對多 obligation／ledger join 重複案件列。
- `POST /api/v1/admin/registries/clients/{case_no}/profile/preview`
- `POST /api/v1/admin/registries/clients/{case_no}/profile/apply`
- `POST /api/v1/admin/registries/clients/{case_no}/beclass/preview`
- `POST /api/v1/admin/registries/clients/{case_no}/beclass/apply`

Orders Terms 修改固定使用既有 `/api/v1/orders/{case_no}/terms` Q／P／A。客戶名冊不得包裝第二個 Orders writer。

2026-10-13 人工裁決：Client-owned `phone` 為聯絡電話，可保存手機或含區碼的市話。

## 4. Query／Preview／Apply 與失敗語意

- Query 唯讀；Preview 零寫入；Apply fresh-lock owner state 並驗 expected version。
- profile／bank／BeClass correction 各自只有一個 aggregate version；正常 stale 回 `409` typed conflict。
- Apply 需要 `Idempotency-Key`、`X-Correlation-ID`、非空 reason 及 Preview 回傳的 fingerprint。
- same key／same command 回傳原 receipt；same key／different command 回 `409 idempotency_mismatch`。
- mutation commit 與 owner event／receipt／必要 outbox 在同一 outer UoW；readback 失敗不得否定已提交 receipt。
- UI 每次只儲存一個 owner section，避免宣稱跨 Domain atomicity。

待辦看板的案件處理可依 current HCM review 直接修改 Client Profile
可編輯欄位，包含電話及 Client-owned `service_type`，沿用上述 Preview／Apply、版本與稽核。
電話沿用既有驗證；LIFF applicant 的可修改欄位維持既有範圍。`service_type` 只保存
非空服務方式文字，去除前後空白後最多 100 字；2026-10-13 最新人工裁決：使用文字輸入，
保留原文、不轉換別名、不限制固定選項，owner 不提供服務方式下拉選單。此 Client 修改不重算
Orders 結束日、排班或帳務。保存後重新讀取正式 Client 資料及 current HCM review；
失敗或結果未確認不得在前端假解除警示。

Client BeClass original `beclass_records` 保持 immutable source evidence。Apply 只更新 Case Import-owned
effective correction state，保存 `before`、`after`、actor、reason、correlation、version 與 idempotency；
客戶名冊以 original 加 current correction overlay 顯示有效值。allowlist 固定為
`name`、`email`、`phone`、`tel`、`ext`、`city`、`zip_code`、`address`、`admin_notes`、
`multi_birth_count`。其中 `multi_birth_count` 僅接受 `單胞胎`／`雙胞胎`，作為案件 Payroll
費率分類及補助核銷單價的有效補正值；原始問卷內容不覆寫。Client Profile 的 `gender`、
`residence_type`、`delivery_type` 與此胎數欄位在後台使用 owner allowlist 提供的下拉選單。
Client Profile 的 `city`（畫面標示「縣市」）改為自由文字輸入，接受縣市、行政區名稱或其他文字，
不驗證固定縣市清單；去除前後空白後不可為空且最多 20 字。其他自由文字欄位維持文字輸入。

胎數 correction 只允許在正式服務開始前 Apply，同一交易同步已存在的 Client Finance 客戶應付、
正式指派 Payroll 月嫂應付與後續補助單價投影；雙胞胎固定每小時 450。未建立正式指派時不得要求
完整 Payroll facts；下游 root 合法不存在時只保存 effective correction，不要求先補齊預計服務開始日、
服務天數或建立帳務／薪資。之後 first-use bootstrap 必須優先採用已保存的 effective 胎數，而非舊問卷值。
同一正式指派反覆胎數補正時，未付款薪資義務依唯一 correction event 重建；已取消的舊義務保留歷史，
不再納入 current impact facts。既有 assignment frozen rate snapshot 不覆寫，有效補正仍由既有費率解析規則套用。
已有 root 的 partial pair、孤立財務歷史與正式指派缺必要 root 仍須阻擋並回滾。服務開始後胎數為財務鎖定欄位，
不得更正；BeClass 電話、地址、備註等非財務欄位仍可依原 Preview／Apply 流程修改。

任何既有訂單沒有 `bound_case_no` BeClass row 時，Query 必須提供 version `0` 的空白可編輯 effective view，
不得要求先匯入或顯示「尚未綁定 BeClass」。Preview 維持零寫入；首次 Apply 才建立
`record_origin='admin_manual'` 的空白來源容器，再以同一 correction state／event／receipt 保存人工補登值。
既有 BeClass row 預設及固定為 `imported`；不得把人工補登偽裝成匯入問卷。無對應訂單或同案多筆綁定時仍 fail closed。

## 7. UI 與入口

- sidebar 提供唯讀「客戶名冊清單」與既有可編輯「客戶名冊」、以及既有「月嫂名冊」。資料中心不再呈現六來源 Data Browser tab。
- 客戶名冊清單以同一個 client registry Query 顯示案件編號、每筆訂單虛擬帳號、客戶、電話、行政區、BeClass effective 胎數、服務天數、下廚需求、預計服務日期與訂單狀態；行政區只從 Client Profile 地址辨識東區、北區、香山區等既有支援行政區名稱；所有行政區套用相同規則，不採用縣市欄位或僅有路名的地址推測，無法辨識時清單欄位留白。展開案件後唯讀顯示 Client Profile、BeClass、訂單資訊、訂單條款及客戶帳務全部已知欄位，包含服務單價、總時數、客戶應付總額、訂金、第一期、第二期、已收、餘額與補助退還。篩選使用 BeClass 胎數、案件／訂單狀態及下廚需求，並由 server 執行；任何 allowlisted 排序皆須提供上一頁／下一頁，不得把符合案件截斷在前 100 筆。寬表格在頁面內使用 bounded vertical viewport，欄名固定於上方、橫向捲軸固定在表格可視區底部，不得要求使用者先捲到整份清單末端。頁面不得提供 owner mutation。
- 客戶名冊清單提供「匯出訂單帳務」按鈕，匯出目前已套用篩選的全部符合案件，不受畫面單頁 100 筆上限影響。HCM 固定欄位為項次、案件編號、姓名、身分資格、服務時間、預產期／預計服務開始月份、預計服務日期、雙胞胎；雙胞胎只輸出「是」／「否」。金額與日期使用 current typed owner projection，Excel 中金額、數量與日期保留可排序／加總的原生型別。補助返還金額直接沿用 Government Subsidy「補助案件統計表」同案的補助款金額，補助返還到期日以該投影的服務結束日套用既有補助返還日期規則；這兩欄是報表投影，不以是否已建立 `subsidy_return` 義務為前提。服務人員付款到期日優先取 Orders 固化日期；尚未固化時，以同一補助投影的服務結束日及 current Client Finance 客戶應付總額套用既有 Payroll 日期規則。
- 2026-10-13 人工裁決：客戶名冊另提供「案件資料檢查匯出」，保留原有訂單帳務匯出。`GET /api/v1/admin/registries/clients/export/case-inspection` 僅供 authenticated registry reader，沿用名冊 current filters 與排序取得全部符合案件，不受單頁限制。固定九個工作表：案件總覽（沿用既有 typed 帳務摘要）、案件保存資料（Client Profile／Orders／付款條件版本與保存值）、派案明細、每日排班、客戶義務、客戶收付流水、客戶款項分配、月嫂應付、月嫂付款分配。以 canonical `orders.case_no -> clients.id` 關聯，不以 `clients.case_no` 重建綁定；每份明細保留案件編號、客戶姓名、來源主鍵與關聯鍵，月嫂相關明細同時帶月嫂識別碼與姓名。一對多資料分工作表，不將流水、排班、派案相乘，不按 current status 丟棄取消、沖銷、被替換或非生效的已關聯資料。月嫂付款按 `staff_transfer_allocations -> staff_monthly_settlement_details.case_no` 歸屬案件，只輸出本案分配金額，不把整筆跨案件轉帳金額重複加總。僅固定欄位白名單 Query，不重算 root facts、不提供任意 table／欄位 selector、不寫入資料。姓名及既有帳務摘要所需虛擬帳號沿用既有查閱範圍；不匯出身分證、電話、住址、真實銀行帳號、憑證或 raw payload。金額、日期保留原生型別，案件編號為文字，DB 文字不得成為 Excel 公式；所有工作表即使無資料仍有欄名、篩選與固定表頭。
- 客戶以案件編號／姓名／電話搜尋；月嫂以人員 selector 搜尋。
- 「名冊資料」案件 selector 必須依 `case_no` cursor 讀完所有頁次；搜尋同樣讀完全部符合結果，不得讓單頁 `limit` 截斷可選案件。
- 選取後才載入 detail；每個 owner section提供編輯、取消、儲存，Preview 後需明確確認才 Apply。
- 欄位顯示 owner；不可編輯原因、validation、conflict、partial owner result 與 commit/readback 狀態不得隱藏。
- 銀行帳號於月嫂名冊清單／詳情直接展示完整帳號（無完整帳號時回退至末四碼）；replace 時輸入新完整值，送出後清空，不保留在 browser state 或錯誤文字。
- Apply 成功後重新 Query，以 server readback 取代 client draft。

## 8. Persistence 與 migration

repository-local schema 只採 additive migration，提供 Client admin change、BeClass correction、Staff Profile、
Staff Bank Account 的 version／immutable event／apply receipt。不得 backfill 推測值、不得更新歷史 event、
不得刪除 legacy source table。fresh bootstrap、preserve-data plan 與 fixture reset分別驗證；production apply／switch
固定 `NOT_RUN`，除非另有人工 Authority。

`beclass_records.record_origin` 為 additive source-lineage 欄位，允許值僅 `imported`／`admin_manual`；
既有資料以 schema default 保持 `imported`，不做業務內容回填。

## 9. 不回溯保護

下列資料固定不可因名冊修改而原地改寫：已簽發／已確認契約、已付款／已匯出薪資、ledger／payment snapshot、
已完成 assignment／schedule、歷史 event／receipt／audit、original BeClass evidence、已送出 LINE 訊息。
Order Terms 若使契約 currentness 失效，只能形成「需重新產生／換版／重新確認」的 owner狀態或後續工作；
不得背景覆寫舊契約。

## 10. 驗收

1. `case_no` detail 正確組合 Client、唯一 BeClass effective view（含所有無 BeClass 訂單的人工補登 view）與 current Order Terms；missing／binding ambiguity fail closed。
2. Staff detail 正確組合 profile 與全部 active／inactive masked銀行帳戶；list／detail皆不洩漏完整帳號。
3. 四個新增 owner mutation皆通過 validation、zero-write Preview、fresh version、typed conflict、idempotency、safe receipt及fresh readback。
4. 後台與 LINE 的 Orders Terms 修改共用同一 `OrderTermsApplication`；無 UI／route／adapter raw SQL旁路。
5. M3-03 驗證目前 Order Terms、Orders／Scheduling／Matching／Finance／Payroll／Lifecycle依既有 workflow 更新，且歷史契約不被覆寫。
6. React desktop及窄畫面實際驗證兩名冊的搜尋、選取、編輯、取消、Preview／Confirm／Apply、錯誤與遮罩狀態。
7. Static、owner module、跨 owner integration、concurrency/idempotency、安全輸出、migration contract及 `git diff --check`通過。
8. DB gate明確回報 `PASS | BLOCKED | NOT_RUN`；production migration／deployment未授權時不得冒充完成。
