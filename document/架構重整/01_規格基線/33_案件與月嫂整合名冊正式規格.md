# 案件與月嫂整合名冊正式規格

## 1. 文件邊界與所有權

- 狀態：`current-spec`
- Owner：Admin Registry Composition（Clients／Staff Roster）
- 單一負責範圍：管理端「客戶名冊」（以 `case_no` 為中心）與「月嫂名冊」（以 `staff_id` 為中心）的跨 owner 唯讀投影組合、Excel 表頭篩選與匯出契約、電話正規化、root 永久刪除案件邊界、欄位可編輯／唯讀能力、BeClass 補登／照護／退款帳號連動與月嫂完整銀行帳號顯示規則。
- 關聯引用：見 [Global 共同契約](00_Global_共同契約.md)、[Client Finance Domain](04_Client_Finance_Domain.md)、[Global Migration 與 Cutover](10_Global_保留資料Migration與Cutover_Subsystem.md)、[Case Import 與非市民待審](17B_Case_Import與非市民Redis待審正式規格.md)、[Global Entry Point Governance](19_Global_Entry_Point_Governance.md)、[LINE 客服與月嫂自助服務](20_LINE客服與月嫂自助服務正式規格.md)、[銀行流水對帳與手動補登](22_銀行流水匯入與帳務異常處理正式規格.md)、[Staff Roster Case Preference Read Model](24A_Staff_Roster_Case_Preference_Read_Model正式補充契約.md)、[歷史訂單生命週期與服務天數帳務正式規格](27_歷史訂單生命週期與服務天數帳務正式規格.md)

名冊只是 authenticated composition／presentation，不擁有任何 root fact。每一區塊獨立呼叫對應 owner Query／Preview／Apply；跨 owner 儲存不得假造 atomicity，UI 必須明確顯示各 owner 結果與 fresh readback。

## 2. Owner 路由矩陣

| UI 區塊／欄位 | 唯一 mutation owner | 名冊責任 |
|---|---|---|
| Client profile（含 `clients.email`） | Client Profile | 組合、送出 typed command、顯示 receipt／readback |
| Client BeClass effective correction（含退款帳戶、照護） | Case Import | 保留原始問卷；僅寫 effective correction Overlay |
| 預計服務日期、天數、時數、下廚、樓層費、服務時段 | Orders Terms | 直接重用 `/api/v1/orders/{case_no}/terms` Q/P/A |
| 取消後受控重開 | Orders | 具 `system.administration` 的操作者從客戶清單開啟「訂單取消」案件，於詳情上方操作「重開訂單」。重用 Orders Preview／Apply，完成後回讀詳情、變更歷程與清單狀態。 |
| 歷史訂單實際服務天數 | Orders / Historical Accounting | 於案件詳情帳務區原地操作（見 [規格 27](27_歷史訂單生命週期與服務天數帳務正式規格.md)） |
| Staff 個人／聯絡／行政註記／`union_no` | Staff Profile | 不混入 lifecycle、資格或 LINE identity |
| Staff active／retired | Staff Lifecycle | 重用 Staff Retirement Q/P/A（無永久刪除） |
| Staff 銀行帳戶 | Staff Bank Account | `add`、`replace`、`deactivate`、`set_primary` |
| Staff 專業資格／接案條件／不可服務期間 | 各既有 owner | 名冊依各 owner Q/P/A 或唯讀投影組合 |

## 3. Root 案件永久刪除（RD-1）

- **權限**：僅已登入、enabled、具持久化 ID 且 `is_root=true` 之帳號可 Query 刪除資格及 Apply（透過 `/api/v1/admin/auth/me` 回讀確認）。月嫂名冊**不提供**永久刪除（僅保留退役／復職）。
- **簽約狀態**：未簽回、已有月嫂或客戶簽回（`contract_signing_events.signed_received`，含非 current plan）及已完成簽約（`order_contract_flow_events.contract_completed`）的案件適用同一永久刪除流程。
- **原子刪除範圍**：同一 outer UoW 內沿 canonical case/client identity 與 inbound FK 刪除該案配對、排班／占用、帳務、匯入綁定、簽約及其他歷程、收據、待處理任務、獨佔 Client 及 LINE／附件之 case-owned metadata。共用 Client、月嫂、共用銀行批次及 NAS 實體檔案保留，外部 LINE 訊息不撤回。現行 price-event／obligation-source cycles 僅於待刪列解除 nullable 指標。歷程 trigger 例外要求有效的 `registry_delete/v1` pending claim 與同案資料歸屬。NAS 固定程序沿用 `lu_nas_delete_unsigned_case_v2` 識別碼。
- **端點與 UI**：`GET /api/v1/admin/registries/clients/{case_no}/deletion`、`POST /api/v1/admin/registries/clients/{case_no}/deletion/apply`（401/403 零寫入、404 不存在、409 conflict／`registry_deletion_guard_rejected`）。UI 明示刪除後果，收到成功 receipt 才關閉抽屜移除案件列；結果未明鎖住離頁以原鍵核對。

## 4. 公開 HTTP 契約

### 4.1 客戶名冊與匯出

- `GET /api/v1/admin/registries/clients`（支援 `query`、`multi_birth_count`、`order_status`、`requires_cooking`、`sort_by`、`sort_order`、`limit`、`after`、`offset`、`column_filters`）：`after` 與非零 `offset` 不得併用；排序 allowlist 為 `case_no`、`customer_name`、`service_days`、`expected_start_date`；接受 A 開頭非市民案號。
- `column_filters`（JSON array，每欄至多一筆 `{field, operator, values}`）：allowlist 涵蓋案件編號、姓名、補助身分、電話、地址行政區、BeClass effective 胎數、訂單狀態、服務方式、下廚、天數、預計服務日期、訂金／一二期／補助退還日、月嫂應付日。不同欄位 AND、`in` OR、`not_in` 排除、`null` 表空白（與 `requires_cooking=false` 分離），支援 `contains`／`starts_with`／`equals`／`gt`／`lt`／`between`／`blank`；多筆義務不因 join 重複案件列。
- 訂單帳務 XLSX 的付款到期日讀 Orders 已保存的月嫂應付日，付款日期試算另列「服務人員預估付款日」。客戶名冊清單呈現「月嫂義務應付日」與「客戶補助退還日」，逐筆讀有效的正式義務。訂單層月嫂應付日保留於資料及既有 API，名冊清單移除該欄及其篩選控制。名冊案件帳務摘要與對帳工作台共用單案帳務查詢，呈現月嫂應付及依方案決定對象的補助給付，補助估算明示為預估。
- 名冊的「薪資預估日期」只顯示自費薪資時程，以實際服務結束日的次月 15 日估算，缺實際日期時使用預定結束日，無須正式排班。已取消或缺服務結束日留空。估算獨立呈現，不代填正式日期或納入其篩選。
- 名冊「月嫂義務應付日」有正式來源分期時，逐筆顯示正額分期的撥款日，與銀行按來源月份配對使用的日期一致。同一義務在同一天的分期只顯示一次。
- 名冊與訂單帳務 XLSX 共用補助預計申請年月。使用實際服務結束日，尚無實際日期時使用預定服務結束日。已取消且無實際結束日、非適用身分或無可用結束日時留空。此欄供安排送件，不代表正式送件。
- `GET /api/v1/admin/registries/clients/filter-options?field=&search=&limit=&offset=`：從全名冊該 allowlisted 欄位取 distinct nullable 值。
- `GET /api/v1/admin/registries/clients/{case_no}`：Client／BeClass／Order Terms／唯讀帳務 composition readback。
- `GET /api/v1/admin/registries/clients/export/order-accounting`：依名冊目前篩選與排序匯出每案一列 XLSX（基本八欄＋Orders Terms＋Client Finance／補助投影金額與日期，原生數值日期型別）。「胎數」與名冊共用 BeClass 有效值，只輸出「單胞胎」或「雙胞胎」，未確認時留空。
- `GET /api/v1/admin/registries/clients/export/case-inspection`：依名冊目前篩選與排序匯出九工作表案件資料檢查 XLSX（案件總覽、保存資料、派案、排班、客戶義務、收付流水、款項分配、月嫂應付、月嫂付款分配，以 `orders.case_no -> clients.id` 關聯；不匯出身分證、電話、住址、真實銀行帳號、憑證或 raw payload，文字不為公式）。
- `POST /api/v1/admin/registries/clients/{case_no}/profile/preview`、`POST /api/v1/admin/registries/clients/{case_no}/profile/apply`、`POST /api/v1/admin/registries/clients/{case_no}/beclass/preview` 與 `POST /api/v1/admin/registries/clients/{case_no}/beclass/apply`（客戶主檔沿用 `client_profile_version` 與 Client-owned event／receipt 保護並行更新）。

### 4.2 月嫂名冊與公會編號

- **名冊履歷操作**：月嫂名冊只提供履歷 PDF 選檔、上傳、版本查詢與 authenticated download，不提供名冊內嵌履歷預覽或預覽關閉入口。上傳沿既有受控檔案 staging／Preview／Apply 保存驗證，不構成人工檔案預覽。客戶確認資訊預覽及正式履歷寄送沿 [媒合規格](02A_媒合候選池與客戶決定及通勤規格.md#32-客戶推薦確認手動更正與服務前整案換人r-04)，不因名冊預覽退役而放寬缺檔或寄送條件。

- `GET /api/v1/staff/roster`（`data_browser.read` 權限，200 人上限 cursor Query，支援 `lifecycle_state=active|retired`）：固定 10 次批次 Query 取得完整 Profile、銀行帳戶、`care_babies` 與七個 canonical relation（含 `cooking_skills`），不逐人發請求，不輸出 LINE User ID、IP 或 credentials。主頁分「現役月嫂／已退役月嫂」分頁；全名冊讀完 bounded cursor 後依 `union_no` 自然升冪排序（例如 A2 在 A10 前，未設定排後、同序依 `staff_id` 升冪）。
- `GET /api/v1/staff/summaries`（支援 `lifecycle_state=active|retired`）：供下拉／排班 selector；管理端所有可由 canonical Staff id 識別之月嫂顯示統一為「公會編號 姓名」（未設定顯示「未設定 姓名」）。
- `staff.union_no`：Staff Profile-owned `VARCHAR(50)`（nullable，去除前後空白，保留前導零，`utf8mb4_0900_bin` 唯一索引 `uq_staff_union_no`，碰撞回 `409 staff_union_no_collision`，1213 死鎖回 `409 staff_profile_concurrent_conflict` 不自動重試）。
- `GET /api/v1/staff/{staff_id}/profile`（含 `profile_version`、`bank_accounts_version`）、`POST /api/v1/staff/{staff_id}/profile/preview`、`POST /api/v1/staff/{staff_id}/profile/apply`、`POST /api/v1/staff/{staff_id}/bank-accounts/preview`、`POST /api/v1/staff/{staff_id}/bank-accounts/apply`、`GET /api/v1/staff/{staff_id}/qualification-editing`、`POST /api/v1/staff/{staff_id}/qualification-editing/preview` 與 `POST /api/v1/staff/{staff_id}/qualification-editing/apply`。
- Staff Profile allowlist：`union_no`、`name`、`identity_card`、`phone`、`tel`、`tel_ext`、`email`、`birthday`、`city`、`zip_code`、`address`、`education`、`emergency_contact_name`、`emergency_contact_phone`、`admin_notes`。Bank command 限 `add`、`replace`、`deactivate`、`set_primary`（同 Staff 至多 20 筆、至少一筆 active primary、不可跨 Staff 共用）。

## 5. 互動模式、Client Profile 與 BeClass Correction

### 5.1 一次點擊送出與選填備註（`CRX-ACCOUNT-04`）

管理端客戶主檔、BeClass 報名／照護／退款帳戶、月嫂個資、銀行、專業資格、接案條件、不可服務期間與退役／復職一律採一次點擊儲存（見 [Global 共同契約](00_Global_共同契約.md) §2.4），客戶／月嫂一般資料異動「備註（選填）」省略時傳空字串；銀行帳戶、人事狀態、不可服務期間與申請審核依各自必填原因契約。`staff_qualification_editing/v1` 使用五欄（`special_skills`、`has_massage_cert`、`certifications`、`care_babies`、`transportation`）canonical snapshot fingerprint 防 stale 409；版本衝突要求重讀、結果未明沿同鍵核對而不 blind retry，正式回讀成功後才更新名冊並保留各區草稿與離頁保護。

### 5.2 Client Profile 與 BeClass 欄位及照護修正（`CRX-ACCOUNT-01`）

- **身分證字號與三節假日雙薪意願（`CRX-REGISTRATION-01`）**：客戶主檔區塊顯示並維護身分證字號；BeClass 區塊顯示並維護三節假日雙薪意願。具名 typed 欄位 `id_number`、`holiday_double_pay` 分別取自本案唯一綁定問卷的 `身分證字號`、`三節假日是否願意支付雙倍薪水` 及既有 BeClass 有效修正。沿用 Case Import 的 BeClass version／Preview／Apply／correction state，不新增 Client 儲存欄位或修改原問卷。
  - 身分證選填。非空值沿既有登記規則正規化為 ASCII 大寫英文字母加九碼數字。雙薪意願只接受「是」、「否」或未填。兩欄的未知或非法來源皆顯示未填。明確清空後以 NULL 為準，不得回落原問卷舊值。兩欄只寫入既有 BeClass 修正紀錄，不觸發財務同步。雙薪意願只作紀錄，法定假日費率、補助、應收應付、薪資及財務帳本均不採用此值。
  - 客戶主檔「儲存」依實際差異組合原 Client Profile 與身分證的 BeClass 操作；只有身分證變更時不提交空白主檔命令。兩個 owner 各自保存與正式回讀，不能宣稱跨 owner 原子交易。前項已成功而後項失敗時保留已保存結果與未完成草稿，不重送已成功項；身分證、報名及照護共用 BeClass version，每次保存後更新版本並使舊預覽失效。取消主檔草稿一併取消身分證草稿，不清掉報名或照護草稿。
  - 單案身分證顯示沿既有 authenticated registry reader 邊界，完整值限必要的單案維護 Query／表單，回應使用 `Cache-Control: no-store`。一般清單、既有匯出、變更歷程、錯誤、日誌、預覽／儲存回執與事件不新增完整證號；非必要的前後值輸出須去敏。寫入仍須 `data_browser.write`。月嫂沿用既有 `identity_card` 清單與詳情欄位及 Staff Profile writer，不新增第二個身分證入口。
- **基本資料單一修改入口（`CRX-PROFILE-01`）**：姓名、電話、Email、縣市、地址只在「客戶主檔」區塊顯示與編輯，不再於 BeClass 區塊提供第二組輸入。各欄以客戶主檔非空白值為準；主檔為 NULL、空字串或純空白時，才採用本案唯一綁定之 BeClass 有效非空白值。無來源或綁定異常不猜配。Email 統一標示「Email」。BeClass 專屬市話、分機、郵遞區號、報名註記、胎數與退款欄位沿原區塊維護。
- **補值與儲存**：查閱、開啟、取消變更與回讀只組合上述有效值，不因帶入來源值自動寫入或製造未存草稿。使用者儲存客戶主檔時，將目前欄位及採用的補值相對於正式主檔的差異，一次送往既有 Client Profile Preview／Apply，沿用主檔 version、驗證、事件、receipt 與正式回讀。BeClass 原始紀錄與已保存修正保留來源用途，不雙寫或批次覆蓋。姓名、電話、Email 等主檔欄位沿原驗證拒絕空值，不能因空白採用來源規則宣稱可清空；只有原契約允許清空的行政註記維持可清空。驗證拒絕時不 Apply、不顯示儲存成功，保留草稿供修正。
- **電話規則**：`clients.phone` 保存手機或含區碼市話（去除空白括號連字號，`+886`/`886` 轉 `0`；手機 `09` 開頭 10 碼，市話 `02`–`08` 開頭 9–10 碼），採用的 BeClass 電話也須通過同一 Client Profile 驗證。
- **Email 與服務方式**：HCM 匯入僅可補入空白主檔 email；`clients.service_type` 採自由文字輸入（≤100 字，不設固定下拉）；`clients.city` 自由文字（≤20 字）。單一入口採用的來源值沿主檔原驗證，不因來源為 BeClass 放寬限制。
- **BeClass Correction（含 13 項照護／約定與未綁定補登）**：原 `beclass_records` 永久唯讀；無 `bound_case_no` BeClass 列之訂單 Query 提供 `version=0` 空白可編輯 view，首次 Apply 建立 `record_origin='admin_manual'` 容器（同案多筆綁定拒絕，不以姓名、電話或 `query_no` 猜配）。
  - **樓層文字**：服務樓層方式僅保存文字協調紀錄，不觸發金額重算；實際樓層費改於 Orders Terms 輸入。
  - **胎數**：`multi_birth_count`（`單胞胎`/`雙胞胎`）僅允許正式服務開始前修改並同交易同步 Client Finance、Payroll 與補助單價（雙胞胎固定 450）；服務開始後財務鎖定。
  - **舊欄位與單一胎數來源（`CRX-BIRTH-01`）**：原「寶寶資訊」`clients.baby_info` 是保留的相容欄位，不再作為獨立自由文字資料或第二個胎數修改入口。一般 Client Profile mutation 拒絕修改此欄，Query 保留既有值並標為唯讀，不改寫或刪除歷史資料；HCM 主檔補件不再提供舊「寶寶資訊」輸入。名冊顯示與修改只使用 BeClass 有效 `multi_birth_count`，值限「單胞胎」或「雙胞胎」，不以舊 `baby_info` 覆蓋有效胎數或繞過費率連動。新案表單只帶入有效的單胞胎／雙胞胎選項；舊自由文字或無效值保持未選，須由承辦人選擇，不猜測第幾胎。
  - **歷程與換人**：案件抽屜最下方顯示預設收合的變更歷程；倒數第二區「服務月嫂」依 Scheduling Assignment Plan Query 顯示分段並提供「換人」／接任流程分流（已服務轉介代班，未服務走 successor matching round）。

### 5.3 客戶名冊欄位權威、唯讀邊界與退款帳戶連動

| ID | 欄位／區塊 | 正式來源與編輯規則 |
|---|---|---|
| `CRX-01` | 補助身分 | 讀取 `clients.identity_status`。管理端只可將尚未開始服務的補助市民或原住民改為一般市民。同一交易重算客戶應付、月嫂薪資與補助。既有收退款、結算與補助核銷保留原紀錄，差額沿各帳務 owner 的更正流程處理。其餘情況唯讀，案號沿用。 |
| `CRX-02` | 計價身分與補助上限 | 獨立於 `CRX-01`，讀取本案綁定政策／個案計價與版本 |
| `CRX-03` | 退款銀行／分行／帳號 | 讀寫唯一綁定之 BeClass 有效修正（7 碼 `refund_bank_code`＋保留前導零 `refund_account_no`）；缺件標「待補」 |
| `CRX-04` | 生日 | 唯讀讀取 `beclass_records.birth_date`（缺值顯示「尚未登錄」） |
| `CRX-05` | 備註與行政註記 | `clients.notes`（Client Profile 編輯）、`clients.admin_notes`（獨立，由管理端 Client Profile 編輯，可清空）、BeClass `admin_notes`（BeClass 編輯）三者分開不互填 |
| `CRX-06` | 案件日期摘要 | 預計與實際起訖唯讀讀取 Orders 正式值（與排班區段分開）；修改走原 Orders 入口 |
| `CRX-07` | 三方案、免自備與退款摘要 | 唯讀組合案件帳務共用 typed Query；不在此設定方案或改義務金額／日期 |

- **目前進件欄位問題（`CRX-IMPORT-FIELD-01`）**。Client Registry Detail 回傳 `import_field_issues`，以 Case Import 的唯讀共同 Query 合併 current HCM 及成功 Client BeClass 欄位警示。每項提供來源、正式 owner、正式欄位 key、來源欄名、issue code 與去敏白話原因。名冊以紅底與可讀原因標出該正式欄位，不新增另一份待辦狀態。Email／縣市沿 `CRX-PROFILE-01` 唯一主檔入口；銀行與帳號沿 `CRX-03` 各自修改。保存後以 fresh Query 逐欄消除已合法或已依契約略過的警示，其他欄位保持；讀取失敗顯示錯誤，不宣稱無問題。生日與建檔時間仍沿原唯讀邊界。
- **退款快照自動連動（`CRX-ACCOUNT-02`）**：一般退款與補助退款共用同一有效帳戶來源，正式退款建立時保存收款快照；透過客戶名冊 BeClass 抽屜補登退款帳戶儲存時，同一 UoW 自動連動 Client Finance `sync_refund_recipient_snapshots`，為該案尚無快照的 open 退款義務補登不可變快照（`source_kind='beclass_correction_supplement'`），不覆寫已有快照。
- **案件退款帳號顯示（`CRX-ACCOUNT-03`）**。具名冊編輯權限（`data_browser.write`）的承辦人可在案件詳細資料及案件帳務核對畫面直接看見 BeClass 有效完整退款帳號，以文字保留前導零。這些單案畫面經同一授權查詢取得完整值，回應使用 `Cache-Control: no-store`。一般查閱、唯讀人員、變更歷程、回執、日誌、錯誤與既有匯出沿用遮蔽及去敏規則。
- **表格操作（`CRX-SCROLL-01`）**：寬表格使用 bounded vertical viewport 並將水平捲軸固定於表格可視區底部，表頭與資料同步對齊。
- **非市民審核與待審問卷邊界**：待審問卷核准前不進 MySQL（滿 14 天清除，見 [Case Import 與非市民待審](17B_Case_Import與非市民Redis待審正式規格.md)）；核准後 A 開頭案件可於名冊搜尋、查看與匯出。

## 6. 月嫂銀行帳戶顯示契約

- **管理端查閱**：Staff Profile Query 與月嫂名冊清單／詳情支援讀取並展示月嫂銀行完整帳號 `account_no`（無完整帳號時向下相容顯示 `account_last4`）。新增、更換帳戶時直接顯示輸入的帳號，送出後清空 browser state。
- **稽核去敏**：bank event、receipt、一般 log、錯誤訊息與匯出不保存或輸出完整帳號（bank event 僅保存 `last4`）；`deactivate` primary 前須已有或同命令指定另一筆 active primary。現行投影僅影響未固定之未來付款 Query，不回寫歷史 payout snapshot。

## 7. Persistence、不回溯保護與驗收標準

### 7.1 Schema 與不回溯保護

- `beclass_records.record_origin` 僅允許 `imported`／`admin_manual`。DB 變更與執行門依 [Global Migration 與 Cutover §6](10_Global_保留資料Migration與Cutover_Subsystem.md)。
- 下列事實固定不可因名冊修改原地改寫：已簽發／確認契約、已付款／匯出薪資、ledger／payment snapshot、已完成 assignment／schedule、歷史 event／receipt／audit、original BeClass evidence、已送出 LINE 訊息。Orders Terms 使契約失效時僅形成需換版或重確認狀態。

### 7.2 驗收標準

1. `case_no` detail 正確組合 Client、唯一 BeClass effective view（含無綁定案件之 `admin_manual` view）與 Order Terms；`CRX-01`～`07` 唯讀與編輯邊界嚴格一致；補助退款補登帳戶後正確連動產生 `beclass_correction_supplement` 快照。
2. 月嫂名冊完整展示 Staff Profile（`union_no` 自然排序）、完整銀行帳號 `account_no`（無完整帳號時向下相容顯示 `account_last4`）與資格能力投影。客戶案件詳細資料以具備與欠缺名冊編輯權限的帳號驗證完整值、前導零及遮蔽，並驗證一般查詢、匯出與事件維持去敏。
   - S：月嫂已有或尚未上傳履歷 PDF。T：管理履歷檔案。A：在名冊選取 PDF、上傳及下載目前版本。R：選檔不開啟內嵌預覽或額外預覽請求；上傳與下載沿既有受控檔案契約，未出現履歷預覽或關閉預覽入口，客戶確認及正式寄送的履歷驗證保持有效。
3. 所有 owner mutation 通過 zero-write Preview、fresh version／snapshot fingerprint、typed 409 conflict、idempotency replay、safe receipt 與 fresh readback。RD-1 驗收如下。
   - S：案件未簽回、已有月嫂或客戶簽回，或已完成簽約。T：root 永久刪除指定案件。A：讀取 Preview 後以相同案件及版本確認 Apply，再以同一操作鍵重試。R：該案及其所屬資料消失，共用 Client、其他案件與月嫂保留，並重播原成功收據。
   - S：登入者非 root、版本已變更，或資料庫刪除範圍缺少同案 pending claim。T：嘗試永久刪除。A：呼叫 Apply，或以不符觸發器要求的資料庫刪除上下文刪除歷程。R：操作遭拒，原資料保留，未新增成功收據。
4. React desktop 與窄畫面實際驗證表頭篩選、底部水平捲動、各區草稿與結果未明離頁保護、換人分流與取消結算入口。
5. `CRX-PROFILE-01` 基本資料單一入口驗收如下。
   - S：客戶主檔與本案 BeClass 姓名、電話、Email、縣市或地址不同，部分主檔值空白。T：承辦人維護一份基本資料。A：開啟案件詳情，在客戶主檔修改或直接儲存採用的補值，再正式回讀。R：每欄只有一個編輯入口，非空主檔優先、空白採用有效 BeClass 值；開啟不產生未存變更，儲存只呼叫 Client Profile writer，回讀保留儲存值與原始報名來源。
   - S：本案無 BeClass 來源、綁定異常、來源欄位空白，或主檔儲存版本已過期／結果未明。T：維護基本資料並保留其他區塊草稿。A：開啟、編輯及儲存客戶主檔。R：不猜配、不提交隱藏 BeClass 基本欄位、不雙寫；版本衝突及結果未明沿原處理，不顯示假成功，BeClass 專屬與照護欄位仍可獨立維護。
6. `CRX-BIRTH-01` 胎數與舊欄位驗收如下。
   - S：既有案件保留舊 `baby_info` 文字，BeClass 有效胎數為單胞胎或雙胞胎。T：承辦人查閱並維護胎數。A：開啟名冊詳情，於服務開始前修改胎數、儲存並重新開啟。R：只出現有效胎數的單一閉鎖選單，沿 BeClass correction writer 保存與回讀，保留財務連動及版本保護；舊文字未獨立顯示不構成欄位遺漏，原值與原問卷保留。
   - S：嘗試由一般主檔修改 `baby_info`、提交非單胞胎／雙胞胎的胎數，或在服務開始後更改胎數。T：嘗試儲存胎數。A：呼叫對應 Preview／Apply 或操作表單。R：舊欄位修改與非法胎數遭 typed 驗證拒絕且零寫入；已開始服務沿原財務鎖拒絕，無第二個主檔入口可繞過。
   - S：Email 已有非空值，或新案來源只保留無效的舊寶寶資訊文字。T：清空 Email，或帶入來源案建立新案。A：送出空 Email，或開啟新案胎數選單。R：前者沿正式 Client Profile 驗證拒絕、不 Apply 且保留草稿；後者不把舊文字當有效選項，須重新選擇單胞胎／雙胞胎。
7. `CRX-REGISTRATION-01` 身分證字號與意願紀錄驗收如下。
   - S：本案唯一綁定問卷已有身分證字號及雙薪意願，或案件尚無問卷而允許人工補登。T：承辦人維護客戶資料。A：在客戶主檔修改證號，在 BeClass 將雙薪意願改為是、否及未填，各次儲存後重新開啟並回讀。R：各欄只有一個輸入入口，重開後顯示儲存值，清空後保持空值；原問卷保留，Client 主檔沒有第二份證號。意願各值不參與帳務計算，保存不觸發財務同步。
   - S：身分證格式不符、送出非法意願值、來源綁定異常、版本已變或儲存回應遺失。T：嘗試修改及確認儲存結果。A：操作表單及原 Preview／Apply，並重試同一筆結果核對。R：驗證及版本衝突 typed 拒絕且不產生成功收據；草稿保留，結果未明鎖住離頁，重試不重複保存，其他主檔／報名／照護草稿不遺失；非必要輸出無完整證號。
   - S：月嫂已有個人資料。T：承辦人維護月嫂身分證。A：沿既有詳情欄修改、儲存並重新查詢。R：Staff Profile version／Preview／Apply／回讀一致，清單及詳情顯示更新值，沒有新增重複欄位。
