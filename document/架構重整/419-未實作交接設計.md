## DS-01｜已簽 PDF 歸檔逾時（原交接設計）

[PR #447](https://github.com/chrishzc/Labor_union/pull/447) 已完成同一瀏覽器分頁內按原操作識別查回歸檔回執。本案不重做 DS-01。以下保留拆案時的提案，不作為現行操作或 API 文件。

- **PM｜要什麼、為什麼**：POST 逾時不代表歸檔失敗。先確認原操作是否已完成，避免再次送出，且不能把舊檔誤認成本次結果。
- **前端｜畫面與動作**：[ContractExternalSigningActions](../../ui_react/src/components/ContractExternalSigningActions.tsx) 的「重新確認歸檔結果」目前在同頁使用原檔與原操作識別重送 POST；重新開頁才 GET。目標是先唯讀查詢。已證實是同操作的正式結果才顯示已歸檔；如果暫時查不到，顯示「結果待確認」，不自動重送或換鍵。若正式讀回仍無法辨認，允許使用者明確選擇用原操作者、原案、原檔及同鍵重送；不能只比對檔名。
- **後端｜API 與第一個待決契約**：Contract Signing 擁有歸檔。現有 `GET /api/v1/orders/{case_no}/contract-external-signing/signed-archive` 回 `data.staff_segments` 和 `data.files`，可看同案最後歸檔，但不是按操作鍵查回執。先確認是否有足以唯一對上原操作的正式關聯，否則由後端提出帶原操作識別的唯讀契約，再給前端接線。沒有可靠關聯前不能把 GET 查到任何舊檔當這次成功。不可在前端自行用檔名拼湊。
- **DB｜資料與責任**：先重用 `contract_signing_command_receipts` 的 `idempotency_key` 與 `result_snapshot.files`，按原案和權限讀取；現有唯一鍵、交易與回滾邊界不改。本提案不預設新增欄位、表或遷移。
- **驗收**：S 已有一組檔名相同的舊歸檔，本次新 POST 成功提交但回應遺失；T 查原操作；A 點重新確認；R 先做唯讀查詢，只有識別吻合才顯示本次成功，而且不送第二個 POST。負例：查到舊檔或無法證明同操作時不得顯示成功；若手動用原命令重送，後端仍只保留一筆正式回執。驗 UI 時重用既有 `contract_external_signing_actions.test.tsx`；只有變更正式查詢或資料契約才補對應 API／DB 驗證。

## DS-02｜歷史月嫂款同步結果不明的畫面

- **PM｜要什麼、為什麼**：查不到正式結果時要能先查，不把未知當失敗、成功或要求再次寫入。已建帳未定付款日及待核對須保留原意。
- **前端｜目前與目標**：[HistoricalPayableReview](../../ui_react/src/components/HistoricalPayableReview.tsx) **修正前已**讀同步回應的多人 `items`，也會逐筆用正式應付回讀。未取得回執或查詢失敗時會提示重新查核，但該畫面主要按鈕仍是「同步月嫂應付」。本案只改善這個未知結果狀態：候選提供明確的唯讀「重新查核」動作，查同案同人；不自動或以同一按鈕重送 POST。已實作的逐人讀回不重做。
- **後端｜沿用契約**：應付清冊 GET `/api/v1/finance-reports/accounts-payable/historical-lookup` 用 `keyword`、`target_month` 定位，核對相同 `case_no` 與人員。若本期查核未涵蓋未定日期的項目，重用 [`financeAccountingClient.query(caseNo)`](../../ui_react/src/api/finance_import/finance_accounting_client.ts) 的 `GET /api/v1/finance-import/cases/{case_no}/accounting`，驗 `data.case_no`，再讀 `data.staff_accounting_availability`。依有證據的 `staff_id`／`assignment_id` 找各人，只有狀態為 `formal` 且能以 `obligation_identities` 對上 `data.staff_items` 的 `identity` 及 `direction=payable` 才顯示該筆 `expected_ntd`；`due_date=null` 表示日期未定。多人逐人處理，不合併同名、不拿 `estimated_amount_ntd` 當正式金額；同一識別無法唯一對應時留待確認，不用未列入清冊推論未建帳。正式建帳由 Payroll 負責；POST 不接外部重送鍵，不把再次同步說成讀回同一命令。沒有證據顯示必須新增 API。
- **前後端｜整包回應遺失時的識別**：同步仍是案號層級，不提交月嫂或指派 ID。從清冊逐人處理入口開啟畫面時，保留原選取列的 `case_no` 和 `staff_id`；不要等同步回應才取識別。以既有同案 accounting GET 的 `staff_accounting_availability` 核對所選 `staff_id`，只有單一可辨認的 `assignment_id` 且能唯一連到正式 payable 項目，才顯示該人的正式金額及原付款日；沒有月嫂 ID、同人有多筆無法區分的指派、義務關聯重複或查詢失敗，都保留待確認。若保留了原查詢月份，可用清冊查回原結果；月份缺失不猜測，單案查核可直接走 accounting GET。成功回應下原有多人 `items` 不改；回應遺失時，不替原命令重造多人明細，也不以查到現有正式應付宣稱本次同步成功。驗收另加：甲乙同名只顯示原所選 ID 唯一對應的正式應付；未唯一對上不得顯示旁人的金額、改資料或重送同步。
- **DB｜資料與責任**：沿用 `staff_obligations` 的 `(case_no, obligation_identity)` 及既有事件；正式應付的日期本來就可空。目標查核是唯讀，不新增分期、日期、應付、資料表或 migration。
- **驗收**：S 同一案件有甲、乙兩位月嫂，案件層級同步回應整包遺失；甲已存在可唯一核對的正式應付但付款日未定，乙無可靠證據。T 重新查核清冊中所選的那位。A 先選甲並點「重新查核」，再回清冊選乙並查核；若清冊沒有可辨認的乙列，不從甲的結果推論乙。R 查甲只顯示甲的正式金額與付款日待確認，查乙僅顯示待確認；不重送 POST、不顯示整批同步成功。負例：選取列無人員 ID、同人多筆指派、出現他案／重複義務或 GET 失敗時，所選人維持待確認，不顯示旁人金額或估算。重用既有應付清冊 UI 驗收入口；未改既有成功回執的多人 `items`、業務計算與寫入規則。
