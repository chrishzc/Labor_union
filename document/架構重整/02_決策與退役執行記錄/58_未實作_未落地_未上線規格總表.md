# 未實作、未落地、未上線規格總表

## 1. 用途與判定規則

本表是 2026-08-12 的現況盤點快照。它只整理已人工確認的正式規格，並把四種常被混用的狀態分開：

| 狀態 | 定義 |
|---|---|
| 未實作 | 已核准的業務／技術契約尚沒有可接受的 production-code、schema 與驗收鏈。 |
| 已實作未落地 | 有局部成果，但尚未達 Work Package 的全部 acceptance；不得對外宣稱可用。 |
| 已驗證未上線 | 已完成核准 scope 的實作與驗證，但尚未對任何 production target 執行部署／schema apply。 |
| 刻意不自動化 | 規格明定只建立待辦、退款單或 anomaly；不產生付款、扣款或自動結清。這不是缺口。 |

「上線」僅指已取得實際 target 的 release execution record，並完成該 target 的 schema／application release 證據；本表不把本機、validation schema 或 disposable MySQL 當成 production。

## 5. 收斂後的工作順序

1. 若要啟動功能開發計畫，先將對應範圍收斂成精確 Work Package，取得 implementation authorization；不得直接以功能計畫修改 production code。
2. Writer Inventory 的四筆 `migrate_then_remove` 依 owner 分案：client identity direct route 需 entrypoint retirement package；staff leave legacy service 需等方案三 canonical request workflow 核准並完成 replacement 後才可退役。
3. 任一目標環境要套用既有 release 時，由指定 operator 依正式規格 18 保存 target、revision、artifact／schema digest、backup／rollback responsibility、switch 與 smoke receipt；不得以本機或 disposable evidence替代。
4. 全系統只有在具備實際 target execution record 後才能宣稱「已上線」。未指定 target 前維持「已驗證未上線」，不重開已完成的 Domain Work Package。

## 6. 維護規則

- `02` 新增、完成或封存 Work Package 時，同步更新 §2；`completed` 必須連結 evidence，封存後改指 archive path。
- 任一 release 實際執行後，更新 §3 的 target、revision、schema digest 與 receipt 連結；沒有這些資料不得改標已上線。
- 新增功能只有在正式規格與已核准 Work Package 產生後，才能加入 §2；提案、來源稿與歷史文件仍留在 §4。
