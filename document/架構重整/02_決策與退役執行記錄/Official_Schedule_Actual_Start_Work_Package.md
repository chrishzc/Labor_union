# 實際服務開始日與正式班表首日一致

## 基線與授權

- 變更前基線為 `95b1076bf660361772d65995d9e5a6db8ed9018a`。本案裁決來自使用者對排休案例的選擇「以正式班表首日為準，實際服務開始日存 12/2」。前提為承辦人輸入 12/1、當日排休，正式班表首日為 12/2。
- 業務規則由 [Orders §3.5](../../../.arch-map/requirements/01_Orders_Domain.md#35-actual-start-previewapply) 維護。Scheduling 提供生效的工作班次，Orders 保存實際首日。付款到期日沿各流程既有的 [Client Finance 契約](../../../.arch-map/requirements/04_Client_Finance_Domain.md#31-分期規劃實際開始日同步與通知資格cf-deposit-0102)。
- 涵蓋改變正式班表的命令。資料庫既有案件的批次補正、帳務重開、通知和部署各依原有權限與入口辦理。

## Delta

### ADDED

- `ACTUAL-START-SCHEDULE-01` 驗收首次存班及後續正式日期異動。以工作班次的案級最早日核對實際開始日。

### MODIFIED

- `ACTUAL-START-REPLAN-01` 驗收承辦人輸入排休日的情境，預覽與正式讀回顯示同一首日。
- 正式班表首次建立、重排、更正、延期、合併、分裂或復原後，由同一 Apply 保存相符的正式服務首日與 Orders 實際開始日。預覽用輸入日期試算並呈現將保存的日期。
- 既有服務事實保護、付款同步、版本、檔期與交易契約各沿原入口。只換人且日期相同時，兩個日期均已一致的案件須保存同一首日。

### REMOVED

- 移除可將排休日輸入值與較晚的正式首日一起保存為正式結果的規則。

整合者以同一候選版本讀回正式日期與 Orders 欄位。先跑各 owner 的 focused 驗證，再按實際交易覆蓋缺口選擇隔離 MySQL。保留既有資料、歷史事件與成功回執。遇到既有資料異常，記錄影響範圍，由資料 owner 決定修復方式。

規格驗證使用 `python -m scripts.validate_spec_hygiene --mode strict` 與 `python -m scripts.validate_agent_governance`。程式交付須有獨立驗證、實際執行結果、精確候選版本與既有入口讀回證據。
