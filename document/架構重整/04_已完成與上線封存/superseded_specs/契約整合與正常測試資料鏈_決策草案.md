## 已收斂的人工裁決摘要

1. 月嫂按媒合 segment 先簽；全部簽回且精確服務日守恆後，才形成簽約前服務承諾。
2. 契約簽署狀態與 Orders lifecycle 分離；訂金可在客戶簽回前精確核銷並使訂單進入
   「訂單成立」，但不得建立 execution assignment。
3. 客戶簽回必須在單一交易寫入簽署根事實、投影 `contract_identity`、執行 Contract
   Completion 並補足未建立期款；已存在的訂金義務不得重建或重複計算。
4. 訂金與客戶契約均完成後，Scheduling 才能把與 commitment 完全相同的月嫂／日期集合
   轉為 execution assignment；月曆、薪資與補助只讀 execution facts。
5. 合約檔案來自核准模板，產生版與簽回版均為不可變版本；LINE 只負責 durable delivery，
   傳送成功不等於簽署完成。
6. 舊資料與驗收 scenario 只能整合到受控的 `lu_test_dataset_*`；preserve migration 不得直接
   搬運 cache、current alert、mutable status 或其他 derived projection。

## 被取代時的 live-drift 快照

- Contract Signing schema、月嫂／客戶 send 與 signed-return application、LINE delivery task、
  `contract_identity` writer 及唯讀 UI 已有局部 worktree 實作。
- 客戶簽回尚未原子串接 Contract Completion；commands 缺 `expected_status_version` 與 payload
  fingerprint conflict；commitment 尚無 exact execution conversion writer。
- UI 只有狀態查詢，沒有模板、寄送、上傳簽回與 repair 操作。
- normal-case seed 只執行 Case Import；preserve migration 仍直接複製所有 source base tables，
  不符合正式 migration 邊界。

上述現況只能作 implementation evidence，不改變正式規格，也不構成完成或部署證據。
