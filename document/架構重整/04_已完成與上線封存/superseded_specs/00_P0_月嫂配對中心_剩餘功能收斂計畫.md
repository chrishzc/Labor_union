## 1. 定位

本文件只承接 WP68 完成後仍未落地的月嫂配對功能，不重做 Candidate Contact Pool、資訊-1／資訊-2、
意願紀錄、單月嫂方案、日期表 snapshot、客戶／月嫂確認或正式指派 gate。

本計畫是 active residual plan。使用者已於 2026-08-13 授權依本文件實作；每一個 change set
仍須先完成直接範圍的欄位來源 inventory、正式契約修正與精確 write set。找不到 canonical
source 的需求不得由 UI label 或舊欄位臆測補造。

## 2. 已完成基線

- 可同時聯繫多名具完整 coverage 的單月嫂候選，每人保有獨立寄送與意願歷史。
- 只有 `willing` 候選可經 fresh availability check 建立正式單月嫂 matching plan。
- 多月嫂共同服務是顯式 fallback，不是單月嫂頁面的預設流程。
- 已確認服務日期可形成客戶 parent snapshot、月嫂 segment snapshots 與 recipient confirmations。
- 客戶與全部月嫂未完成目前版本確認前，Assignment／schedule Apply 必須阻擋。
- Matching UI 不再提供 first-use case architecture bootstrap。

完成證據由 Scheduling 正式規格、封存 WP68 與 WP68 receipt 擁有。

## 3. Residual business scenarios

### MATCH-RES-01 五項篩選

配對中心以下條件預設全部勾選：

1. 檔期；
2. 服務地區；
3. 希望服務天數（容許相差幾天）；
4. 是否需要月嫂下廚；
5. 每日服務時數。

取消條件只影響本次 Query，不得修改根事實。重新勾選或改變容許天數後必須重新查詢並清除舊選擇。
2026-08-13 人工裁決：雙胞胎／多胞胎案件一律視為「月嫂偏好」而非 hard eligibility。它若在未來取得
Orders canonical 胎數條款，必須以可取消的偏好 filter 呈現；不得以 `clients.baby_info` 或其他自由文字
猜測胎數，也不得因缺值阻擋配對或正式指派。

### MATCH-RES-02 檔期與七日 buffer

- 正式 assignment、正式服務日或明確不可服務期間衝突：勾選「檔期」時不可列為可選候選。
- 只與 waiting-deposit lock 的七日 buffer 重疊：仍顯示候選，但標示日期、原因及「需人工確認」；
  不得顯示成完全可用，也不得直接 Apply。
- 同一月嫂可跨案件重複使用，正式服務檔期不得衝突。
- Query 與 Apply 使用同一 occupancy／lock 語意；Apply 必須 fresh-read、lock、validate。

### MATCH-RES-03 不可服務期間

月嫂長假、暫停接案等不可服務期間屬 Scheduling availability，應同時顯示於服務人員行事曆。
Matching 只能消費 bounded Query，不得在 UI 建立第二套日期事實。

目前正式管理功能尚未落地。本計畫先盤點 canonical source；若不存在，回傳 typed
`staff_unavailability_source_not_ready` 並另立正式 Work Package，不得為畫面自行新增 schema。

### MATCH-RES-04 單月嫂預設 UI

- 預設順序：案件摘要 → 五項篩選 → 候選結果 → Candidate Contact Pool → 意願 → 選定一人。
- 多月嫂 controls 只在單人無法完整 coverage 或管理員明確進入 fallback 時顯示。
- 用 bounded typed 案件摘要與訂單 deep link 取代 `_render_matching_order_summary()`。
- render function 不得接收 `segment_candidates` raw dataframe 或要求使用者以 staff ID 對照姓名。
- 候選 view 顯示姓名、逐條件結果、支援日期、coverage、衝突／buffer 提示與版本。
- 無候選時顯示 typed exclusion summary，不顯示空白 dataframe 或內部欄位。

### MATCH-RES-05 日期表過期與人工重送

正式服務日期異動後：

- 舊 snapshot／delivery receipt immutable；
- current projection 顯示 `sent_outdated`；
- 日期異動本身不建立新 intent、delivery task 或外部訊息；
- UI 顯示舊／新差異，由人員決定是否重送；
- 人工重送才建立新 snapshot／intent／task；
- 客戶及月嫂的舊 confirmation 不得套用到新版日期表。

## 4. Global → Domain → Subsystem → Module

### Global

- Query 唯讀、Preview 零寫入、Apply fresh-read／lock／validate。
- mutation 只有一個 outer Unit of Work；保存 actor、reason、version、fingerprint、idempotency 與 receipt。
- outward delivery 只能由 committed durable task 執行；provider failure 不回滾 matching facts。

### Domain ownership

| Owner | 根事實／責任 |
|---|---|
| Orders | 預計開始日期、希望服務天數、每日服務時數、服務地區、下廚需求等案件條款 |
| Staff | 月嫂資格與已確認的服務能力／偏好 |
| Scheduling | assignment、正式服務日、waiting-deposit lock、七日 buffer、不可服務期間與 occupancy |
| Matching | filter request、candidate explanation、Candidate Contact Pool、matching plan |
| LINE Delivery | recipient、payload snapshot、delivery task、status、retry |

實作前必須核對正式欄位文件與 live schema，確認下廚、服務天數能力及每日時數能力的 canonical source；
找不到時只記錄 gap，不得由 UI label 反推或新增欄位。

### Subsystems

1. Matching Recommendation Query：接收五項 filter policy，回傳 typed candidates／exclusion summary。
2. Scheduling Availability Query：分類 actual occupancy、service lock、七日 buffer、unavailable period。
3. Candidate Contact Pool Workflow：沿用既有聯繫、意願與 select-one 流程。
4. Schedule Confirmation Workflow：補 current snapshot 與 `sent_outdated` readiness。
5. Assignment Plan Workflow：Apply 前重驗 availability、occupancy、lock 與 confirmations。

### Module／UI

- Streamlit 只組合 typed API clients，不讀 DB、不計算 coverage、不自行判斷衝突。
- filter state 只屬於 Query request，不是業務 SSOT。
- API success payload 必須驗證為 typed view；raw `dict` 不得穿透 render function。

## 5. Typed candidate contract

每名候選至少包含：

- staff identity、顯示名稱及 source versions；
- required、supported、conflicting、buffer-overlap 日期摘要；
- 五項條件各自的 `matched`、`not_matched`、`not_applicable` 或 `source_not_ready`；
- formal availability eligibility、`selectable`、typed reason codes；可取消偏好不得自行改寫
  availability eligibility；
- coverage count／ranges 與是否可加入 Candidate Contact Pool。

UI 不得從中文 label 反推 `selectable`。

### R0 未裁決的條款來源 blocker

- **希望服務天數**：`orders.service_days` 可表示案件需求，但 Staff 沒有「可承接天數／容許差」的
  canonical capability；不得把既有排班天數或 legacy 欄位誤當能力。
- **是否下廚**：`staff_cooking_skills` 可表示月嫂能力，但案件端只有 BeClass 問卷自由文字，尚未有
  Orders canonical `requires_cooking` 條款。
- **每日服務時數**：`orders.service_hours_per_day` 是案件條款，`staff_time_slots` 是月嫂可服務時段；
  兩者尚未有已裁決的相容對照規則。

## 7. 驗收方式

### pytest

- 五項條件預設、取消、缺值、容許天數／每日時數邊界；
- actual conflict、buffer-only overlap、跨案件重複月嫂；
- stale、concurrent selection、Apply fresh conflict、exact replay／different payload；
- `sent_current → sent_outdated → manual resend → pending confirmations`；
- 測試 Adapter delivery success、retryable failure、terminal failure 與 projection。

### Browser UI

- 五項 filter 預設全勾，取消／重勾後清單與理由刷新；
- actual conflict 不可選，buffer-only overlap 仍顯示且有警告；
- 多名候選可分別聯繫、記錄意願，只能選一人建立正式方案；
- 無完整單人 coverage 時才能進多月嫂 fallback；
- 日期表過期後可人工重送並重新確認；
- 不顯示 raw dataframe、內部 ID 對照或架構 bootstrap。

### 本輪跳過真人 LINE 驗收

本輪不使用真人 LINE 帳號、真人 LINE App 或實際 provider delivery 作為完成 gate，也不保存手機畫面、
截圖或影片。LINE template、payload、binding、enqueue、retry 與 projection 使用 pytest、測試 Adapter及
本機 Browser UI 驗證。completion receipt 必須明示真人 provider 驗收為 `not-in-scope`，不得宣稱完成
正式 LINE delivery 驗收。
