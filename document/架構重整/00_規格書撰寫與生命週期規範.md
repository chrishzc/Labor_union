# 規格書撰寫與生命週期規範

> 狀態：`current-governance`（正式生效之規格書撰寫與生命週期規範）
> 配套檢核腳本：[`scripts/validate_spec_hygiene.py`](../../scripts/validate_spec_hygiene.py)
> 正式規格基線：[`01_規格基線/`](01_規格基線/)（全面遵守 Living Current Truth 標準）

## 1. 核心目標與邊界

本規範旨在消除規格書「前後互相衝突」與「舊規格殘留」的結構性問題，確立所有系統規格必須遵守的 **Living Current Truth（唯一現行契約）** 標準。

- **規格書只描述現在**：描述系統**當下應遵守的行為、資料所有權、契約與驗收標準**，不承擔決策日誌、測試日報或變更歷史的職責。
- **歷史脈絡交給 Git 與封存層**：為何改版、何時裁決、當時跑了幾條測試，由 Git commit history 與 [`04_已完成與上線封存/`](04_已完成與上線封存/README.md) 保存，不得留存在規格正文。
- **工作進度留在工作包**：施工中進度、待補資料與測試結果留在 [`02_決策與退役執行記錄/`](02_決策與退役執行記錄/README.md) 與 [`03_追蹤清單與證據/`](03_追蹤清單與證據/README.md)，結案後同步回主規格並移出工作樹。

---

## 2. 四大設計鐵律

### 2.1 唯一現行契約（禁止補丁堆疊）
1. 任何裁決更新契約時，**必須原地改寫受影響章節，並直接刪除被廢止的舊條文**。
2. 嚴禁在檔案頂端堆疊 `> YYYY-MM-DD 最新裁決` 引言，嚴禁在檔案末尾追加 `§17 / §18 / §19` 等覆寫前文的補丁章節。
3. 嚴禁使用「已取代」、「僅供歷史追溯」、「舊規則」、「supersede 前述」等方式保留失效內容。

### 2.2 單一所有權（SSOT，禁止跨檔複述）
1. 每項業務規則、公式、狀態機、API 契約與畫面分工，只能存在於**唯一一個 Owner 規格檔**。
2. 其他相關規格需要引用該規則時，只能使用相對路徑 Markdown 連結（例如 `見 [Client Finance](04_Client_Finance_Domain.md#2-核心不變量)`），**嚴禁在多份檔案用自然語言重述或摘要規則內容**。
3. 總索引（如 `15_正式規格索引與裁決總表.md`）必須維持為「純路由索引表」（領域／主題 → 唯一 Owner 規格路徑），不得再重複抄錄各次裁決全文。

### 2.3 執行狀態與測試紀錄徹底抽離
1. 規格書內嚴禁出現暫態施工或驗收字樣，例如：`尚未實作`、`待施工`、`本輪僅更新規格`、`未修改程式`、`X 項測試通過`、`passed`、`NOT_RUN`。
2. 人工測試手冊、UI 功能盤點紀錄、Closeout 結案備忘錄不屬於系統規格，不得存放於規格基線目錄。

### 2.4 單檔長度上限與按邊界分片
1. 單份規格書軟上限為 **600 行**。
2. 超過 600 行或同時橫跨 2 個以上獨立子系統／作業面的巨型文件，必須依能力邊界拆片為獨立規格檔，並由索引文件統一路由。

## 3. 標準規格書結構模板

所有新建或依本規範重寫的規格書，必須符合下列結構規範：

```markdown
# <領域或模組正式名稱>

## 1. 文件邊界與所有權

- 狀態：`current-spec`（或 `proposed-spec`）
- Owner：<Domain / Subsystem>
- 單一負責範圍：<本檔唯一擁有什麼業務語意或介面邊界>
- 關聯引用：<僅列相依規格的相對路徑連結，不複述內容>

## 2. 核心不變量與資料模型（SSOT）

- 列出 root facts、immutable events、derived projections 與不變量。

## 3. 公開契約與流程

- 列出 Query / Preview / Apply、API、狀態轉移與 typed errors。

## 4. 驗收標準

- 列出可驗證的 observable acceptance 與關鍵失敗情境。
```

### 格式硬規定
1. **UTF-8 編碼**：全檔為合法 UTF-8，不留行尾空白。
2. **單一 H1 標題**：第一行非空白內容必須為 `# <正式名稱>`，且全檔只允許一個 H1。
3. **章節化**：至少包含一個 `## ` 區段，且標題內禁止嵌入日期（如 `（2026-11-05 核准）`）。
4. **可攜相對連結**：所有 Markdown 內部連結必須為有效相對路徑（禁止 `file://`、本機磁碟路徑或 `/private/tmp/`），目標檔案必須存在。

---

## 4. 規格變更生命週期（Delta → Sync ＋ Archive）

日常開發若涉及契約修改，一律走三步閉環，不直接拿主規格檔打草稿：

1. **Delta（施工期間）**：在 `02_決策與退役執行記錄/<task-slug>.md` 以 `ADDED / MODIFIED / REMOVED` 三段式描述本次契約差異，並於該檔記錄測試計畫與執行進度。
2. **Sync（結案收斂）**：實作與驗收通過後，依 Delta 內容回到主規格目錄**原地更新受影響條文、直接刪除廢止舊條文**。
3. **Archive（移出工作樹）**：執行 [`scripts/validate_spec_hygiene.py`](../../scripts/validate_spec_hygiene.py) 通過後，將 `02_` 的任務檔移出工作樹，由 Git commit 保存變更脈絡。

## 5. 自動化檢核規範（對應檢查腳本）

[`scripts/validate_spec_hygiene.py`](../../scripts/validate_spec_hygiene.py) 對目標規格目錄執行以下確定性規則檢查（任何一項失敗在 `strict` 模式下皆回傳非零結束碼）：

| 規則代碼 | 檢查內容 |
| :--- | :--- |
| `invalid_utf8` | 檔案無法以嚴格 UTF-8 解碼 |
| `missing_h1_title` / `duplicate_h1_title` | 首個非空白行非 `# ` 標題，或出現多個 H1 |
| `missing_section` | 缺少任何 `## ` 二級章節標題 |
| `max_lines_exceeded` | 單檔總行數超過上限（預設 600 行） |
| `non_spec_document` | 檔名或內文屬於結案備忘（Closeout）、盤點紀錄或人工測試手冊 |
| `top_patch_blockquote` | 檔案前 35 行出現日期型或「最新裁決／授權／同步」引言補丁 |
| `dated_heading` | 標題（`#`～`######`）嵌入 `YYYY-MM-DD` 日期標籤 |
| `chronological_patch` | 正文出現「`YYYY-MM-DD`＋裁決／授權／核准／修訂／更正」編年敘事 |
| `legacy_residue` | 出現 `已取代`、`歷史追溯`、`舊規則`、`舊機制`、`舊流程`、`舊版本`、`歷史來源`、`supersede` 等殘留詞 |
| `retired_tech_residue` | 出現已退役前端技術名詞（`Streamlit`、`ui/app.py`、`.streamlit/`） |
| `execution_status_residue` | 出現 `尚未實作`、`待施工`、`本輪僅`、`測試通過`、`passed`、`NOT_RUN` 等過渡執行狀態 |
| `non_portable_link` | 連結使用 `file://`、本機盤符路徑或 `/private/tmp/` 等不可攜路徑 |
| `broken_markdown_link` | 相對 `.md` 或本地資產連結指向不存在的檔案 |
